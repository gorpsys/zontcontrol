# Проверка предложенного протокола оркестрации через name

14.10.2026. Предложение владельца проверено офлайн; этот документ не меняет
согласованный контракт мьютекса и не объявляет протокол принятым.
Реальные команды и записи в ЛК в этой проверке не выполнялись.
Свойства строкового API — [натурный тест](2026-10-14-zont-name-live-probe.md),
наличие штатных механизмов — [исследование API](2026-10-14-zont-control-lock-api.md).

## Проверяемая схема

В строке есть UUID координатора, срок аренды и один слот заявки. Исполнитель
при запуске создаёт UUID. Свободную/просроченную аренду пытается занять записью
своего UUID; после случайной паузы проверяет, что он остался владельцем.
Участники дописывают свою заявку в свободный слот. Координатор переводит
request в confirmed, ждёт finished и очищает слот. Владелец запрашивает
доступ для своих действий тем же способом. Действия координатора продлевают
аренду; после её истечения все могут пытаться стать координатором.

## Модель и границы проверки

Предположены наиболее благоприятные свойства API: каждое отдельное чтение
и запись атомарны, чтение видит последнюю завершённую запись, часы совпадают,
сеть не возвращает ошибки. Пары read/modify/write не атомарны. Запись name
заменяет всю строку; отдельного атомарного добавления суффикса API не имеет.
Между чтением и записью процесс/запрос может задержаться.

Проверены последовательный рабочий сценарий и три конкретных конфликтующих
порядка операций в исполняемой Python-модели. Все утверждения сценариев
сошлись: нормальный порядок работает, два порядка допускают одновременно
два управляющих действия, третий теряет finished. Это проверка
контрпримеров, не полный перебор всех состояний и не оценка вероятностей.
Модель предполагает повторную проверку своего владельца при подготовке
координатором подтверждения; это не устраняет паузу между чтением и записью.

## Контрпример 1: случайная пауза не выбирает единственного координатора

| Шаг | Действие |
| --- | --- |
| 1 | A и B читают свободную строку |
| 2 | A записывает владельца A, ждёт случайное время, читает A и начинает координацию |
| 3 | X пишет заявку; A читает её и владельца A, готовит подтверждение X, затем задерживается |
| 4 | B завершает ранее подготовленную запись владельца B, ждёт и читает B |
| 5 | Y пишет заявку; B подтверждает Y; Y читает подтверждение и начинает действие |
| 6 | A завершает подготовленную запись подтверждения X с владельцем A и продлённой арендой |
| 7 | X читает своё подтверждение и начинает действие; Y ещё действует |

И X, и Y получили адресованное им подтверждение. Проверка владельца перед
подготовкой записи соблюдена, но запись A была задержана. Длительность
случайного ожидания не запрещает такую задержку. Позднее обнаружение смены
владельца не отменяет уже начатое действие Y.

## Контрпример 2: устаревшая заявка стирает подтверждение и продление аренды

| Шаг | Действие |
| --- | --- |
| 1 | Координатор O, expires=10, слот свободен. X читает это состояние и готовит заявку |
| 2 | Y успевает записать заявку. O подтверждает Y и продлевает expires до 20. Y начинает длительное действие |
| 3 | X записывает свой суффикс на основе первого чтения: подтверждение Y заменяется request X, expires возвращается к 10 |
| 4 | В момент 11 B видит просроченную аренду и занимает её, сохраняя видимый request X |
| 5 | B подтверждает X; X начинает действие, пока Y ещё действует |

Требование X «нет чужой заявки» было истинным при его чтении. Логическое
изменение только своего суффикса физически заменило всю строку. Контрпример
не требует, чтобы новый координатор удалял занятую очередь при захвате:
он может сохранить видимый слот и всё равно не знать о потерянном confirmed Y.
Локальная память O о Y не передаётся новому координатору.

## Контрпример 3: продление аренды теряет finished

1. Координатор читает confirmed X для продления аренды.
2. X завершает действие и записывает finished X.
3. Координатор записывает продлённую аренду с ранее прочитанным confirmed X.

Финиш исчез. Координатор может бесконечно ждать его; повторное действие X
по тому же подтверждению было бы ошибкой. Повторы finished могут улучшить
восстановление, но сами не дают гарантии прогресса при произвольных задержках.

## Дополнительные неопределённости

- Продление «при каждом действии» не задаёт heartbeat во время ожидания
  finished. Координатор может быть жив и ждать, а аренда истечёт.
- Новый владелец должен учитывать незавершённый доступ старого клиента.
  Само истечение аренды координатора не доказывает завершение чужой команды.
- UUID процесса не идентифицирует отдельную заявку. Для повторных действий
  нужны отдельный request_id и запоминание уже исполненного подтверждения.
- HTTP timeout не доказывает отсутствие записи. Запоздалая запись может
  заменить более новое состояние. Повторная запись также не является CAS.
- Единственный слот без порядка обслуживания не гарантирует отсутствие
  голодания участников.

## Вывод

В штатном последовательном порядке схема сериализует действия. При допустимых
задержках строгая монополия и прогресс не обеспечиваются. Случайное ожидание
полезно как backoff, но не является доказательством единственного владельца.

Периодический heartbeat, повторение финиша, request_id, локальный мьютекс
между потоками одного процесса и остановка при потере владельца устраняют
часть практических проблем. Однако они не делают межклиентское изменение
name атомарным и не запрещают устаревшему владельцу отправить команду ZONT.

Для строгой монополии предпочтителен общий исполнитель; для независимых
координаторов требуется подтверждённый механизм общей синхронизации и
продуманная граница передачи активного управления. Вариант без автоматического
перехвата — заранее назначенный владелец и явная передача права после
завершения всех действий — сохраняет безопасность ценой остановки при потере
владельца, при дополнительных согласованных правилах участников.
