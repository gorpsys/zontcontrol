# Вторая строка устройства: проверка notes

> Исторический отчёт от 14.10.2026: исследование отменённой координации.
> Синхронизация удалена по [решению от 20.10.2026](../history/2026-10-20-remove-synchronization.md);
> действующий [управляющий API](../agents/contracts.md#управляющий-api) не использует эти критерии.
> Исходные измерения, допущения и выводы ниже сохранены.

14.10.2026, SMART 2.0, device_id=700877. Исследована возможность второй
строки для обсуждаемого протокола оркестрации. Проверка реальная, через
полный API, с коротким временным маркером и последующей очисткой.
Настройки отопления и управляющие команды не отправлялись.

## Прочитанные кандидаты

POST /api/devices с load_io=false возвращает:

| Поле | Начальное значение | Результат записи через update_device |
| --- | --- | --- |
| name | Существующее название | Уже проверено отдельно |
| individual_device_note | Пустая строка | ok=true, но значение не изменилось |
| notes | null | Маркер записался и точно прочитался |
| individual_device_name | Строка | Запись не тестировалась |

boiler_vendor, boiler_model, gui_settings и user_data в ответе этого прибора
отсутствовали. Содержимое прочих полей аккаунта в отчёт не переносилось.

## Работающий контракт

Чтение: POST https://my.zont.online/api/devices, затем notes нужного прибора.
Изменение, пример тела:

```json
{"device_id": 700877, "notes": " [zc:metadata-test=1]"}
```

Запись выполнена одним экземпляром ZontClient; отдельный экземпляр с тем же
токеном и собственным HTTP transport прочитал точную 21-символьную строку.
Это подтверждает серверное сохранение, а не локальное состояние клиента.
Название name и individual_device_name не изменились.

При проверке individual_device_note успешный ответ API не сопровождался
сохранением строки. Этот способ изменения индивидуальной заметки не работает
в исследованном запросе; другие способы её изменения не проверялись.

## Очистка и исходный null

Попытка вернуть notes=null через update_device получила HTTP 400.
Пустая строка notes="" принята и прочитана точно другим экземпляром клиента.
Тестовое содержимое удалено. Начальное отсутствие заметки восстановлено
по содержимому, но тип значения изменился: было null, стало пустой строкой.
Это различие не скрывается как точное восстановление исходного JSON.

После очистки выполнен ещё один полный цикл: пустая строка → тестовый маркер
→ пустая строка. Запись, чтение отдельным клиентом и точное восстановление
успешны. name и individual_device_name оставались неизменными во всех проверках.

Ограничения длины и символов notes не проверялись; результаты больших строк
для name нельзя автоматически переносить на notes.

## Значение для оркестрации

Есть два читаемых поля — name и notes — и запись только notes фактически
сохраняет name. Проверка обратного направления и одновременной записи обоих
полей здесь не выполнялась. Отдельные тела запроса позволяют не перезаписывать
name при логическом изменении notes; свойство CAS этим не появляется.

Можно рассматривать name для координатора/аренды, notes для заявки и её
состояния. Разделение устраняет необходимость заявителю включать прочитанную
аренду в своё тело записи. Однако остаются гонки выбора координатора и
конкурирующей записи в один слот notes. Этот результат сам по себе не доказывает
строгую монополию предложенного протокола.
