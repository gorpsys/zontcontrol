## Реализация и границы

Приватный `_RowCache` находится в `zontcontrol/monitor.py`. Один assessment
получает один локальный LRU; самостоятельный ленивый `history_samples`
создаёт свой. Между вызовами данные не сохраняются. Ключ — `(id(row), cutoff)`;
cutoff — точный UTC datetime. Запись удерживает сильную ссылку на frozen
HeatingSeries и проверяет `is`, поэтому время жизни записи исключает повторное
использование её id другим объектом. Структурное равенство рядов не используется.

Значение — неизменяемые tuple отфильтрованных точек и их исходных timestamps.
Промах выполняет тот же полный фильтр `measured_at <= cutoff`; hit переиспользует
результат. Новый cutoff или другой объект дают отдельную запись; вытеснение
LRU меняет только стоимость повторной подготовки. None обходит кэш,
пустой существующий ряд занимает запись. Лимит записей не задаёт лимит байтов.

Публичные сигнатуры, DTO, Controller, адаптер и чистый детектор не менялись.
Сохранены span-only, буфер 40, арифметика datetime, интерполяция, reset,
порядок дублей, null/quality и весь диагностический результат. Кэш интерполяции
(вариант 3), absence (вариант 4), batch и изменение порогов вне этой работы.

## Метод CPU и trace

Таймер CPU — `process_time_ns`, wall — `perf_counter_ns`. На каждом из
137591 окон измерен настоящий публичный `assess_history` baseline и всех
capacity 6…14. Декодирование, построение window, сравнение и запись исключены
из таймера. Порядок capacity циклически сдвигается по номеру окна modulo 9;
на нечётном окне весь блок обращён. Baseline чередует начало/конец блока.
Второй полный проход аналогично измеряет `list(history_samples(history))`.

Capacity устанавливалась через приватный default конструктора вне таймера,
с восстановлением `(7,)` в finally. Обёрток, mock, prepared-samples и AST-патчей
в timed path нет. Каждый публичный вызов начинает с нового кэша.
Suite и другие замеры параллельно не запускались.

Базовая 7 принята: сумма CPU assess меньше baseline, все три контрольные
медианы >1.0. Для существенного преимущества конкурента план требует CPU
<=0.98 от 7 одновременно на полном replay и во всех трёх нормированных
контролях. Таких конкурентов нет. 2% — инженерный порог, не статистическая
гарантия. Лучший суммарный результат 13 выигрывает у 7 лишь около 0.026%,
преимущество не повторяется во всех контролях. 6 расходует на 2.188% больше
CPU, чем 7. Поэтому **7 — минимальная ёмкость на измеренном плато эффективности**;
выбор основан на фактическом CPU, а отсутствие eviction объясняет trace.
