# Проверка предложения R1/R2

> Исторический отчёт от 14.10.2026: исследование отменённой координации.
> Синхронизация удалена по [решению от 20.10.2026](../history/2026-10-20-remove-synchronization.md);
> действующий [управляющий API](../agents/contracts.md#управляющий-api) не использует эти критерии.
> Исходные измерения, допущения и выводы ниже сохранены.

14.10.2026. Продолжение проектирования по предложению владельца.
Проверки офлайн; реальных записей в ЛК и команд устройству не было.
После этого разбора владелец принимает текущую схему с риском, сбором
статистики и доработками. Ниже сохраняются контрпримеры и ограничения;
безопасность и надёжность 99.9% не объявлены доказанными.

## Предложение и обязательные проверки

- R1 — лидерство и канал запросов/heartbeat исполнителей.
- R2 — единственный источник разрешения исполнения; писать могут только лидеры.
- Исполнитель пишет только R1, читает R2 и не действует без совпавшего grant.
- Перед выдачей/продлением R2 лидер подтверждает свою роль чтением R1.
- Исполнитель сопоставляет owner, request_id, grant_id и текущего лидера R1.
- Отсутствие heartbeat не отзывает уже выданную аренду немедленно.

grant_id связывается с уникальным token конкретного срока лидерства, а не
только UUID процесса: один процесс может переизбираться. Для продления нужны
уникальные revision записи, не повторное значение старого разрешения.
Сериализация назначений одним действующим лидером — полезное свойство этой
схемы. Дополнительные проверки необходимы, но сохранность лидерства в R1
при записи исполнителей требуется доказать отдельно.

## Проблема общей записи R1

ZONT записывает целую строку, а не атомарно executor_request. Исполнитель
включает в запрос копию leader/token/seq/lease_s, прочитанную раньше. Поэтому
он может откатить seq после продления, восстановить старого лидера или FREE.
Потеря заявки и восстановление лидерства имеют разные последствия.

Если наблюдение L сравнивает всю R1, постоянные обновления заявок не дают
неизменного интервала даже после crash лидера. Если оно сравнивает только
проекцию лидерства, копии исполнителей могут создать ABA: наблюдатель видит
старую проекцию в начале и конце L, хотя между ними было продление.

Ограничение каждой записи Delta не устраняет проблему: старое значение может
переходить от одного исполнителя к следующему. Каждый читает его недавно,
поэтому конечная цепочка удовлетворяет Delta, хотя сам token старый.

## Временной контрпример с обеими дополнительными проверками

Офлайн-модель использует линеаризуемые get/set, одинаковые скорости часов,
Delta=1, L=30, W=2*Delta. Наблюдатель сравнивает блок лидерства R1; запросы
меняют только служебную часть, копируя этот блок. Это проверка одного
допустимого порядка, не полный перебор.

В начале A имеет seq=2. В 28.3 A корректно продлевает аренду записью seq=3;
старый deadline около 29.406 оставляет Delta на продление. Новый локальный
deadline A — 57.706. Несколько копирующих исполнителей чередуют seq=2 и seq=3
в R1, каждый за время меньше Delta. В момент 30 наблюдатель видит seq=2,
как при первом чтении в момент 0, и ошибочно считает аренду истёкшей.

| Время, с | Действие |
| --- | --- |
| 30.01 | B записывает свой token |
| 30.5 | Исполнитель восстанавливает A/seq=3 из чтения в 29.7 |
| 31.0 | Другой восстанавливает B из чтения в 30.1 |
| 31.5 | Следующий восстанавливает A/seq=3 из чтения в 30.6 |
| 32.0 | Следующий восстанавливает B из чтения в 31.1 |
| 32.1 | B после барьера больше 2*Delta подтверждает свой token |
| 32.2 | B проверяет R1=B, читает FREE в R2 и готовит разрешение Y |
| 32.5 | Исполнитель восстанавливает A/seq=3 из чтения в 31.6 |
| 32.6 | A проверяет точный собственный token и seq=3, читает всё ещё FREE в R2 и готовит разрешение X |
| 32.9 | Запись B в R2 с разрешением Y завершается |
| 32.95 | Исполнитель восстанавливает B из чтения в 32.15 |
| 32.96 | Y читает своё разрешение R2 и совпадающий B в R1; начинает операцию длительностью Delta |
| 33.2 | Завершается подготовленная запись A в R2 с разрешением X |
| 33.3 | Исполнитель восстанавливает A/seq=3 из чтения в 32.55 |
| 33.31 | X читает своё разрешение R2 и совпадающий A в R1; начинает операцию длительностью Delta |

Операции Y [32.96,33.96] и X [33.31,34.31] пересекаются. Подготовка записи
R2 B заняла 0.7 с, A — 0.6 с; обе укладываются в Delta. Все перечисленные
копии R1 тоже укладываются в Delta. A проверил свою последнюю seq=3, не просто
имя процесса. B прошёл барьер. Исполнители проверили соответствие grant лидеру.

Причина — нарушение модели лидерского регистра через чужие read/modify/write:
проверки видят восстановленный header, а не гарантированно актуальный срок.
Предположение «ровно один корректно действующий лидер» перестаёт следовать
из первоначального доказательства Fischer. Пример требует чтения/записи
обоими лидерами до окончательного получения доступа; каждый видел FREE при
подготовке, а CAS для проверки FREE в момент применения отсутствует.

## Часы и срок разрешения

leader_until, lease_until и heartbeat нельзя сравнивать как абсолютные
CLOCK_BOOTTIME разных машин. Даже равные скорости не устраняют разницу
времени загрузки. Пример: часы лидера 950, исполнителя 10; lease_until=960.
Через 11 секунд аренда лидера уже истекла, но исполнитель видит 21<960.

Простой переход на lease_s с deadline=received_at+V также небезопасен:
позднее чтение старого grant искусственно начинает срок заново.

Возможная основа решения — уникальный challenge/heartbeat_nonce исполнителя,
который лидер подтверждает в R2 как ack_nonce. Исполнитель помнит момент
отправки этого конкретного nonce и считает локальный deadline от него,
а не от ответа/чтения. Лидер мог выдать подтверждение только после появления
nonce. Для каждого продления новый nonce; повторные чтения того же ack не
продлевают deadline. Это требует отдельной проверки формул и полных окон.

Пример направления формата, ещё не готовый безопасный протокол:

```json
{"owner":"E1","request_id":"abc123","grant_id":"leader-token:105","leader_token":"leader-token","revision":1,"lease_s":90,"ack_nonce":"heartbeat-nonce"}
```

Новый лидер наблюдает полную неизменную запись R2 не меньше lease_s между
первым ответом и отправкой последнего чтения; изменения revision сбрасывают
наблюдение. Считывание R2 не даёт права игнорировать ещё активного владельца.

## Связь с finally

Предложение вводит отдельную аренду исполнителя R2. Обязательная проверка
совпадения с текущим лидером может прекратить разрешение раньше lease_s при
смене R1. Это снова затрагивает off из finally, хотя аренда лидера была
отделена от управляющего действия предыдущим решением владельца.

Для сброса желательно выдавать бюджет на весь импульс, включая cleanup,
без обязательного продления в середине. Но правило при смене лидера во время
активного grant всё равно нужно определить: считать ли прежнее разрешение
действующим до срока либо прекращать его по изменению R1. Здесь выбор не
сделан и прежняя гарантия finally молча не меняется.

## Что согласовано и что осталось

Согласованы необходимые проверки лидера перед записью R2 и исполнителя
перед действием, единственный писатель R2 при корректном лидерстве и запрет
немедленного отзыва из-за отсутствующего heartbeat.

Остались: безопасная публикация запросов без восстановления лидерства R1;
протокол относительных сроков и подтверждения свежести grant; судьба активного
grant/finally при смене лидера. Изолированный лидерский регистр и отдельный
канал запросов снимают первую причину, но конкретная реализация канала
пока не выбрана. Две обычные строки не обеспечивают атомарного изменения
их отдельных логических частей автоматически.

Последнее решение владельца принимает текущую схему со сбором статистики
и доработками по её результатам, без предварительного подтверждения 99.9%.
[Учёт и целевой критерий](../history/orchestration-risk.md)
не подменяют контрпримеры вероятностной оценкой: её пока нет. Замечание №6
закрыто решением о риске; выявленные технические ограничения сохраняются.
