# Проверка условного Fischer + lease

14.10.2026. Оценка предложенного владельцем протокола одной строки notes.
Это анализ требований, не реализация и не изменение согласованных контрактов.
Команд устройству и записей в ЛК не выполнялось.

Последующее решение владельца: пункты о барьере, окнах и наблюдении приняты;
Fischer применяется только для выбора лидера с общим пределом 20 минут,
который координирует доступ через вторую строку. Текущий согласованный
[контракт и пересчитанные сроки](../history/leader-election.md) хранятся
отдельно. Разделы ниже сохраняют анализ первоначального L=30 и прямой аренды
защищённой работы; конфликт с finally снят разделением этих ролей.

## Принятые для анализа предположения

- Каждый get/set строки линеаризуем. CAS нет; участников заранее не знаем.
- Все участники соблюдают протокол и совместимые параметры L, rho и Delta.
- Часы монотонные; используются локальные интервалы, а не wall-clock.
- Скорости часов укладываются в заявленный предел расхождения.
- Delta действительно ограничивает задержки соответствующих последовательностей
  запросов и их применение, включая паузы процесса. Это предположение о среде.
- Нефиксированные записи никогда не повторяются; случайные UUID/token не
  сталкиваются. Последнее — дополнительное условие математической гарантии,
  при 128 случайных битах практически очень сильное, но вероятностное.

При временных ограничениях Fischer-подобное взаимное исключение на read/write
регистре возможно. Контрпримеры без ограничения задержек из предыдущего
обсуждения не являются доказательством невозможности этой условной схемы.
Линеаризуемость API ZONT натурными тестами ранее не доказана: совпадение
последовательных чтений является наблюдением, а не контрактом сервиса.

## Числа при L=30, rho=0.01

| Величина | Значение |
| --- | --- |
| V = L * (1-rho)/(1+rho) | 29.405940594 с |
| T_r = V/3 | 9.801980198 с |
| poll без jitter | 3 с |
| Максимальное Delta из V >= 8*Delta | 3.675742574 с |
| K = (1+rho)/(1-rho) | 1.020202020 |

Если Delta >= 10*p99.9 RTT, при остальных условиях этой конфигурации
p99.9 RTT должен быть не больше примерно 367.6 мс. Это следствие условий
конфигурации, не измерение задержек ZONT. Короткие предыдущие проверки не
образуют надёжную оценку p99.9.

## Контрпример к ожиданию ровно Delta по локальным часам

Исполняемая офлайн-модель проверила следующие числа: Delta=1 с, скорость A
равна 1.01, скорость B равна 1.00. Различие скоростей не превышает rho=0.01.
В таблице условное внешнее время используется только для описания трассы;
алгоритм не получает синхронизированные часы.

| Время, с | Действие |
| --- | --- |
| 0 | A и B читают FREE |
| 0.001 | A записывает свой token |
| 0.991099 | A выждал Delta по своим быстрым часам, читает свой token и входит |
| 0.996 | B завершает запись своего token; окно от чтения FREE до записи всё ещё не превышает Delta |
| 1.996 | B выждал Delta, читает свой token и тоже входит |
| 29.115793 | Только теперь истекает локальная аренда A |

Управляющие действия могут пересекаться, хотя заявленные ограничения задержек
и расхождения скоростей часов соблюдены. Следовательно, ожидание Delta требует
точного определения единиц и запаса на относительную скорость часов.

Консервативная нижняя граница при трактовке скоростей через 1±rho:
W > Delta * (1+rho)/(1-rho). Строгое неравенство либо дополнительный запас
исключают гонку на границе. При rho=0.01 ожидание 2*Delta даёт простой запас,
но при произвольном rho его достаточность надо проверять заново. Jitter может
добавляться к безопасной нижней границе, а не уменьшать её.

## Что нужно явно определить в переходах

1. Захват включает чтение FREE либо подтверждение истечения чужой записи и
   последующую запись собственного уникального token. Всё окно от отправки
   этого разрешающего чтения до ack записи должно быть <= Delta. Превышение
   означает отказ от входа, даже если token ещё виден.
2. W отсчитывается после успешного ack записи. Deadline аренды одновременно
   отсчитывается от отправки этой записи. Это два разных начала интервала:
   задержка ack не должна продлевать аренду или сокращать барьер Fischer.
3. После W выполняется подтверждающее чтение точного собственного значения.
   Оно также должно уложиться в свой бюджет. До этого защищённых действий нет.
4. У занятой записи наблюдатель запоминает полное значение и момент получения
   первого ответа. После любого изменения owner/token/seq начинает наблюдение
   заново. От первого ответа до отправки последнего чтения должно пройти >= L;
   только тот же самый полный record разрешает попытку перехвата. Срок не
   записывается как абсолютное локальное время, непонятное другому процессу.
5. Начальная запись захвата не требует can_act, иначе захват логически
   невозможен. Проверку требуют продление, освобождение и защищённая работа
   уже подтверждённого владельца.
6. d_op охватывает весь участок от успешного can_act до окончательного
   завершения действия, включая паузу перед отправкой и применение запроса.
   Определение Delta только от первого отправленного запроса не покрывает
   автоматически промежуток между can_act и этой отправкой.
7. Продление разрешается только пока хватает старого бюджета для его
   завершения. Новое значение seq уникально; новый deadline начинается с
   отправки продления. Неизвестный результат означает LeaseLost, а не retry
   той же записи или предположение о продлённом владении.
8. Перед FREE завершаются все защищённые действия и in-flight команды.
   После отправки FREE клиент уже не действует; неизвестный исход не даёт
   права повторять FREE после потери аренды и стирать нового владельца.

Локальные потоки одного владельца должны согласовывать seq, deadline,
renew/release и отмену; иначе heartbeat и освобождение способны конфликтовать
даже без второго процесса. Точные окна нужны для каждого перехода, а не
один общий таймер, включающий ожидание W и неизвестно какие HTTP-вызовы.

## Конфигурация, измерения и ограничения

Все участники должны использовать общую допустимую временную модель.
Малый Delta одного клиента не ограничивает позднюю запись другого клиента.
Наблюдение L не безопасно, если другой участник использует большую аренду.
Разные параметры допускаются только при доказанном совместимом контракте.

10*p99.9 — практический выбор запаса, не доказательство жёсткой верхней
границы. HTTP 429, долгие паузы, миграция VM и нарушение дрейфа могут вывести
исполнение за принятую модель. CLOCK_BOOTTIME помогает обнаружить прошедшее
время suspend; оно само по себе не предотвращает запоздалое действие.
Измерение превышения после отправки не отменяет уже применённую команду.

Нужно проверять в notes весь сериализованный owner/token/seq, включая запас
на рост seq и точное чтение. Проверки только 16 байт недостаточно для записи
с 128-битным token и остальными полями. Большие строки notes пока не тестированы.

Схема остаётся условной, без fencing ZONT, без справедливости и без гарантии
прогресса при произвольных отказах. Это не Paxos: quorum и consensus здесь
не появляются, а безопасность опирается на временные границы.

## Совместимость со сбросом котла

Импульс длится 40 с, а V по умолчанию около 29.4 с. Если d_op обозначает
весь импульс, can_act(40) при L=30 всегда отказывает. Если d_op относится к
отдельному HTTP-действию, владение надо продлевать на протяжении всего импульса.

Ранее согласованный finally немедленно отправляет off при штатной остановке
и исключениях. Новый запрет защищённых операций после LeaseLost конфликтует
с этим поведением: клиент не может одновременно считать себя потерявшим
монополию и безусловно отправлять off. Это продуктовая граница, которую
нужно решить отдельно; данный анализ не меняет старое правило молча.
Увеличение L может дать бюджет на полный импульс и штатный cleanup, но не
устраняет неизвестные исходы и все случаи потери владения.

## Вывод

Идея условного Fischer + lease оправданна для заявленной ограниченной среды.
Текущая формулировка не завершает доказательство: найден контрпример к
ожиданию ровно Delta, необходимо определить окна переходов, совместимость
параметров, бюджет can_act и поведение cleanup при LeaseLost. Код клиента,
регистратора и котла не менялся.
