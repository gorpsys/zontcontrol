# Монополия управления и общие флаги в API ZONT

> Исторический отчёт от 14.10.2026: исследование отменённой координации.
> Синхронизация удалена по [решению от 20.10.2026](../history/2026-10-20-remove-synchronization.md);
> действующий [управляющий API](../agents/contracts.md#управляющий-api) не использует эти критерии.
> Исходные измерения, допущения и выводы ниже сохранены.

Дата исследования: 14.10.2026. Цель — найти штатную монополию управления
прибором либо общие флаги устройства/аккаунта, читаемые другими клиентами.
Первый этап — опубликованные спецификации и публичные GET-запросы
документации без авторизации. Затем владелец разрешил отдельные реальные
проверки строки name с сохранением исходного префикса; результаты —
[натурные тесты названия](2026-10-14-zont-name-live-probe.md).
При поиске второй строки выполнены [реальные тесты notes](2026-10-14-zont-notes-live-probe.md).
Настройки отопления и управляющие команды в этих тестах не менялись.

## Результат

В опубликованной документации не найден штатный lock/unlock, mutex, lease,
атомарный test-and-set/CAS, условная запись по revision/If-Match или передача
токена владельца в управляющих командах. Не найден и документированный
произвольный флаг/словарь переменных уровня аккаунта. Это вывод о доступной
документации, а не доказательство отсутствия недокументированных методов.
Полный API прямо предупреждает, что документация обновляется и неполна.

Состояние существующей кнопки-переключателя читается и изменяется через API:
это кандидат на общий согласительный флаг. Однако безвредный переключатель,
не связанный с физическим действием, на SMART 2.0 не проверен; атомарный захват
через него не поддерживается опубликованным контрактом.

При дополнительной проверке строковых полей найден более прямой вариант:
name — название устройства, документированное среди общих настроек всех
типов приборов. Настройки читаются через devices и изменяются через
update_device. Реальные тесты на SMART 2.0 подтвердили запись и точное чтение
через полный API и Widget v3, включая JSON, Unicode и 65536 ASCII-символов.
Исходное название сохранялось префиксом тестовых значений и восстанавливалось
после каждого блока. Это общая строка, но не атомарный замок.

## Кандидаты на общие флаги

| Кандидат | Что документировано | Чего это не доказывает |
| --- | --- | --- |
| name в полном API | Строка названия; чтение devices, изменение update_device; на SMART 2.0 проверены JSON, Unicode и длины до 65536 ASCII-символов | Нет атомарной условной записи; верхний предел и ограничения веб-формы не установлены |
| ToggleButton в v3 | id, name, active: boolean/null; чтение через GET /devices и GET /devices/{device_id}; изменение через POST /devices/{device_id}/controls/{entity_id}/actions/trigger с target_state | Нет owner, срока владения, ожидаемого старого значения или атомарного захвата. Создание отдельного безвредного переключателя на SMART 2.0 не проверено |
| notes в полном API | Документировано при add_device; реальная запись update_device и чтение devices подтверждены на SMART 2.0 | Нет CAS; ограничения длины не проверены; запись null получила HTTP 400, очистка пустой строкой работает |
| update_device | Обновление документированных настроек, сохранение неуказанных вложенных полей | Не объявляет произвольные поля/метаданные; нельзя выводить поддержку notes из самого наличия метода |
| custom_controls / custom_controls_state | Модельно-зависимые команды и состояния ZTC-7xx/Mega SX | Не подтверждают произвольные флаги SMART 2.0 |
| state, флаги состояния | Телеметрия устройства | Не право записи произвольных значений и не владение управлением |
| Токены аккаунта | Создание, перечисление и удаление credentials | Не общий словарь значений и не механизм блокировки |

Названия gui_settings и user_data в опубликованном справочнике не найдены.
set_io_port описывает конкретные воздействия guard-state, siren,
engine-block, webasto и auto-ignition, а не произвольное key/value-хранилище.
Его ответ ok, по документации, возможен даже без доставки команды прибору.

### Название устройства как строка

В разделе «Параметры устройств → Общие для всех типов устройств → Настройки»
поле name объявлено строкой «Название». Общая часть документации прямо
связывает чтение настроек с devices, а их изменение — с update_device.
Это более полный документированный контракт, чем notes, показанное только
при добавлении; его обновление позднее подтверждено натурным тестом.

Документированный путь чтения: POST https://my.zont.online/api/devices
с телом {"load_io": false}, затем поле name нужного прибора в devices.
Метод чтения по устройству API использует POST, хотя настройки не меняет.
В v3 название также входит в описание устройства; в натурных тестах оно
совпадало с записанным при следующем чтении через каждую версию API.
Это наблюдение тестов, не гарантия линейной согласованности сервиса.

Пример тела изменения названия через документированный метод настроек.
В натурных тестах использовалось фактическое исходное название как префикс:

```http
POST /api/update_device
Content-Type: application/json

{"device_id": 700877, "name": "Дом [zc:owner=worker1]"}
```

Остальные настройки передавать не требуется. Документация update_device
предупреждает о передаче изменённых настроек прибору сразу либо при следующем
выходе на связь. Не следует обещать, что переименование затрагивает только
сервер ЛК. Проверены точное сохранение выбранных символов и длины до 64 КиБ;
при частых запросах получен HTTP 429. Верхняя граница размера и точное
правило квоты не установлены; подробности в отчёте натурных тестов.

Название видно пользователю; служебный суффикс меняет отображение прибора.
Другие клиенты могут читать ту же настройку, но запись остаётся обычной
безусловной записью. Это кандидат на хранение строки/согласительный маркер,
а не доказанный замок. Тестовые переименования выполнялись с последующим
восстановлением исходного названия.

### Состояние переключателя

Документированная форма запроса, приведённая только для описания контракта:

```http
POST /api/widget/v3/devices/{device_id}/controls/{entity_id}/actions/trigger
Content-Type: application/json

{"target_state": true}
```

false деактивирует переключатель. По описанию метод ждёт подтверждения
устройства и возвращает ошибку для offline. TriggerButtonRequest содержит
только target_state, без условия на прежнее значение. active=null означает
недоступное состояние, его нельзя интерпретировать как свободный замок.

Другой клиент с доступом к тому же прибору может читать его состояние через
API. Задержки видимости, согласованность одновременных чтений/записей и
сохранение состояния при перезапусках на реальном SMART 2.0 не проверялись.
Для использования как флага нужен специально настроенный элемент без
физических последствий. Возможность создать именно такой элемент ещё
предстоит подтвердить. Сброс котла, реле и отопительные режимы для хранения
служебного флага не подходят: их изменение воздействует на отопление.

### Почему флаг не равен мьютексу

Допустимая гонка при обычном чтении и записи:

1. Клиент A читает «свободно».
2. Клиент B читает «свободно».
3. A записывает «занято» и начинает управление.
4. B записывает «занято» и тоже начинает управление.

Оба считают себя владельцами. Запись собственного ID с последующим чтением
тоже сама по себе не создаёт атомарного захвата. Нужна доказанная семантика
взаимного исключения; опубликованные методы её не предоставляют. Флаг может
сообщать другим согласованным клиентам о работе алгоритма, но не обеспечивать
исключительное управление и не запрещать команды через прямой ЛК.

## Принятое архитектурное решение

В [исполнителе управляющего модуля](../agents/architecture.md) предусматривается
явный мьютекс на весь прибор: один алгоритм владеет одним прибором в данный
момент, разные приборы допускают одновременное управление. Без своей монополии
любая управляющая команда завершается ошибкой до сетевого вызова. Чтения,
история, инвентаризация и предпросмотр не требуют монополии.

Алгоритм сброса удерживает монополию через on, ожидание и off из finally,
затем освобождает. Stop/timeout не аннулируют принятые команды и не отбирают
монополию до finally. Журналы, watchdog и восстановление после crash этим
решением не добавляются.

Гарантия ограничена одним общим исполнителем. Локальный мьютекс каждого
из нескольких экземпляров не обеспечивает общую монополию. Для нескольких
независимых writers одного устройства нужен общий исполнитель или отдельный
подтверждённый механизм атомарного владения; конкретный backend пока не выбран.
В частности, параллельные Cloud Functions не могут считать собственные
локальные мьютексы общей блокировкой. Прямой ЛК этой гарантией не охвачен;
его приоритет обсуждается отдельно в замечании №7.

## Что остаётся непроверенным

- Возможность настроить отдельный инертный переключатель именно на SMART 2.0.
- Предел длины/символов notes и свойства одновременной записи двух полей.
- Наличие непубличного штатного механизма владения у ZONT.

Эти возможности не являются зависимостями согласованного локального мьютекса
и не объявлены реализованными. Код рабочего клиента не менялся. Из реальных
настроек тестировались name с восстановлением и notes с очисткой. У notes
исходное null изменилось на пустую строку, потому что API отверг запись null;
тестовый маркер удалён. Отопительные параметры и переключатели не изменялись.
