# Калибровка pacing координации v2

Офлайн-статус: **simulation**, границы ZONT **unmeasured**. Прогон выбирает
интервалы для опубликованной нагрузки и scheduler. Он не доказывает
линеаризуемость, гарантированное применение до timeout, физическое завершение
или достигнутые 99.9% на настоящем API.

## Входы и воспроизведение

Исходная методика —
[план, статистика и калибровка](../plans/completed/20261019002421-monopoly-protocol-v2-implementation-plan.md#статистика-и-калибровка).
Исполняются настоящие LeaderElection, GrantCoordinator, ExecutorGate,
LeaderStore/ExecutorStore и wire v2. UUID генерируются через DI. Управляемые
часы и fake metadata port не обращаются к устройству.

Зафиксированы Delta=5 с, Delta_cmd=5 с, период лидера 300 с,
lease=timeout=30 с, профиль 99c733ec-f8d4-42fc-9cdb-376d46a4bd31.
W=2Delta, ступени rho и предел непрерывного срока 1200 с не оптимизировались.
Pacing: poll/retry из {0.25,0.5,1,2,3,5}, jitter из {0,0.1,0.25,0.5},
renewal из {1/5,1/4,1/3} полезного периода: 432 допустимых кандидата.

Для каждого кандидата исполнены 90 серий по 100 начатых запросов:
пять сценариев × seed 17/42/73 × полное окно 0.1/0.5/0.9Delta
× скорости часов 1/1 и 0.995/1.005. Сценарии: один исполнитель, два
одновременно, пять с новыми идентификаторами после terminal предыдущих,
смена лидера по пределу срока, одно вытеснение R2 другим запросом.
В последнем сценарии однократный immediate acquire конкурента входит
в те же 100 запросов; его отказ из-за contention учитывается как DECLINED.

Scheduler детерминированный, сериализует события без вытеснения. Латентность
распределена между пятью сетевыми шагами полного окна; самые длинные окна
достигли 4.5000000000009095 с. Нормальные трассы соблюдают временную модель.
Предусмотренные scheduler ожидания отделены от injected freeze. Для
ускорения кешируются только чистые декодирования одинаковых неизменяемых
wire-строк; каждый вызов объектов протокола и port I/O всё равно исполняется.
Равенство cached/uncached трасс проверено unittest.

```sh
python3 scripts/calibrate_coordination.py --output reports/coordination-v2 --workers 16
python3 scripts/calibrate_coordination.py --fault-only --output reports/coordination-v2
python3 scripts/analyze_orchestration.py --calibration reports/coordination-v2/report.json reports/coordination-v2/fault-report.json
```

Текущие полные результаты harness revision 3 находятся локально в
`reports/coordination-v2-20261019-review-corrected/`: report.json, 432 gzip JSONL,
fault-report.json и независимо пересчитанный verified-report.json.
Каждая строка gzip содержит входы серии, все 100 terminal исходов с UUID,
ожидания/границы цензурирования и все измеренные полные окна. Manifest
содержит SHA256 каждого файла. Анализатор перепроверил хеши, полный набор
профилей/входов и заново вычислил победителя из всех исходов. Эти генерируемые
артефакты игнорируются Git; команды выше восстанавливают их из исходников.

Первоначальный `reports/coordination-v2-20261019-final/` сохранён, включая все
натурные raw observations. Его term-handover оказался невалидным: после
первого захвата часы перескакивали за начальный lease без renewal, поэтому
измерялось восстановление протухшего лидера. Эти клетки и первоначальное
ранжирование заменены. В revision 3 настоящий лидер последовательно продлевает
аренду до окрестности непрерывного предела; term_trace содержит продления,
подтверждённую активность near-cap, retirement с причиной term-limit и новый term.
Все 432×18×100=777 600 затронутых запросов пересчитаны с прежними seed,
задержками и drift; остальные 3 110 400 исходов сохранены из сопоставимых
клеток. Полные denominator, hashes и ранжирование проверены заново.

Первый промежуточный `reports/coordination-v2-20261019-review-fixed/` также
сохранён: попытка добавить лишний READ в election увеличила исходное окно
с пяти до шести операций и остановилась на .9-клетках. Это незавершённый
невалидный прогон, его результаты не участвуют в ранжировании. Пара профилей
проверяется при bootstrap до worker и существующими READ перед WRITE;
лишний READ удалён, исходные bounded окна не ослаблялись.

Всего 38 880 серий и 3 888 000 начатых запросов, 192 710 079 операций
metadata port, соответствующих HTTP-запросам модели. Итоги всех кандидатов:

| timeout | 2 809 763 |

Нарушений интервалов, неожиданных выходов за Delta и неполных terminal
результатов нет; все 432 кандидата прошли проверку допустимости.
Повторы nonce и polling не увеличивают знаменатель. Ошибка cleanup после
получения сессии не меняет неизменный terminal GRANTED на timeout.

Выбранный симуляцией кортеж:
**poll=1 с, retry=0.5 с, jitter=0.25, renewal=1/4 периода (75 с)**.

затем числовой кортеж pacing. После натурного сравнения пример controller
вручную изменён на отдельную provisional рекомендацию 20/60, описанную ниже;

Timeout цензурирован справа: известно только wait≥30 с. Для всех 9000

заданных задержек, а не основание объявить измеренную Delta ZONT или
автоматически сменить профиль на устройстве.

## Fault-матрица

Отдельно выполнены 432×3×6=7776 намеренных fault cases:
timeout, потеря ack, 429, cancel, freeze/превышение Delta, stop/finally.
Неожиданных результатов 0. Эти случаи не входят в нормальные denominator
и success_rate. Timeout после send сохраняет неизвестный исход без повтора;
freeze запрещает запись, превышение полного окна отклоняется; abandon
локального pending не делает I/O; потеря роли лидера не отменяет finally
внутри действующего grant.

## Натурная часть

Read-only проверка настоящего прибора 700877 от 19.10.2026 через
create_read_controller подтвердила контур «Отопление» 20496: target_temp=24.0,
minimum=10, maximum=30, **step=1.0**; mode «Расписание» имеет ID 20503.
step переносится из ответа ZONT без пересчёта. quality=unknown ожидаемо:
Widget API не возвращает время измерения. current_mode=null означает ручной
режим согласно документации API; это не доказательство невозможности
будущего подтверждения конкретного режима.

Повторно прочитанный [публичный OpenAPI v26.8.2](https://my.zont.online/api/widget/v3/docs)
описывает Circuit.step как «Шаг изменения целевой t° (для котлового контура
отсутствует)», example=1.0. SHA256 документа
`8db8fb750c16d253a923282e34a647c7fc55987b5e2081c1b6bb61439a287b1f`
совпадает с [исследованием API](2026-10-14-zont-control-lock-api.md).
Тип float у SetTargetTempRequest без multipleOf не подтверждает допустимость
шага ±0.1 для этого прибора. После сообщения об этом владелец явно выбрал:
«Только «Расписание», температурную серию пропустить».
Температурная серия **пропущена по решению владельца**, не выполнена;
замена шага большим или другой целью не выполнялась. Дословное решение
сохранено в [исходной постановке](../plans/20261019002421-monopoly-protocol-v2-task.md).

Общий prepare_command проверяет типы, возможности и min/max, но не шаг UI.
Натурный harness теперь отдельно отклоняет ±0.1, если известный step
не делит 0.1 нацело, сохраняя внешнее завершение в «Расписание».
Выполнена отдельная серия count=0: только настоящий grant, активация
«Расписания» и readback mode_id без температурных команд.
Внешний finally допускает один новый ограниченный acquire при ownership
expiry; неизвестная запись не повторяется вслепую. Конечный mode_id=20503
подтверждён чтением выбранного «Отопления». Реальный сброс котла
и запуск автономных алгоритмов в натурную часть не входят.

Первый Schedule-only прогон с первоначальным офлайн pacing 1/5/0.25/0.25
не получил grant: два отдельных запроса lease=180 с, timeout=90 с дали
два timeout; физических команд отправлено **0**, конечный режим остался
неподтверждённым. Отказы сохранены в `schedule-live.json` и
`schedule-observations.jsonl` рядом с исходными результатами матрицы.
В наблюдениях есть HTTP 429 (11 событий rate_limited) и потеря лидерства;
превышений freeze/Delta не было. Первый отказ роли произошёл при чтении R1
перед записью продления, до sync_write. Класс этой первой ошибки прежнее
событие error не сохранило; утверждать, что это точно 429, нельзя.

Следующий read-only снимок подтвердил R1 с тем же profile_id, периодом
лидера 300 с, пустыми grants и неизменным опубликованным горизонтом 300 с;
фактический current_mode=null (ручной). Протокол требует наблюдать старую
неизменную запись ещё 300×K(300)≈331.58 с с момента первого собственного
чтения. Поэтому новый запрос с прежним timeout=90 с не может сам по себе
обеспечить takeover. Увеличение timeout до 600 с при lease=180 с тоже
некорректно, поскольку локальная аренда фиксируется при создании запроса.

Выполнен отдельный прогон в одном приложении: bootstrap-запрос
lease=180 с / timeout=30 с завершился timeout; координатор остался работать
и ожидался не более 500 с от начала bootstrap по локальному событию
leader_acquired. Затем создан **новый** запрос lease=180 с / timeout=90 с
для Schedule-only finally. Параметры poll=20 с / retry=60 с снижают сетевую
нагрузку; это ручной диагностический pacing вне офлайн-сетки, не новый
победитель матрицы. Delta, Delta_cmd, период лидера и профиль не изменены.
Ни один request не продлевается скрыто. Все timeout и промежуточные
ошибки входят в отдельный натурный знаменатель; эти наблюдения не
смешиваются с нормальной симуляционной матрицей.

Новый запрос получил GRANTED через 43.081693758955225 с. Через действующий
grant выполнена ровно одна команда mode 20503 / activate, после неё
read_current(mode_id) подтвердил **20503**. schedule_confirmed=true,
error/finalization_error=null; ошибка release не наблюдалась. Температурных,
reset-команд, запусков автономных алгоритмов и деплоя не было.

Натурный aggregate — `schedule-aggregate.json`: **4 начатых запроса,
1 GRANTED, 3 timeout, 0 DECLINED, 0 unknown**. Два первых timeout имеют
нижнюю границу ожидания 90 с; bootstrap timeout — 30 с. Таким образом,
success_rate=25%, timeout_fraction=75%; для всех ожиданий p99/p99.9/max
нижних границ равны 90 с. Один успешный образец имеет max=p99=p99.9
43.081693758955225 с, но не позволяет оценить эксплуатационные хвосты.
Второй прогон отдельно содержит bootstrap timeout и GRANTED, без потери
первого неудачного прогона из общего знаменателя.

| Наблюдение | Первый прогон 1/5 | Второй прогон 20/60 |
| --- | ---: | ---: |
| До начала WRITE (исторические образцы / max) | 4 / 1.4367566959699616 с | 6 / 1.3466918860794976 с |
| READ→ответ WRITE: max / p99 / p99.9 | unavailable | unavailable |

| Неуспешное полное окно: образцы / нижняя граница max | 1 / 2.5787340980023146 с | 0 / unavailable |

| Превышения Delta / freeze | 0 / 0 | 0 / 0 |
| RateLimited / leader_lost | 11 / 14 | 0 / 0 |

Историческое событие sync_write записывалось **перед** WRITE. Его значения
сохранены выше как время до начала отправки, но не измеряют ответ WRITE.
Сырые наблюдения не содержат достоверной отдельной метки этого ответа:
READ→ответ WRITE max/p99/p99.9 восстановить нельзя, они **unavailable**.
Новый анализатор оставляет эти исходные значения только как цензурированные
нижние границы, без включения в percentiles завершённых записей. Исправленные
runtime-события отделяют sync_write_started и sync_write после ответа;
unknown/timeout остаются цензурированными. Повторных натурных команд ради
этого исправления не выполнялось.

Для столь малых полных окон p99 и p99.9 совпадают с max.
Первый прогон содержит одно неуспешное полное окно: оно сохранено как
цензурированное наблюдение, отдельно от завершённых окон.
Диагностический транспорт второго прогона зафиксировал 53 успешных HTTP
вызова, без rate limit или потери роли. Общий HTTP count первого прогона
не инструментировался и не восстанавливается из числа polling-событий.
Сырые JSONL и результаты analyze/analyze_command_effects сохранены в
`schedule-*-observations.jsonl`, `schedule-*-timing-analysis.json`,
`schedule-*-effect-analysis.json` рядом с матрицей; файлы с первым прогоном
имеют префикс `schedule-`, со вторым — `schedule-slow-`.

По этой пробе пример controller вручную содержит **provisional poll=20 с,
retry=60 с, jitter=0.25, renewal=1/4**. Это консервативная runtime рекомендация
для снижения наблюдавшейся нагрузки, а не победитель 432-кандидатной сетки,
SLA или статус calibrated. Для 10 завершённых окон и одного цензурированного формула
max(5,10×p99.9,1.2×max) дала бы 30.386819898849353 с; малая выборка,
неполные ошибочные чтения и отсутствие физического подтверждения не
доказывают жёсткой границы. Параметры безопасности автоматически не менялись:
Delta=5 с, Delta_cmd=5 с и их profile_id остаются начальными допущениями.

Физический хвост команды без отдельного достоверного источника остаётся
unknown. API RTT, подтверждённая уставка и 40-секундный цикл сброса не заменяют
такой источник. Delta_cmd=5 с остаётся начальным допущением.

## Проверки

TDD: RED отсутствующего модуля/функций и несовместимого старого pacing
примера → GREEN. Финальный make check PYTHON=python3 прошёл 637 unittest,
4 прежних skips; lint 158 файлов и локальные Markdown-ссылки прошли.
Один прежний threaded ProductFlow тест при первой проверке под 16CPU
нагрузкой не уложился в своё 20-мс окно; отдельно и в полном повторе после
завершения CPU он прошёл без изменений тестов или runtime.
Дополнительный TDD guard для настоящего step=1.0: RED пропущенной проверки
→ GREEN, отдельно проверены несовместимый шаг 0.3, допустимые 0.1/0.05
и завершение count=0 без изменения температуры. После guard полный
make check PYTHON=python3 прошёл 639 unittest, 4 прежних skips.
Для provisional примера отдельно выполнен TDD RED старых 1/5 → GREEN 20/60;
тест сохраняет явную проверку renewal/stop margin и статуса unmeasured.

После comprehensive review исправлены сокращение резерва при heartbeat,
повторы известного вытеснения acquire/heartbeat, общий pacing-бюджет,
запрет пары R1 A/R2 B и измерение ответа WRITE; восстановлены регрессии
усечения/нормализации readback. Отдельный поведенческий тест term-handover
проверяет действующую роль у cap, её остановку и получение нового term.
Полный make check PYTHON=python3: 655 unittest, четыре прежних skips;
PIP_NO_INDEX=1 make package-check PYTHON=python3: шесть тестов без skip,
wheel 0.3.0. Анализатор заново проверил все 432 SHA256 и состав нормальной
матрицы, пересчитал terminal-сводки и ранжирование; все сводки совпали
с manifest revision 3. Отдельная fault-матрица: 7776 случаев, 0 неожиданных.
Новых натурных запросов или команд для этих исправлений не выполнялось.
