Дата: 21.10.2026, Europe/Moscow. Статус: план подготовлен, реализация не начата.
Запрос владельца: «plan-writer навести порядок в документации. образец

## Цель и границы

Разработчик, оператор и агент должны находить действующую инструкцию по своей
задаче, отличать её от истории и понимать, куда вносить следующее изменение.
Результат — ясная навигация, устранение устаревших текущих утверждений,
разделение контрактов/процедур/свидетельств и явные правила поддержания порядка.

Образец — организация инструкций autorepeater на
[SHA 5bfeeeb](https://github.com/gorpsys/autorepeater/tree/5bfeeeb865f6c3fdb381b27419309b41b1f5b26a):
короткий AGENTS, тематический индекс, отдельные текущие контракты и история
находок с ID, контрпримером, источником и ссылкой на действующий способ.
Бизнесовые правила, SDK, Sandbox E2E и зависимости образца не переносятся.
Существующие удачные разделы zontcontrol сохраняются; полного копирования
дерева autorepeater не требуется.

Работа не меняет Controller API v2, детектор, конфиги, алгоритмы, CLI,
формат логов/notes, протокол деплоя или IAM. Синхронизация управления
не возвращается. Нет новых зависимостей, генераторов сайта, Markdown-linter,
проверяющих Python-скриптов или новых тестов. Из Python-файлов допускается
только литерал версии при подготовке документационного PATCH.
Рабочие конфиги и корневой reports/ не перемещаются.
Запросы к ZONT, ручные yc, создание ресурсов и запуск handler не нужны.

ради симметрии дерева: общий вход — docs/README, исторический — docs/history/README.

## Правила ведения документации, которые должны появиться

В docs/agents/documentation.md создать следующие разделы с конкретными правилами:

1. **Выбор места.** Использовать матрицу выше; новый текст сначала отнести
   к контракту, процедуре, обоснованию, свидетельству или будущей работе.
2. **Один источник.** Для API/поведения — соответствующий контракт/справочник,
   для порядка выпуска — scripts/README, для текущих ресурсов — их реестр.
   В остальных местах краткое описание и ссылка, а не копия изменяемого списка.
   Таблицы в примерах могут повторяться только как явно обозначенные примеры.
3. **Основания утверждений.** Действующий контракт сверяется с кодом и тестами;
   несовпадение не даёт разрешения менять код под текст. Внешний факт получает
   дату, конкретный источник/отчёт, SHA/ID при наличии и предел вывода.
4. **Статусы.** Текущий документ описывает действующее поведение без «этот PR».
   План имеет статус draft/принят/в работе/выполнен. Исторический документ
   указывает дату и, для отменённого решения, ссылку на заменившее решение.
5. **Изменение контракта.** Обновить один канонический раздел и затронутые
   ссылки/примеры, записать причину в историю и результат выпуска в CHANGELOG.
   Не переносить бизнес-решения из autorepeater.
6. **Версия и деплой.** Различать подготовленную версию, тег, опубликованную
   версию функции и наблюдённый вызов. Не объявлять старый датированный отчёт
   доказательством нынешнего ACTIVE или новой физической проверки.
7. **Находки.** Следующий свободный H-ID, дата, один контрпример, причина,
   ссылка на проверенный источник и действующий раздел. Не создавать отдельный
   файл на каждую короткую находку; большие свидетельства хранить в reports/reviews.
8. **Жизненный цикл плана.** В docs/plans только невыполненная работа.
   Перед completed проверить обязательные результаты и внешние действия,
   если они нужны цели; отсутствие разрешения не равно выполнению.
   Перенос сопровождается исправлением входящих/исходящих ссылок и якорей.
9. **Архивирование.** Не удалять свидетельства отменённой координации и не
   переписывать старые измерения под новую архитектуру. Историческая пометка
   с текущей ссылкой достаточна; документы не становятся обязательным вводом.
10. **Примеры и секреты.** Рабочие токены/пароли/сертификаты, secret payload,
    сырые ответы с credentials и рабочие JSON не публиковать. В how-to
    отмечать placeholders, адресата, эффект команды и ожидаемую проверку.
    Чтение инструкции не разрешает выполнять команды. Ручные yc подтверждаются
    отдельно; офлайн-проверки ZONT и облако не вызывают.
11. **Проверка.** Локальные относительные ссылки с якорями, GitHub-ссылки на
    конкретный SHA для свидетельств, make lint/check и git diff --check.
    Для shell/Python-примеров — статическая проверка без исполнения эффектов.
12. **Завершение изменения.** Проверить карту документации, канонический раздел,
    обоснование при необходимости, статус плана, release metadata и отсутствие
    секретов. Ни timestamp, ни фраза «проверено» не заменяют результат проверки.

## Подход к реализации и проверкам

Последовательно завершать задачи. Реальные файлы и пути перечислены ниже;
новые назначения документации не требуют новых runtime-модулей.
Метод — документационные правки с проверкой существующих контрактов.
TDD и новые unit-тесты не нужны: поведение кода и тестовые ожидания неизменны.
Существующие тесты не редактировать. Если выясняется, что нужна правка
runtime/CI/checker или тестов, вынести её за этот план и согласовать отдельно.

После каждой задачи — make lint и git diff --check. После завершения всего
плана — make check. make package-check нужен только если по отдельно
согласованному расширению изменится состав пакета; здесь такого изменения нет.
Не вводить новую автоматизацию семантического аудита Markdown: действующий
scripts.check_project уже проверяет существование файлов/якорей, включая
новые Markdown-файлы. Смысл и актуальность проверяются по чеклисту приёмки.

Прогресс отмечать в этом плане; фактически не выполненные пункты не закрывать.
При появлении нового существенного решения обновить план до реализации.

## После завершения

Ревью и разрешение на merge относятся к последующему PR. Уже существующий
автоматический deploy после разрешённого merge может опубликовать тот же код
с новым номером версии; его workflow, параметры и таймер в этой задаче
не меняются. Дополнительная натурная приёмка и ручные yc не являются условием
упорядочения Markdown и не запускаются под видом проверки документации.

Соседний autorepeater используется только как образец. Его документация,
бизнес-правила и рабочие ресурсы в рамках этого плана не изменяются.
