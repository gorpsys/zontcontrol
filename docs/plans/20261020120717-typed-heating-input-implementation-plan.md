# Issue #5: предметный вход и нормализация температур на минутную сетку

Статус: этап 1 выполнен; этапы 2–5 не начаты.
Основание: [issue #5](https://github.com/gorpsys/zontcontrol/issues/5), P3.
Проверенная база: master 9f157f8, выпуск 0.3.0, 20.10.2026.
Порядок реализации — TDD, отдельный PR, без деплоя и обращений к ZONT.
Дополнение владельца: сохранить минутную сетку детектора, выбирать и
сортировать исходные измерения по точному времени, фактические температуры
между соседними точками линейно интерполировать к расчётной минуте.
Это согласованное изменение входных вычислений сверх первоначальной типизации;
пороги и NoHeatDetector не меняются.

## Актуальность и цель

Задача остаётся актуальной после удаления синхронизации. Сейчас
BoilerReset.run_once получает HistoryResult и вызывает history_packet:
тот создаёт вложенные temperature_sensors/circuits/web_elements, преобразует
datetime в строки и дублирует метаданные. monitor.assess_history повторно
выбирает те же прибор/контур/датчики, разбирает даты и строит HeatingSample.

NoHeatDetector уже имеет предметный вход HeatingSample. Менять сам детектор
или вводить новую иерархию исполнителей не требуется. Нужно заменить вход
monitor и отделить преобразование HistoryResult от чистой логики.

Результат: одна явная конвертация истории в предметные ряды; monitor не знает
формы архива и API ZONT. Критерий качества — меньше повторного разбора
и условных форматов, понятные поля и отсутствие совместимых заглушек.

## Контекст и принятые ограничения

- Цель: поддерживаемость; подтверждённого дефекта детекции issue не заявляет.
- Потребители: автономный boiler_reset и локальные исследовательские скрипты.
- Данные: семь исторических рядов, их исходные значения, качество,
  происхождение, точные даты и признаки неполноты. Хранилище не добавляется.
  Сохранение качества/точности относится к данным, доступным на конкретной
  входной границе. Потери, уже происходящие в исследовательском load_series
  независимо от формата, не исправлять в этой задаче.
- Поток production: Controller.read_history → адаптер предметной истории →
  monitor → NoHeatDetector → прежний результат → прежняя политика on/off.
- Controller API v2, конфиги, CLI, DI, once/continuous и прямое исполнение
  команд не меняются. Синхронизация управления не возвращается.
- Runtime остаётся stdlib; HTTP, БД, новые зависимости и сервисы не нужны.
- Окно прогона детектора 45 минут, импульс 40 секунд, off в finally, пауза
  continuous 300 секунд и SMART_2_HEATING_CONFIG остаются прежними.
  Историю запрашивать за 46 минут: дополнительная минута нужна для границ
  интерполяции и допустимого сдвига конца расчёта.
- Переход выполняется сразу для всех потребителей внутри репозитория.
  Старые сигнатуры monitor/history_packet и aliases не сохраняются.
- Существующие JSON-архивы остаются входными исследовательскими данными.
  Их чтение — действующая обязанность scripts, а не совместимость production API.
- Уточнение владельца по ревью: исследовательский загрузчик адаптировать
  только при необходимости нового формата; не восстанавливать quality,
  метаданные или дробные секунды, которые он уже отбрасывал. Пустой срез
  reset в heating_window должен сохранить прежнее поведение.
- Сортировка и выбор исходных точек выполняются по точному datetime.
  Минутная сетка сохраняется. Для фактических температур принята линейная
  интерполяция с интервалом пары не более 120 секунд. Без правой точки
  используется описанный ниже сдвиг окна, без подстановки прежней температуры.

## Подход и границы модулей

Выбран один путь из постановки issue: предметные неизменяемые ряды, два
явных входных адаптера и один monitor. Дополнительные варианты с общим
универсальным преобразователем или сохранением двух monitor не вводятся.

| Модуль | Ответственность и разрешённые зависимости |
| --- | --- |
| zontcontrol/heating.py | Предметные dataclass и их структурная проверка; только stdlib. |
| zontcontrol/heating_adapter.py | HistoryResult → HeatingHistory; controller.contracts и heating, без I/O и config. |
| zontcontrol/monitor.py | HeatingHistory → HeatingSample → решение; heating, anomaly, detection_profile и stdlib. |
| zontcontrol/algorithms/boiler_reset.py | Получение истории, явные привязки, вызов адаптера/monitor, прежняя политика сброса. |
| scripts/heating_archive.py | Сохранённый JSON-архив → HeatingHistory; знает архивный формат, не HTTP и не управление. |
| scripts/validate_one_shot.py | Строит предметное окно из объединённых архивных рядов вместо вложенного packet. |

Не переносить архивный словарь в новое поле payload/raw/metadata предметного
объекта. Не создавать Protocol/factory/plugin registry для двух адаптеров.
Не использовать HistoryResult как предметную модель: архивные окна могут
содержать исходный отсчёт до start, который Controller DTO намеренно запрещает.

## Предметные типы и функции

В heating.py добавить три frozen dataclass. Коллекции — tuple; тип значений —
локальный Scalar = int | float | bool | str | None. Импортов controller нет.

### HeatingPoint

- measured_at: datetime, aware UTC; исходная точность сохраняется.
- value: Scalar, исходное значение, включая значение плохого качества.
- quality: Literal['good', 'unknown', 'missing', 'stale'].

Не заменять value на None в адаптере ради детектора: это теряет исходное
измерение. Для production-входа использовать value только при quality='good';
во всех остальных случаях вычислительное значение — None. Никаких копий
одного значения в полях value/original_value/effective_value не хранить.
Исследовательский вход сохраняет прежнюю проекцию value без новой политики
качества: он использует quality='good' как прежнее вычислительное допущение
архивного пути, а не доказательство исходного качества или свежести измерения.

### HeatingSeries

- points: tuple[HeatingPoint, ...], стабильно по возрастанию точного measured_at.
- source: str | None, unit: str | None.
- value_type: str | None и kind: str | None — известные метаданные ряда;
  для архивов без них None, а не выдуманный источник или тип.
- incomplete_reasons: tuple[str, ...].

Отсутствующий ряд обозначается None в HeatingHistory, существующий пустой —
HeatingSeries(points=()). Это сохраняет reset_history_available. Даты должны
быть aware; типизированный вход не разбирает ISO-строки. Для архивных дублей
допустить равные даты: стабильный порядок сохраняется, lookup выбирает
последний отсчёт, как существующий bisect_right. Не объединять разные значения.
Для heating_window действует прежнее специальное правило: если выбранный
срез reset пуст, поле reset=None, reset_history_available=False. Если же
в исходном archive packet явно есть элемент reset с пустым рядом или
Controller DTO содержит пустой ряд reset, сохраняется HeatingSeries(points=()),
reset_history_available=True. Эти два случая не унифицировать.

### HeatingHistory

- device_id, circuit_id, air_sensor_id, coolant_sensor_id, reset_control_id:
  положительные int, два температурных датчика различаются.
- start, end, received_at: aware UTC datetime, start < end.
- air, coolant, air_target, coolant_target, worktime, target_sensor_id, reset:
  HeatingSeries | None, явные предметные поля, без mapping произвольных ключей.
- time_truncated: bool и incomplete_reasons: tuple[str, ...].

Объект допускает исходные точки до start: их возраст учитывается при
проекции. Ни точку, ни время получения не переносить на границу окна.
Структурные ошибки дают ValueError до детекции. Пропуск ряда, пустой ряд,
null или плохое качество — данные для unknown, а не ошибка структуры.
Числовые границы/worktime и пригодность для решения проверяет прежняя логика.

### Новые сигнатуры

```python
# zontcontrol.heating_adapter
def from_controller_history(history: HistoryResult, *, device_id: int,
                            circuit_id: int, air_id: int, coolant_id: int,
                            reset_id: int) -> HeatingHistory: ...

# zontcontrol.monitor
def history_samples(history: HeatingHistory): ...  # Iterator[HeatingSample]
def assess_history(history: HeatingHistory, *, config=None) -> dict: ...

# scripts.heating_archive
def from_archive_packet(packet: dict, *, device_id: int, circuit_id: int,
                        air_id: int, coolant_id: int, reset_id: int) -> HeatingHistory: ...
```

device_id в production-адаптере сверяется с HistoryResult.device_id, остальные
ID выбирают точные ValueKey. Нет поиска первого прибора или похожего контура.
Неизвестные/посторонние ряды не подставляются. Отсутствующие выбранные ряды
остаются None. Quality/value_type/kind передаются как их enum.value;
даты, значения и причины неполноты сохраняются.

Архивный адаптер требует ровно один прибор с указанным ID и явно указанный
контур, как текущий monitor. Отсутствие выбранного контура — ValueError,
отсутствие датчика/ряда/переключателя — None. Он разбирает даты один раз,
сортирует по точному времени. Архивный monitor раньше не учитывал
поле quality: сохранить это поведение, не добавлять фильтрацию или отказ
из-за архивного quality. Для вычисления использовать прежний value.
Не создавать HistoryResult из архивного packet и не вызывать production-адаптер
через обратную конвертацию. Это два независимых входа в одну предметную модель.

В heating_window поступают уже объединённые load_series пары
(целая секунда, value). Строить типизированные точки с ровно этой доступной
точностью, quality='good' и отсутствующими метаданными. Не заявлять сохранение
отброшенных загрузчиком сведений. Тесты archive/controller сравнивают одинаковые
доступные значения; тесты качества Controller DTO проверяются отдельно.

### Нормализация температур и выбор состояний

Сортировка находится в history_samples и обслуживает вычисления детектора.
Прежний int(timestamp) для исходных точек удалить; он теряет точность и меняет
порядок субсекундных измерений. Сетка расчёта остаётся минутной.

Для каждой минуты t:

1. Фактические air и coolant обрабатываются независимо. Для каждого точного
   timestamp сначала выбрать последнюю точку исходного порядка, затем
   проверять её значение/качество. Это правило действует и для точного
   совпадения t, и для левой/правой опоры. Если последний дубль плохой/null,
   более ранний хороший дубль не подставлять. Исходные points не удалять.
   Если выбранная точка ровно в t пригодна, использовать её; если непригодна,
   вернуть None для температуры в t, не обходить её интерполяцией.
2. Иначе найти две непосредственно соседние исходные точки t0 < t < t1.
   Обе должны быть конечными числовыми измерениями, пригодными по действующей
   политике качества входа. Не пропускать null/плохую точку ради поиска более
   далёкой подходящей пары и не интерполировать через явный разрыв данных.
3. При 0 < (t1 - t0).total_seconds() <= 120 вычислить
   T(t) = T0 + (T1 - T0) * (t - t0).total_seconds() / (t1 - t0).total_seconds().
   Не округлять промежуточные значения до десятых: это вычислительная точность,
   а не формат отображения. Например, 12:00:50 → 20.0 и 12:01:30 → 20.4 дают
   12:01:00 → 20.1. Указанное в сообщении 12:00:00 трактуется как опечатка.
4. Цели air_target/coolant_target, worktime, target_sensor_id и reset остаются
   ступенчатыми: брать последнее значение с точным временем <= t. Для них
   линейная интерполяция и использование будущего состояния запрещены.
5. Правая температурная точка может быть позже внутренней минуты t, но обязана
   быть доступна к моменту разового опроса: measured_at <= history.end и
   measured_at <= history.received_at. Данные после конца проверяемого окна
   не использовать, в том числе в backtest. Поэтому прежняя оценка внутренней
   минуты может уточниться после поступления правого измерения.
6. Исходные measured_at в HeatingHistory не менять. HeatingSample.time —
   расчётная минута; интерполированная температура не становится новым
   фактически полученным измерением. latest_valid_sample и свежесть итоговой
   телеметрии рассчитываются по исходным измерениям, не по синтетическим точкам.

### Границы окна и дополнительная минута

При разовом опросе обозначить T=history.end, G=начало минуты, содержащей T.
Все исходные точки сначала ограничить временем <= T и <= received_at.
Окончание минутной сетки E по умолчанию равно G. Если у air или coolant нет
точки с временем >= G (точной точки либо правой опоры), взять E=G-60 секунд.
Доступность опоры здесь определяется её временем, не качеством/значением:
наличие null/плохой точки не разрешает сдвигать окно, чтобы её скрыть.
Дальше чем на одну минуту относительно G окно не сдвигать.

Запрос BoilerReset: [T-46 минут, T]. Для детектора брать минуты строго после
max(history.start, E-45 минут) и до E включительно. При полном исходном окне
это сохраняет 45 последовательных расчётных отсчётов. 40 в NoHeatDetector —
ёмкость deque, а не обязательное число входных точек; новый минимум 40/45
пригодных точек не вводится. Прежняя проверка минимум пяти остаётся.

Внутренние пропуски, null, плохие значения и пары с интервалом >120 секунд
не выкидывать из минутной сетки: соответствующая температура — None.
Если на E после единственного допустимого сдвига всё ещё нет нужных опор,
не выполнять экстраполяцию, перенос последнего значения или дальнейший
поиск более старого удобного окна. На этой минуте значение неизвестно;
существующая проверка пригодности текущей телеметрии даёт unknown.

Сдвиг относительно G составляет не более 60 секунд; относительно самого
опроса T последняя расчётная минута может отставать почти на 120 секунд,
так как T не обязан совпадать с началом минуты. Свежесть исходных измерений
и reset_at_end проверять относительно T, а не E. Иначе сдвиг скрыл бы
устаревание или ручное отключение после последней расчётной минуты.

Состав production-ответа не расширять: sample_period/sample_lag_seconds
не добавлять. Границы фактической сетки и её отставание от T указывать только
в регрессионном отчёте. requested_period остаётся периодом запрошенных
исходных данных. Результат state_at_period_end — решение на момент T по
доступной сетке и актуальному состоянию сброса. Для synthetic samples
не выдумывать новое measured_at.

Субсекундный порядок и интерполяция проверяются отдельными тестами с явно
рассчитанным expected. Прежний baseline сохраняется для отчёта различий;
он не должен автоматически перезаписываться из новой реализации.

## Сохранение вычислений monitor

Переносить существующие вычисления, кроме явно согласованной нормализации выше:

1. Свежий NoHeatDetector(config, require_known_reset=True) на каждый вызов.
2. Минутная сетка остаётся; границы выбирать по разделу выше с дополнительной
   минутой исходной истории. Исходные datetime production-модели не округлять;
   индексы поиска строить по точным датам.
3. Фактические температуры нормализовать по правилам предыдущего раздела;
   ступенчатые значения не интерполируются. Разрыв между температурными
   опорами — не более 120 секунд включительно; без правой опоры нет подстановки.
4. Сохранить сравнение target_sensor_id с выбранным air_sensor_id.
5. Сохранить отдельный просмотр reset до точного end. Импульс между минутами
   и изменение после последней сеточной минуты продолжают учитываться;
   состояние после end не используется.
6. Правила распознавания reset в минутных samples и финальном состоянии
   перенести отдельно без их объединения: сейчас они различаются для
   некорректных значений, и унификация могла бы изменить решение.
7. Сохранить valid_temperature_samples, поиск latest_valid_sample по реальным
   точкам, порог 120 секунд, минимум пяти пригодных samples и проверку worktime.
8. Сохранить приоритеты итогового решения: truncation → неизвестный reset →
   включённый reset → restart grace → недостаточная телеметрия → уровень детектора.
9. Наличие incomplete_reasons/complete=False само по себе не запрещает решение
   за всё окно. После старого пропуска детектор вправе накопить новые данные.
10. Прежние ключи результата, события, incident_pending и automatic_control=False
    сохраняются; новые ключи не добавляются. Времена
    сериализуются в ISO UTC только при формировании
    результата. Сравнение дат в baseline учитывает равенство момента времени,
    а не различия эквивалентных ISO-offsets.

NoHeatDetector, HeatingSample и SMART_2_HEATING_CONFIG не изменять.
Интерполяция и точный выбор измерений могут изменить результаты monitor;
отделять такие различия от непредусмотренных изменений. Другие исправления
не включать, expected и пороги не подгонять под новую реализацию.

## Регрессии и архивная проверка

CI получает небольшой набор синтетических архивных входов и замороженных
полных результатов текущего monitor. Не требовать локальных reports для CI
и не добавлять skip вместо отсутствующего обязательного fixture.

Матрица: confirmed, warning, нормальный нагрев, восстановление, старое событие
при текущем normal, intentional shutdown, субминутный импульс, restart grace,
неизвестный reset, отсутствующий/плохой датчик, неверный target_sensor_id,
невалидный worktime, truncated, короткое окно и старый пропуск с восстановлением.
Отдельные границы: 90/120 секунд, точки до start, reset после последней минуты,
reset после end, одинаковые архивные timestamps и числовые/boolean reset.

Локально доступны reports/history-3w и reports/history-prior-2months,
reports/recalibration-validation-83days.json и его minutes.csv.gz,
reports/recalibration-83days.json. Проверенная база: 119520 решений,
704 сравнения с полным monitor; 22 июля — normal=640, unknown=56;
подтверждений вне известных отказов нет. Это прежняя калибровочная выборка,
не новое доказательство точности детектора на будущих данных.

Сравнение реального архива выполнить разовым локальным скриптом, без нового
поддерживаемого CLI capture/verify, manifest-инфраструктуры и тестов самого

## Критерии готовности

- Production не создаёт архивный packet из HistoryResult; monitor принимает
  только HeatingHistory, а NoHeatDetector — прежний HeatingSample.
- Нет union-входа dict | HeatingHistory, aliases старых функций или временного
  второго пути детекции. Входные адаптеры не содержат правил обнаружения.
- Контракты качества/времени/неполноты сохранены в пределах доступных входных
  данных. Изменения golden-результатов допустимы только от согласованной
  нормализации и описаны в отчёте;
  old gap не становится общим запретом решения, unknown не превращается в normal.
- Все четыре исследовательских потребителя переведены; сырые архивы читаются
  на исследовательской границе. Полные результаты выбранных архивных окон
  сопоставлены; различия от новой нормализации явно перечислены.
- Состав production-ответа сохранён; новый постоянный CLI регрессионной
  проверки и его инфраструктурные тесты не добавлены. Полный прогон архива
  не является обязательным условием завершения.
- make check, установленный wheel, CI и версия проверены. Изменения управления,
  интервалов, профиля, конфигов и синхронизации отсутствуют.
