## 4. Автоматическое восстановление

Архитектура определена в [отдельном контракте](../agents/architecture.md):
boiler_reset — once/continuous, только текущее confirmed_pattern допускает
импульс 40 секунд; сам алгоритм в finally немедленно выключает сброс
при штатной остановке/исключениях. Для once boiler_reset рекомендован запуск примерно раз в 15 минут,
без отдельного учёта повторных попыток между вызовами. Правила модуля —
[здесь](../reference/boiler-reset.md). Журналы, watchdog и независимый исполнитель
не добавляются; смерть host и жёсткое завершение runtime вне гарантии.
Координация прямых команд из ЛК остаётся отдельным обсуждаемым вопросом №7.

Постоянный CLI и continuous не запускаются бесконечным циклом внутри
Cloud Functions. Для них нужен локальный host или долгоживущий контейнер/VM;
scheduler функции выполняет повторные once. Плановые 60s read-only функции
не достаточное основание для бюджета чтение + импульс 40s + выключение.
Внутренний таймаут и штатное завершение должны оставить время на finally
до жёсткого timeout платформы; аппаратного восстановления после kill не обещается.
Этот этап ещё не реализован; архитектурное решение не выполняет реальный сброс.
