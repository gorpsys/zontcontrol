# Issue #3: штатное завершение внешних сессий управления

Статус: **этапы 1–4 выполнены и проверены офлайн 16.10.2026**.
Приоритет: **P1**.
Задача: [gorpsys/zontcontrol#3](https://github.com/gorpsys/zontcontrol/issues/3).
Основание: `master`, `d0352bf6f332601ed5eb6a2326e60652c6527019`, версия `0.1.1`.
Подход: TDD, Python >=3.11, только stdlib, без деплоя и обращений к ZONT.

## Обзор

Исправить штатную остановку приложения, встроенного через Python API.
До исправления `app.controller()` выдавал внешнему потребителю полноценную привязку
управляющего фасада, но `app.close()` ждал только потоки зарегистрированных
алгоритмов. Внешняя сессия и принятая команда не участвуют в этом ожидании.
Из-за этого приложение может закрыть координацию и транспорт до `finally/off`.

Результат: приложение перестаёт принимать новые захваты и потребителей,
кооперативно останавливает зарегистрированные алгоритмы, ждёт освобождения
всех сессий и завершения выполняющейся работы исполнителя и лишь затем
закрывает общие ресурсы. Ограниченный `wait_timeout` ограничивает ожидание
вызывающего потока, а не время жизни cleanup.

Пользователи исправления — внешние потребители `app.controller()` и владелец
приложения, вызывающий `close()` или использующий контекстный менеджер.
Новых хранимых данных, сервисов, конфигов и внешних интеграций нет.
Цель, участники, потоки данных и ограничения уже заданы issue и действующими
договорами; повторный выбор архитектуры и опрос владельца не требуются.

## Границы решения

- Сохраняются публичные сигнатуры `Application.close(wait_timeout=None)`
  и управляющего API v1. `True` означает, что shutdown завершён успешно;
  `False` — что ожидаемая работа ещё не закончилась. Ошибка закрытия ресурсов
  остаётся ошибкой, а не успешным `True`.
- Новые `bind` и захваты после начала shutdown отклоняются безопасной
  `ControlOwnershipRequired` до gate/HTTP. Новые запуски алгоритмов отклоняются
  существующим механизмом закрытого регистратора.
- При действующей, ещё не освобождаемой сессии обычный `execute_command`
  продолжает работать, в том числе для `finally`. Не анализировать смысл
  команды и не разрешать только off: правила admission остаются общими.
- Shutdown не выставляет `_Ownership.closing` всем владельцам: этот флаг
  означает запрос release и запрещает новые команды сессии. Глобальное
  закрытие входа и освобождение конкретной сессии — разные состояния.
- Истечение R2 по-прежнему запрещает новые команды, включая off. Принятая
  до истечения команда завершается. Shutdown не продлевает аренду.
- Внешние потоки не принадлежат регистратору и не получают от него отмену.
  Внешний потребитель сам заканчивает работу и вызывает release в `finally`.
  Нельзя ждать полного `app.close()` в том же потоке, всё ещё удерживая свою
  сессию: сначала release либо ограниченный close и завершение cleanup.
- Не реализовывать [issue #4](https://github.com/gorpsys/zontcontrol/issues/4)
  с новым API запроса монополии и [issue #5](https://github.com/gorpsys/zontcontrol/issues/5)
  с предметным входом детектора. Они независимы от исправления shutdown.
- Не добавлять watchdog, журнал восстановления, IPC, отдельные процессы,
  принудительный release активного владельца или автоматические повторы
  записей/команд с неизвестным исходом.
- Отдельный учёт произвольных внешних чтений, начатых без сессии, в эту задачу
  не входит. Задача защищает сессии, получение монополии и принятые команды;
  не объявлять её общей гарантией завершения любого вызова API.

## Решение

У общего исполнителя появляется внутренний жизненный цикл. Только он знает
локальные резервации и сессии. Регистратор получает две функции через DI:
начать закрытие входа и завершить закрытие ресурсов. Регистратор не читает
таблицу сессий, не знает R1/R2 и не начинает управлять внешними потоками.

Оставить один существующий `registry-close` поток. Вводить второй координатор
shutdown в Application или параллельную систему учёта сессий не требуется.
Ожидание только `in_flight == 0` недостаточно: между on и off сетевых вызовов
может не быть, хотя критическая секция всё ещё продолжается.

### Состояние и внутренние методы

В `CommandExecutor`:

- `begin_close()` — идемпотентно и без I/O закрывает выдачу новых binding
  и вход в `_acquire`; граница сериализуется тем же lock, что и резервации.
- `wait_idle()` — внутреннее блокирующее ожидание завершения всех резерваций,
  вызывается shutdown-потоком после завершения runtimes. Сам не отправляет
  off, release или повторные запросы и не имеет таймаута алгоритма.
- Состояние закрытого входа хранится одним флагом; ожидание — через
  `threading.Condition` на существующем lock. `_devices` остаётся единственным
  источником локальных резерваций. Новых публичных DTO/эндпоинтов не нужно.
- `release_failed` отмечает только завершившуюся неуспешную попытку remote
  release. `closing` без этого признака не позволяет удалить reservation
  по expiry: release может ещё ожидать передачи управления от владельца
  или последней принятой команды. Проверка одинакова в drain и reacquire.

`bind()` должен атомарно проверить закрытие входа. Ранее выданный пустой
контроллер не задерживает shutdown; хранить strong-reference реестр всех
когда-либо выданных фасадов не требуется.

Выдача сессии фиксируется в `_acquire` под тем же lock, что и begin_close:
после возврата gate повторно проверить глобальное состояние и тождество
резервации перед признанием её выданной потребителю. Если проверка прошла
до begin_close, захват уже принят, даже если Python-метод вернётся позже.
Если begin_close победил, сохранить полученную сессию только для cleanup,
пометить её reservation как closing и выполнить remote release вне lock.
После успешного release вернуть `ControlOwnershipRequired`; при ошибке release
передать её существующий безопасный тип вызывающему, не выдавая сессии.
Закрытие входа не может вклиниться между финальной проверкой и фиксацией
выдачи. Проверить оба порядка этой гонки управляемыми барьерами.

У `AlgorithmRegistry` добавить необязательный keyword DI-hook
`begin_close_controller`, в production равный `executor.begin_close`.
Существующий `close_controller` остаётся завершающим hook.

Ранний hook вызывается один раз на первый валидный `close`, после проверки
`wait_timeout`, до запуска потока закрытия и до отмены runtimes. Для атомарного
начала использовать текущую синхронизацию регистратора; ранний hook должен
только переключать локальное состояние исполнителя, не ждать и не выполнять
I/O. Не держать lock регистратора/исполнителя во время join или сетевых вызовов.

### Ошибка раннего hook

Это терминальная ошибка операции shutdown, а не основание повторить hook
или продолжить закрытие ресурсов:

1. В `AlgorithmRegistry.__init__` добавить `_close_started=False`, отдельный
   от `_shutdown`: отсутствие потока не означает, что hook ещё не пробовали.
   В первом валидном close под lock установить `_closed=True` и
   `_close_started=True` до единственного вызова раннего hook.
2. При исключении hook под тем же lock зафиксировать `_close_failed=True`.
   Shutdown-поток не создавать, завершающий close_controller не вызывать.
   Не хранить и не выводить произвольный текст исходного исключения.
3. Вне lock послать `runtime.close(wait_timeout=0)` всем уже созданным runtimes,
   не ожидая их finally. Новые старты уже запрещены. Продолжающаяся регистрация
   не должна автозапустить поздно подготовленный runtime.
4. После публикации отмены установить существующее `_resources_closed`:
   здесь событие означает завершение операции **с ошибкой**, а не закрытие
   ресурсов. Координация, транспорт и принадлежащий приложению sink остаются
   открытыми для cleanup; автоматического восстановления shutdown нет.
5. Первый, конкурентные и повторные валидные close получают одинаковый
   `RuntimeError('Shared controller shutdown failed') from None`, в том числе
   при wait_timeout=0. В ветке зафиксированной ошибки сначала обеспечить
   публикацию отмены, затем вернуть ошибку; не возвращать False и не ждать
   событие, которое никто не установит. Повторная публикация отмены безопасна,
   повтор hook или закрытия ресурсов запрещён.

В успешной ветке единственный shutdown-поток создаётся после hook под lock.
Каждый последующий close различает `_close_started`, `_close_failed` и событие
результата, а не решает начать shutdown заново только по `_shutdown is None`.
Не обещать завершения cleanup или закрытия входа исполнителя после упавшего
hook: он мог не выполнить свою работу. Ошибку нельзя объявлять штатным close.

### Последовательность закрытия

1. Проверить `wait_timeout` существующим способом. Невалидный аргумент не
   меняет состояние приложения, регистратора или исполнителя.
2. Закрыть регистратор для запусков и вызвать ранний hook закрытия входа.
   При его ошибке выполнить терминальную ветку выше; к шагам 3–7 не переходить.
3. Выставить отмену всем активным runtimes до ожидания любого из них,
   сохранив существующую синхронизацию с незаконченной регистрацией.
4. В единственном shutdown-потоке дождаться завершения всех runtimes/finally.
5. В `close_resources()` вызвать `executor.wait_idle()` **перед** блоками,
   закрывающими координацию/транспорт. Дождаться внешних сессий и выполняющихся
   gate/command/release-вызовов, которые держат резервации.
6. Закрыть координацию, затем транспорт, затем принадлежащий приложению sink;
   сохранить нынешнюю политику закрытия ресурсов при ошибке одного из них.
   Переданный извне statistics_sink не закрывать.
7. Установить итоговое событие существующего shutdown. У всех конкурентных
   вызовов close один результат и один набор закрываемых ресурсов.

При успешном раннем hook `wait_timeout=0` сразу публикует начало остановки
и отмену, затем возвращает False, если shutdown не завершён.
Каждый следующий вызов ждёт ту же операцию,
не запускает её заново и не обновляет аренды. `None` ждёт без ограничений;
конечное значение ограничивает только ожидание своего caller.

### Что считается незавершённой работой

| Состояние | Поведение shutdown |
| --- | --- |
| Только выдан пустой controller/binding | Не ждать: активной сессии или вызова gate нет. |
| `_acquire` зарезервирован до закрытия входа, gate ещё выполняется | Ждать завершения gate-вызова, не закрывать транспорт под ним. |
| Gate завершился Busy/ошибкой без сессии | Удалить резервацию и разбудить ожидание. Не ждать незавершённый удалённый запрос бесконечно: его жизненный цикл остаётся у координации. |
| Gate вернул сессию после закрытия входа | Не выдавать её потребителю. Завершить release полученного разрешения существующим механизмом, затем отклонить acquisition. Не терять резервацию, если release не подтверждён. |
| Выданная сессия удерживается между командами | Ждать явного release владельца, сохраняя возможность cleanup в пределах R2. |
| Выполняется validation/gate.validate/send | Ждать; reservation включает проверку до admission и принятую команду. |
| Release запросили, но команды ещё выполняются | Ждать окончания всех команд и единственного последующего release. |
| Последняя команда завершилась или явный release запрошен, но Gate.release ещё не начался | Ждать первой попытки release даже после expiry; не удалять reservation и не выдавать её новому владельцу. |
| Gate.release выполняется | Ждать окончания вызова, даже если lease за это время истёк. |
| Release завершился ошибкой, работа закончилась | Без повторных записей сохранять reservation до локального истечения; после истечения удалить её только при `release_failed == True`, `in_flight == 0` и `releasing == False`. |
| Аренда истекла, но владелец ещё не вызвал release | Не освобождать сессию за владельца. Новые команды запрещены, ожидание cleanup продолжается. |

Ожидание должно просыпаться на всех изменениях, способных освободить
резервацию: исход acquisition, завершение validation/send, начало/окончание
release, ошибка release. Для истечения неуспешно освобождённой closing-сессии
предусмотреть ограниченное ожидание до повторной проверки локальных lease-часов;
не полагаться на уведомление от нового acquire, который уже запрещён.
Не обращаться к wall-clock/NTP и не вычислять новую R2-аренду для shutdown.

Удаление записи при гонках проверяет тождество текущей резервации. Исключения
и финализаторы не должны удалить чужую запись, декрементировать чужой счётчик
или превратить исходную ошибку в KeyError. Учёт release/in_flight не дублировать
во внешнем списке активных команд.

## Подход разработки и проверки

Каждая кодовая задача: воспроизводимый падающий тест → минимальное исправление
→ рефакторинг → новые тесты и `make check PYTHON=python3`. Не переходить дальше
при падениях. Менять план при обнаружении расширения объёма.

Все тесты офлайн: имеющиеся LocalTestGate/FakeClock, VirtualHTTP/FakeZontServer,
Event/Barrier. Сценарии гонок запускать управляемыми барьерами; короткие timeout
использовать как предохранители, не как способ угадать порядок планирования.
Каждый тест обязан разблокировать свои потоки и освободить свои сессии даже
при падении assertion. Сначала cleanup сессий/барьеров, затем полный app.close.
