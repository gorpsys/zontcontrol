## 2. Архитектурные границы и совместимость

Существующий путь: Controller → heating_adapter → frozen HeatingHistory →
monitor.history_samples → NoHeatDetector. Ответственность RowCache — только
подготовка неизменяемого ряда и индекса внутри monitor.

- RowCache не помещается в Controller, transport, adapter, BoilerReset, UI,
  application или регистратор; эти слои не узнают о внутренней оптимизации.
- HeatingHistory/HeatingSeries/HeatingPoint и Controller API v2 не меняются.
  В transport/history.py не переносится фильтрация для детекции.
- Публичные сигнатуры сохраняются: assess_history(history, *, config=None),
  history_samples(history). Кэш не становится новым обязательным аргументом,
  опцией конфигурации/CLI/env или хранилищем состояния прибора.
- Новый детектор на каждый assessment, буфер 40, span-only и арифметика absence
  остаются прежними. `_temperature`, reset transitions и проверки monitor
  не оптимизируются этим изменением.
- Весь dict и выбор последнего дубля до quality-проверки сохраняются.
  Фактический received_at, truncation, bindings и config вычисляются заново.

Контрактных изменений не предлагается: выигрыш достигается внутри слоя,
отвечающего за подготовку. Если реализация потребует нового публичного
аргумента/изменения DTO или поведения, это отклонение от плана: сначала
обоснование владельцу и обновление плана с повторным ревью, затем код.

Варианты 3 и 4, batch, сокращение буфера/истории, перекалибровка, persistent
detector и межвызовный кэш интерполяции вне области.

## 3. Жизненный цикл, ёмкость и альтернативы [R2]

Итог исполнения: **capacity=7**. Sweep 6…14 подтвердил ускорение 1.051357×
против 0.7.7; 6 требует на 2.188% больше CPU, 8…14 не показывают существенного
преимущества по правилу 2% ниже. Семь — минимальная ёмкость измеренного плато
эффективности. Числа и три повторных контроля — в итоговых свидетельствах.

Рекомендуемое решение: приватный `_RowCache` в zontcontrol/monitor.py,
**один экземпляр на один assess_history**, явно передаваемый приватным helper.
Никаких globals, thread-local/ContextVar, singleton, TTL или mutex.
Параллельные assessments изолированы. После возврата/ошибки локальные ссылки
освобождаются обычным механизмом Python; кэш не удерживает завершённые вызовы.
Самостоятельный history_samples получает свой cache внутри генератора при
первом next; закрытие/исчерпание генератора завершает срок его использования.

Базовая фиксированная **capacity=7 утверждена владельцем**. Её эффективность
проверяется полным sweep 6…14 по §7, а не только отсутствием eviction.
В текущем monitor семь row-слотов; при одном вызове history/cutoff не меняются.
Порядок обращений: air, coolant, air_target, coolant_target, worktime,
target_sensor_id, reset, air, coolant, reset, reset — 11 обращений.
Последнее чтение reset связано с диагностикой 0.7.6+.

| 6 | 9 | 2 | 3 |
| 7 | 7 | 4 | 0 |
| 8 | 7 | 4 | 0 |
| 9 | 7 | 4 | 0 |
| 10 | 7 | 4 | 0 |
| 11 | 7 | 4 | 0 |

Это аналитическая симуляция последовательности текущего кода при семи разных
существующих рядах, не измерение будущего CPU. Семь — минимальная ёмкость,
которая не вытесняет нужные ряды в таком вызове. Если несколько слотов ссылаются
на один объект, записей меньше. None не занимает слот, пустой HeatingSeries занимает.
Ограничение числа записей не является байтовым лимитом: память O(суммы длин
удержанных рядов), точки разделяются с исходным DTO без копирования объектов.
Строки 6/7/14 взяты из уже выполненной симуляции без повторного запуска;
8…13 добавлены отдельным аналитическим прогоном. Эти числа не подменяют
фактический CPU и instrumented get будущего продукта.

Правило выбора [R2]: 7 остаётся базовым значением при прохождении условий
ускорения §7. Отсутствие CPU-преимущества других ёмкостей — самостоятельный
вывод измерений, а не следствие равных hit/miss. Для сравнения ёмкостей
практический порог существенности — 2% CPU, одновременно по sum полного replay
и во всех трёх контрольных benchmark (median нормированного CPU по 15 окнам).
2% — явный инженерный порог, снижающий влияние малых колебаний локального CPU,
не SLO и не утверждение о статистической достоверности. Все числа публикуются,
включая меньшие различия. Если у иной capacity sum CPU <=0.98×sum CPU(7),
а нормированный CPU во всех трёх контрольных повторах <=0.98×нормированного
CPU(7), **остановиться с докладом владельцу**, не менять default автоматически.
Если преимущество нестабильно или меньше порога, сохраняется одобренное 7:
дополнительные слоты не дают доказанного выигрыша, а 6 повторяет фильтрацию.

Альтернативы рассмотрены и не выбраны:

- LRU8…14 с тем же локальным lifecycle: тот же hit/miss; CPU-эффект отдельно
  проверяется полным sweep, заранее не объявляется нулевым.
- Общий процессный LRU14: в исследовании было ровно 7×137591 промахов;
  каждый window создавал новые ряды. Дополнительный lifecycle и совместное
  состояние не обоснованы данными. Возможность межвызовного reuse из issue
  не означает обязанность вводить его здесь.

Старые 4265321 lookups / 3302184 hits включают sample crosschecks — 31 lookup
на решение. Не сравнивать этот hit rate с 11 обращениями продуктового вызова.

## 4. Устройство RowCache: ключ, результат, hit/miss

Внутренний интерфейс: `_RowCache(capacity=7).get(row, cutoff)`.
Он принимает предметный ряд и UTC datetime, **не HeatingHistory**:
обёртка monitor вычисляет cutoff=min(history.end, history.received_at).
Это не даёт cache зависеть от IDs/config/управляющих объектов и сохраняет
его узкую ответственность. Приватный constructor отклоняет bool, не-int и
capacity<=0 через ValueError; параметр нужен тестам LRU и офлайн sweep [R2],
продукт использует утверждённое значение 7.

Хранилище — stdlib OrderedDict. Lookup key — `(id(row), cutoff)` без округления,
ISO, float timestamp или структурного хеша. Значение — `(strong_row, prepared)`,
prepared — immutable пара `(tuple(filtered_points), tuple(measured_at_index))`.
Пустой существующий ряд имеет свою identity. Для row=None сразу вернуть две
пустые tuple без cache entry. Index[i] всегда равен measured_at points[i].

На hit проверить `strong_row is row`, переместить запись в MRU и вернуть
prepared без копирования. Сильная ссылка не даёт переиспользовать id живого
ряда. После eviction исчезают и ссылка, и ключ. Структурное equality не
используется: равные копии ряда, False/0 и int/float не создают ложный hit.

На miss целиком пройти row.points и сохранить все точки с measured_at<=cutoff
в исходном порядке; из этой последовательности построить индекс. sorted
не нужен: HeatingSeries уже проверяет неубывающий порядок. Стабильность
сохраняет все дубли, None, quality и точность времени. Ничего не обрезать по
history.start, не удалять плохие точки, не делать дедупликацию/интерполяцию.
Установить запись только после успешного построения обеих tuple. Добавить
как MRU, затем popitem(last=False), пока размер больше capacity.
Защитное несовпадение `is` трактовать как miss с удалением конфликтующей записи.

Инвалидация — точные зависимости: новый row или любой другой cutoff дают
другой ключ, включая движение времени назад и микросекунды. Возврат к прежнему
точному cutoff может дать корректный hit, если запись ещё не вытеснена.
Одинаковые row+cutoff разрешают одинаковый filtered результат при различиях
start/IDs/config/truncation; эти поля не кэшируются и проверяются monitor заново.
В нормальном runtime отдельные assessments всё равно имеют отдельные кэши.
Frozen-типы и вложенные tuple/scalars — предпосылка; обход frozen внешней
мутацией не поддерживается существующим контрактом.

«Нет деградации при miss» означает точный пересчёт прежнего результата,
без stale fallback/unknown→normal, а не нулевой CPU overhead lookup/аллокаций.
На miss O(n), на hit O(1); положительный эффект полного вызова надо измерить.
Ошибки не скрываются и не превращаются в нормальное решение.

## 5. Подключение без нарушения абстракций

1. Оставить `_points(history,row)` независимым исходным sorted-filter с list:
   он используется локальными research-скриптами и uncached oracle тестов.
2. Тело history_samples перенести в приватный `_history_samples(history,row_cache)`.
   Для семи рядов вызвать get(row,cutoff) по одному разу; series/indexes берут
   сохранённые tuple. Остальную логику генератора, включая reset transitions,
   сетку и вызов `_temperature`, перенести буквально.
3. Публичный history_samples делает yield from внутреннего генератора с новым
   RowCache, сохраняя ленивость. В assess_history создать один RowCache и
   вызвать внутренний генератор с ним; latest air/coolant/reset брать из него же.
4. `_reset_at_end(history, *, row_cache=None)` — приватный helper: при передаче
   cache получает filtered reset из get; без него использует прежний `_points`.
   В assess_history передать его cache. Сам обход reset не менять.
5. Не переносить в cache `_value`, `_number`, transitions, reset-at-end,
   last valid measurement, параметры/состояние детектора или assessment.
   Runtime-логов и counters кэша не добавлять; измерения — только в harness.

## 6. Тесты и регрессии

Стиль — существующий unittest, только stdlib mock и синтетические данные.
Новые unit/integration cases — в tests/test_monitor.py. RowCache сравнивать с
неизменённым `_points`; индекс — с measured_at того же oracle. Проверять
порядок, идентичности и типы скаляров, а не полагаться на False==0.

- Identity: первый miss/повтор hit, одинаковое содержимое в разных row — miss;
  новые quality/value/последний дубль при прежних timestamps; int/float/bool/null,
  все good/unknown/missing/stale, непригодные числовые значения.
- Cutoff: end и received_at по обе стороны min, та же min при изменении одного
  поля, движение вперёд/назад/возврат, равенство границы, секунды/микросекунды,
  полностью будущие точки. Anchor до start не теряется.
- None/пустые rows/все дубли, последний null/bad duplicate; неизменяемость
  результата и согласованность points/index. На hit tuple сохраняют identity.
- LRU при capacity=2: A,B,A,C вытесняет B; повтор B пересчитывается. Число записей
  после get не больше capacity; сильная ссылка удерживается до eviction/уничтожения.
  Для lifetime использовать weakref к тестовому подклассу HeatingSeries без slots;
  не рассчитывать на принудительное повторение конкретного id от Python.
- [R2] Все capacity=6…14 проверить на том же 11-get trace: исходные точки и
  индексы равны oracle, фактические hit/miss/eviction совпадают с таблицей §3.
- Default/None/явный SMART config; SMART→иной валидный config→SMART.
  Разные IDs/bindings/start/received_at/truncation при тех же row не дают старый verdict.
- Interleaved генераторы и два параллельных assessment разных histories изолированы;
  генератор ленив, RowCache не переносится в следующий публичный вызов.
- Причинный контрпример C1 с поздней правой опорой: на 12:04 normal, не ошибочный
  unknown. Span=120/121 секунд, короткий reset pulse, unknown/active/grace reset,
  stale/короткий буфер и приоритет truncated_history проверяются прежними правилами.

Для полного синтетического сравнения test-only ReferenceRows каждый раз
вызывает `_points` и строит индекс без memoization. Через mock заменить только
фабрику `_RowCache`, сопоставить все samples и весь dict с обычным путём.
Существующие fixed-expectation monitor/heating_regressions тесты сохранить.
Такой oracle не заменяет отдельный replay с настоящим baseline 0.7.7.

Весь sweep последовательный и только в отдельном офлайн-процессе. Для выбора
capacity перед timed вызовом harness временно ставит приватному
`_RowCache.__init__.__defaults__` значение `(capacity,)`; тип класса, тела
методов и публичных функций неизменны, ни фабрики-обёртки, ни mock в timed
path нет. Выбор default и его восстановление вне таймера; исходный `(7,)`
восстанавливается в finally, включая ошибки. Это механизм только harness,
в runtime продукта настройки/переключения default не добавляются.

Контроль повторяемости: 15 окон — первое/среднее/последнее каждого состояния CSV
(среднее — индекс len//2 при нумерации с нуля) плюс saved typed unknown
reports/unknown-replay-2026-10-25/primary-history.json. Для каждого входа
30 warmup-блоков, 1050 timed-блоков baseline + все девять capacity [R2],
с тем же сдвигом/обратным порядком по номеру блока, как для окна полного replay.
Полный контрольный benchmark повторить три раза последовательно, без
параллельной suite/replay и правок входа.
Для каждого окна speedup — ratio median CPU baseline/candidate, затем
медиана этих 15 speedups. Saved unknown показать отдельно, без отбора результатов.
Для сравнения capacity между собой дополнительно вычислить для каждого из
трёх повторов median по 15 окнам от (median CPU capacity / median CPU baseline)
и отношение этого нормированного CPU к capacity=7; меньший CPU лучше.
**Каждый публичный вызов начинает с нового cache**, включая повтор одного DTO.

Untimed harness считает calls/hits/miss/eviction/peak entries и воспроизводит
trace **всех capacity=6…14** [R2]; counters/mock не включаются в timed path.
На каждом из тех же 137591 окон выполнить 11-get trace §3 настоящим get с
новым cache для каждого capacity, без детектора. Порядок вызовов дополнительно
сверить через один instrumented полный assessment на каждом из 15 контрольных
окон. Если порядок отличается от §3, это расхождение плана: стоп и доклад.
Записать суммарные calls/hit/miss/eviction и peak entries для каждой capacity.
None считать отдельным bypass, не hit/miss: calls=hit+miss+bypass.
Для семи разных существующих рядов ожидаются 11 get, 7 miss, 4 hit, 0 eviction
при capacity=7. Все-miss путь get тестируется отдельно на семи новых row;
его накладные расходы уже включены в CPU полного assessment.

Условие ускорения базовой capacity=7 [R2]: sum CPU assess на полном replay меньше baseline, и в каждом
из трёх контрольных benchmark медиана 15 оконных speedups >1.0. Показать
также все регрессии отдельных окон/состояний, а не только общую медиану.
Если условий нет, оптимизация не принята: сохранить отрицательный результат
и доложить; не расширять область до C2/absence/batch. Cloud end-to-end и
физический эффект на котёл этим локальным CPU-протоколом не доказываются.
Итоговая evidence-таблица [R2] содержит все 6…14, агрегированные hit/miss/
eviction/peak, sum CPU и speedup assess/history_samples, три контрольных
повтора и saved unknown. Обоснование capacity=7 обязано опираться и на эту
CPU-таблицу с правилом §3, не только на отсутствие вытеснений.
