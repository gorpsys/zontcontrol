## Обзор

Превратить текущий клиент в локальный продукт: стабильный управляющий API
одного ЛК с несколькими устройствами, монополия на управляющие воздействия,
координация R1/R2, регистратор независимых алгоритмов в потоках одного
процесса, автоматический сброс и постоянный интерактивный CLI.

Это замена прототипа, не совместимая надстройка над ним. Старый монолитный
клиент разбирается на новые модули и в прежнем виде удаляется. Его Python API,
CLI-флаги, JSON и точки входа не требуется сохранять; compatibility/deprecation
слои не создаются. Новый API v1 становится первым стабильным контрактом продукта.

Цель — устранять подтверждённые температурные паттерны отказа котла и дать
другим алгоритмам единый интерфейс чтения/управления. Пользователь — владелец
отопления, разработчик новых алгоритмов и человек, контролирующий ручные
вмешательства. Первое устройство SMART 2.0; контроллер и CLI адресуют все
устройства аккаунта явно, не выбирая первый прибор автоматически.

## Подход разработки

- Каждый этап: тесты требуемого поведения → ожидаемое падение → минимальная
  реализация → рефакторинг → зелёные новые тесты и весь `make check`.
- Завершать этап полностью перед следующим. Все новые и изменённые пути
  проверять на успех, ошибки и относящиеся к ним конкурентные сценарии.
- Проверки поведения переносить вместе с ответственностью соответствующего
  модуля. Утверждения о старых сигнатурах, JSON и entrypoints заменять новыми
  контрактными тестами; не сохранять старый код ради зелёных тестов и не терять
  проверку данных, ошибок, калибровки и запрета управления без монополии.
- Runtime Python >=3.11 и stdlib. Новых зависимостей этот план не требует.
- Все проверки плана офлайн, с виртуальным устройством/HTTP и управляемыми
  часами. Не обращаться к токену владельца и не выполнять команды котлу.
- Не менять калибровку, трактовку unknown/suppressed и результаты имеющихся
  архивных проверок. Не требовать идеальных 45 минут и не инвалидировать
  решение автоматически из-за ручных изменений пользователя.
- Старые внешние контракты не поддерживаются. Проверяются новый API v1,
  новый CLI, help/version без токена/сети и чистая подготовка команд.
- Ещё не перенесённые части прототипа могут временно оставаться между этапами,
  но это не обязательство совместимости; их сигнатуры и тесты допустимо менять
  вместе с переносом. Не создавать transitional apply_command или legacy-обёртки.
  Не объявлять промежуточную сборку готовым продуктом. В этапе 15 удалить
  client.py/ZontClient, apply_command, cli.py/control.py, старые entrypoints
  и все оставшиеся импорты после переноса нужного поведения.
- Не добавлять IPC, отдельные процессы алгоритмов, DI-фреймворк, глобальный
  preview/execute, tickets, watchdog и журналы восстановления.

## Стратегия тестирования

Unit и контрактные тесты — unittest, текущий стиль Mock/patch. Основной
транспорт заменяем подставным; общий виртуальный сервер R1/R2 позволяет
проверять несколько независимых экземпляров приложения, а не только потоки.
Подставные часы учитывают продвижение времени, паузы и заданное расхождение
скоростей. Конкуренцию потоков синхронизировать Event/Barrier, а не долгими
sleep; реальные короткие ожидания допустимы только как предохранитель теста.

Для границ неизвестного исхода моделировать отдельно отправку, применение
запроса и получение ответа. У виртуального ресурса есть независимый oracle
интервалов управления для проверки статистики конфликтов. Наличие известного
межклиентского контрпримера не превращать в ложное обещание «всё безопасно»:
тестировать обнаружение/учёт результата. Локальный мьютекс, напротив, обязан
исключать одновременных владельцев одного прибора в одном процессе.

Графики проверять по содержимому SVG, данным, разрывам и подписям. Для CLI —
сценарии stdin/stdout/TTY с подставными адаптерами, без запуска браузера.
Browser e2e в проекте нет, новая веб-платформа не требуется.

После каждого этапа: `make check PYTHON=python3`. В конце — те же проверки
на Python 3.11/3.12, wheel и установленный CLI вне checkout. Порог coverage
не вводить произвольным числом: покрыть контрактные и отказовые сценарии.

## Решение и границы

Один управляющий модуль авторизованного ЛК, обычный DI и отдельный поток
каждого алгоритма. Монополия на целый прибор; чтение и подготовка команд
доступны без неё. Разные приборы управляются параллельно. Запуск once имеет
таймаут результата регистратора, кооперативную отмену и stopping до конца
finally; зависший поток отдельно не убивается.

R1=`notes` содержит лидерство и запрос/heartbeat. R2 — служебный суффикс
`name`, сохраняющий исходное имя, содержит grant и видимую занятость.
Исполнители R2 только читают; действующий лидер назначает/продлевает grant
после проверки R1. Исполнитель проверяет grant и текущий срок лидера.
Новый лидер учитывает существующую аренду; отсутствие heartbeat не означает
немедленный отзыв. Риск совместных записей R1 принят, статистика обязательна.

Внешний ЛК остаётся доступным. Человек контролирует редкие вмешательства
и принимает риск, автоматический finally сохраняется. API-успех команды
не называется физическим восстановлением отопления.

## Технические детали

### Публичный управляющий API v1

`list_devices`, `describe_values`, `read_current`, `read_history`,
`list_controls`, `prepare_command`, `try_acquire_control`, `release_control`,
`execute_command(command, control_session)` — в соответствии с архитектурой.

Неизменяемые DTO: DeviceInfo; ValueKey/ValueDescriptor; ValueReading/Snapshot;
HistoryPoint/HistorySeries/HistoryResult; ControlDescriptor/ValidatedCommand;
ControlSession/CommandResult. Ключ адресует device_id, kind, element_id и поле.
Хранятся unit/source, реальные measured_at либо null, received_at, quality,
запрошенный интервал, фактическое покрытие и time_truncated/причины неполноты.
Не синтезировать доступность истории из наличия current.

Ошибки фасада типизированы по договорённостям. Успех execute — успешный ответ
API; явное отклонение — известная ошибка; timeout/обрыв после отправки —
CommandOutcomeUnknown. Ошибка до отправки не означает неизвестное исполнение.
Наблюдаемое состояние необязательно и не подменяет подтверждение API.

Сессия привязана DI к конкретному потребителю и прибору.
try_acquire_control(device_id, lease_seconds=...) получает локальный бюджет
от отправки подтверждаемого nonce: получение grant и вся критическая секция
с finally и запасом. Его величину выбирает алгоритм. Сессия сообщает expires_at;
повторный захват той же сессии не продлевает её срок. try-acquire не ждёт
скрытую очередь: возвращает сессию либо Busy. Запрос R1 может оставаться
pending; повторная попытка того же ожидания использует request_id, а новая
операция — новый request_id. Если потребителю нужно ожидание собственного
grant, он явно повторяет try-acquire с прерываемым ожиданием в рамках своего
запуска. Чужой владелец не отзывается. Таймаут регистратора не отзывает сессию
автоматически; cleanup и ранее принятые команды завершаются по контракту.

### R1/R2 и относительное время

Формат versioned JSON; свободное состояние и некорректную запись различать.
R1: leader(owner UUID запуска, новый 128-битный token, seq, lease_s, clock_rho), request
(executor UUID, request_id, nonce, lease_seconds, состояние request/heartbeat/finished).
R2: owner, request_id, уникальный grant_id, leader_token, revision, lease_s, clock_rho,
подтверждённый nonce. Точные типы и правила парсинга фиксируются тестами.
grant_id связывается с token срока лидера; renewal увеличивает revision.

Абсолютные leader_until/lease_until чужих CLOCK_BOOTTIME не сравниваются.
rho выбирается по исходному lease_seconds до поправки: до 60 с включительно
0.10, до 300 с 0.05, до 600 с 0.01, свыше 600 с 0.005.
При K=(1+rho)/(1-rho) в R2 записываются lease_s=K*lease_seconds и clock_rho.
Ступень фиксирована на интервал; по увеличенному lease_s её заново не выбирают.
Deadline исполнителя равен nonce_send+lease_s/K,
где nonce_send — локальный момент отправки конкретного уникального
request/heartbeat nonce, подтверждённого в R2. Повторное чтение
того же подтверждения не начинает срок заново; неизвестный nonce не даёт
права действовать. Лидер мог подтвердить nonce только после его публикации.
Перед конфликтующей выдачей координатор, включая нового лидера, наблюдает
неизменный R2 не меньше его lease_s по своим часам: от получения первого
ответа до отправки последнего чтения с совпавшим результатом. Смена revision
сбрасывает наблюдение; явное завершение владельца допускает освобождение
без ожидания срока. Эти технические правила реализуют ранее принятые
ограничения часов; они не устраняют известную гонку совместной записи R1.

Лидерство: rho выбирается по исходному полезному периоду P, K=(1+rho)/(1-rho),
L=K*P, V=L/K. Для короткого Delta свой K_delta по той же таблице;
W=2*Delta с проверкой W>K_delta*Delta,
T_r=V/3. L выбирает кандидат, V>=8*Delta. Deadline от отправки, барьер от ack.
Общий предел срока — первоначальная отправка +1200/K_term при rho=0.005;
renewal его не сдвигает. Все участники используют совместимые Delta и таблицу
запаса, валидируют clock_rho и исходный период. CLOCK_BOOTTIME
обязателен для активной координации; отсутствие подходящих часов даёт явную
ошибку, а не молчаливый fallback без учёта suspend. Чтения вне координации
остаются доступны.

Для R1 наблюдение срока относится к блоку лидерства, а не частоте чужих
заявок. Восстановление старого блока посредством read/modify/write остаётся
известным принятым риском. Не вводить третий регистр/CAS или иной протокол
молча под видом реализации согласованной схемы.

Для сброса размер grant должен оставлять бюджет на весь 40-секундный импульс
и отправку off, чтобы штатное завершение не зависело от renewal в середине.
Этот бюджет и запас на получение grant/проверки/завершение выбирает сам
алгоритм. Для отдельной команды после обязательных проверок достаточно
now < executor_deadline в точке приёма; при равенстве или превышении —
ControlOwnershipRequired без отправки. Отдельный d_op/Delta не резервируется:
по решению владельца команда считается достаточно быстрой и атомарной.
Принятая до границы команда завершается и при более позднем ответе API.
Правило полного окна can_coordinate для служебных действий лидера сохраняется.
При потере/неопределённости доступа off всё равно вызывается из finally через
обычный API: нет обхода проверок, отказ явно отражается в результате/статистике.
Принятая команда не отменяется из-за последующего timeout запуска. Ограничения
физического выполнения при ошибке API и принятой гонке не скрываются.

### Регистратор, конфигурация и CLI

AlgorithmSpec: уникальный ID, modes, factory, требования и технический
minimum. RegistryConfig: disabled_modules, autostart_dual_mode=false,
minimum/recommended once timeouts, без module_configs. Собственный конфиг
алгоритм читает и валидирует сам. Технический minimum сброса
выводится из бюджетов здорового прохода, чтений, grant, 40 с и cleanup;
иллюстративные 120/180 не копировать как доказанные значения. Конкуренция
может дать Busy/Timeout и при корректном minimum.

Таймауты регистратора действуют только для once. Continuous работает без
deadline регистратора; его внутренние циклы, проверки, интервалы и таймауты
принадлежат самому алгоритму. Регистратор предоставляет start/stop и состояние,
не выдаёт внутренним действиям отдельные бюджеты и не применяет once timeout
к постоянному режиму. Управляющие воздействия требуют действующей монополии.

Фиксированные JSON в config/ корня проекта: registry.json для регистратора,
controller.json для управляющего модуля (контакт, транспорт, Delta/таблица rho,
статистика), boiler_reset.json и boiler_cli.json для алгоритмов.
Нет общей схемы конфигурации модулей в регистраторе: каждый сам владеет своим
форматом и ошибками чтения/валидации. Общий config.py может содержать только
общий JSON-reader и собственные настройки инфраструктурных компонентов.
Загрузка/схемы алгоритмов находятся в их модулях.
Каталог фиксирован относительно cwd: checkout и wheel запускают из корня
проекта с config/. Нет поиска вверх, --config и ZONT_CONFIG; в тестах чтение
и путь подставляются через DI. Примеры *.example.json копируют в фиксированные
рабочие имена. Запрещённый модуль свой конфиг не читает.
ZONT_TOKEN приходит из env; ошибка отсутствия с инструкцией текущей утилиты.
Не читать пользовательские credential-файлы внутри приложения. Для once
без терминала registry.json явно исключает boiler_cli; скрытого переключения его
режима или общего разрешения на реальные эффекты нет.

Прежний control --execute и его overrides удаляются вместе с кодом прототипа;
сохранять --contact/--timeout/ZONT_CONTACT и их приоритеты не требуется.
Новый boiler_cli читает свой фиксированный конфиг, получает готовый фасад через
DI и управляет только с действующей сессией. Общие контакт/HTTP-таймауты задаёт
controller.json. Отсутствие обязательного файла даёт ошибку с путём до сети.
Новые --help/--version и чистая prepare_command не требуют файлов, токена
и создания клиента.

Новый `zontcontrol` / `python -m zontcontrol` через application:
список алгоритмов, once одного/всех и локальный длительный host с явным
стартом dual-mode по команде. start/stop/restart доступны через объект
приложения/регистратор внутри того же процесса. Отдельный CLI-процесс не
объявляется способным остановить чужие потоки без согласованного транспорта;
daemon/control socket этим планом не добавляется. Закрытие host — сигнал
кооперативной остановки. Для программного чтения/истории потребитель получает
управляющий фасад без register_all и без запуска автоматики; старые read-only
команды прототипа не являются обязательными точками входа.

Постоянный boiler_cli обновляет данные раз в 60 с, работает параллельно вводу,
показывает разрешённые config устройства/controls/graphs, строит SVG stdlib.
Путь графика показывается пользователю; открытие viewer только по явному
действию. Цели — ступенчатые ряды, отсутствующие измерения — разрывы.

### Статистика

Структурированные события и агрегаты: попытки, grants, время ожидания,
потери/повторы заявок, смены лидера при active grant, Delta/RTT, 429/timeout,
cleanup, конфликты, неизвестные исходы и покрытие наблюдения. IDs — отдельно
от credentials; API-токен и сырые ответы ошибок не логируются. Локальный JSONL
в reports — наблюдения, не хранилище восстановления/владения. Версия протокола
и профиль нагрузки входят в отчёт; 99.9% остаётся ориентиром без gate.

Чекбоксы ниже — изменения/проверки внутри проекта. Внешние проверки на ЛК,

## Post-Completion

**Реальные наблюдения и приёмка:** проверка сериализованных размеров notes,
независимости name/notes в обоих направлениях, индикации и сохранения префикса;
read-only измерения RTT/полных окон и подбор Delta. Такие данные подтверждают
наблюдаемое поведение, а не доказывают линеаризуемость/жёсткую границу задержек.
Короткие прежние тесты не являются оценкой p99.9.

**Физическая проверка:** подтверждённая аномалия, on/off и остановка во время
импульса рядом с котлом; реальные команды только в рамках конкретного сценария
владельца. План, unit tests и сборка не выполняют эту проверку автоматически.
Ручной ЛК доступен с принятой ответственностью человека и видимой занятостью.

**Эксплуатационные данные:** собирать статистику реальных эпизодов и покрытия,
дорабатывать по результатам, отдельно по версиям/нагрузке. 99.9% не является
предварительным запретом реализации, но не объявляется достигнутым без данных.

**Будущая облачная работа:** Yandex Cloud Functions, handler/ZIP, OIDC,
workflow/deploy scripts и отдельные идентификаторы zontcontrol — следующий
план, не чекбоксы этого. Continuous требует долгоживущего host; once и
прерывание функции должны учитывать завершение finally. Ресурсы autorepeater
не переиспользуются. Настройка GitHub/ресурсов/публикация и выпуск также не
выполнены этим локальным планом.
