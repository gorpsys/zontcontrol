# История сброса за два часа и разрешение конфликтов worktime

Дата: 22.10.2026.
Статус: согласован владельцем 22.10.2026, в работе.
Изменения тестов согласованы вместе с планом 22.10.2026.

[Постановка владельца](20261022174030-reset-history-worktime-request.md).
База исследования: master 752c7efe10746dccca0cdb7be651553e6f0832c5, версия 0.7.2.

## Цель и границы

BoilerReset должен учитывать последнее доступное историческое состояние
переключателя сброса в пределах двух часов, даже если оно предшествует
температурному окну. При разных значениях worktime на одном времени
абсолютная метка исходного ответа ZONT получает приоритет перед дельтой.

Сохраняются Controller API v2, фиксированные конфиги, минутная сетка,
температурная интерполяция и профиль SMART_2_HEATING_CONFIG. Температуры,
цели, worktime и выбор датчика запрашиваются за прежние 46 минут, из которых
строится прежняя сетка детектора. Расширяется только история reset.
Не меняются пороги, минимальные пять пригодных точек, свежесть 120 секунд,
условия сброса, on → 40 секунд → off в finally и пауза после сброса.

Новые конфигурационные поля, зависимости, кэш между вызовами, координация,
новые облачные ресурсы и автоматическое повторение команд не нужны.
Дополнительное логирование причин unknown и измерение задержек публикации
ZONT в эту работу не входят.

По уточнению владельца изменение reset ограничено
zontcontrol/algorithms/boiler_reset.py. Изменение worktime ограничено
нормализацией в zontcontrol/history.py. Controller, транспорт, загрузчик,
heating_adapter, публичные DTO и форматы передачи данных между слоями
не меняются. Не добавлять reset_history в сигнатуру предметного адаптера
и не передавать признак абсолютной метки через Controller.

## Текущий путь данных

1. BoilerReset._run_once в zontcontrol/algorithms/boiler_reset.py получает T
   после проверки bindings и делает один read_history за 46 минут,
   включая reset_key.
2. ReadControllerService.read_history в zontcontrol/controller/service.py
   вызывает ZontAdapter.load_history, project_history и merge_history_points.
3. decode_delta_array в zontcontrol/history.py разворачивает время, но
   не сохраняет способ его записи. merge_history_points заменяет
   противоречивые значения на одном datetime на null/Quality.UNKNOWN.
4. from_controller_history в zontcontrol/heating_adapter.py выбирает
   предметные серии. assess_history и history_samples в zontcontrol/monitor.py
   уже умеют использовать точки reset, предшествующие HeatingHistory.start:
   нижнюю границу к ним повторно не применяют.

В [формате ZONT](https://lk.zont-online.ru/api/docs/#delta-time-array)
временные метки целочисленные. Отрицательное число задаёт приращение вперёд
от предыдущей метки; положительное — абсолютное UNIX-время.
Приоритет абсолютной записи — согласованное правило нашего клиента;
документация провайдера не задаёт разрешение таких конфликтов.

## Решение для истории reset

### Два запроса с общим конечным временем

В _run_once один раз получить T = self._wall_clock(), затем последовательно:

1. read_history(device_id, telemetry_keys, T − 46 минут, T), где
   telemetry_keys — config.history_keys без config.reset_key.
2. После проверки отмены read_history(device_id, (config.reset_key,),
   T − 120 минут, T).

Добавить фиксированную константу RESET_HISTORY_MINUTES = 120 рядом с
HISTORY_MINUTES = 46. config.history_keys оставить полным набором bindings:
_validate_bindings должен по-прежнему проверять и переключатель.
Перед вторым запросом и перед оценкой проверять context.cancelled;
при отмене вернуть существующий результат cancelled, не отправлять команды.

Пользоваться существующим read_history. Не менять load_history ради
оптимизации его data_types: запрос только reset_key может всё равно
получить дополнительные каналы ZONT, но предметный вход выбирает только reset.
За весь вызов once добавляется один запрос истории, без новых повторов.
Таймауты транспорта, once и облачной функции остаются прежними.

### Сборка HeatingHistory

Сборку выполнить только в BoilerReset, используя существующие типы
и from_controller_history с прежней сигнатурой:

1. Преобразовать первый ответ в основной HeatingHistory прежним вызовом
   from_controller_history с bindings config.
2. Отдельно преобразовать второй ответ тем же from_controller_history
   с теми же bindings. В этом предмете будет заполнена только reset-серия;
   отсутствие остальных серий уже допускается существующим адаптером.
3. Через dataclasses.replace создать копию основного HeatingHistory:
   reset взять из второго предмета целиком, received_at — максимум времён
   двух ответов, time_truncated — OR флагов, общие incomplete_reasons —
   объединение без потери причин. start/end и все телеметрические серии
   оставить от основного предмета. Не вводить общий merger или новый порт.

Сохранить все точки reset вместе с quality и incomplete_reasons. Не оставлять
только последнюю точку: переходы нужны для подавления во время сброса и
после его завершения. Существующие _points, _reset_at_end и history_samples
уже выбирают последнее значение не позднее min(end, received_at), включая
отметку до температурного окна. monitor.py и heating_adapter.py не менять.

При отсутствии reset, пустой серии, последней null или плохом качестве
сохраняется unknown; не подставлять сегодняшнее состояние read_current,
не брать значение старше двухчасового ответа и не угадывать OFF.
Точка после T не может определять состояние в T. При time_truncated
любой из двух историй сохраняется существующий отказ от оценки.
Ошибка второго чтения проходит по существующему пути ошибки run_once;
алгоритм не продолжает работу с одним температурным ответом.

Перед реальным импульсом по-прежнему отдельно проверяются online и текущее
состояние переключателя. Двухчасовая история эту проверку не заменяет.
Once, continuous и cloud используют один и тот же путь _run_once.

## Решение для worktime

### Сохранение происхождения метки

В zontcontrol/history.py вынести существующий разбор в частный
_decode_delta_candidates. Внутри этого файла сохранить для каждого
элемента точный datetime, value и признак row[0] > 0.
Признак относится к конкретной записи, не наследуется дельтами после
абсолютного якоря и не вычисляется по уже развёрнутому datetime.

decode_delta_array остаётся с прежними аргументами и возвращает прежний
список словарей time/value. Он использует частный разбор, затем убирает
внутренний признак. Валидация и разворачивание дельт остаются прежними.

project_history использует тот же частный разбор, проверяет значения и
отсекает будущие точки как раньше. Только для circuit/worktime разрешает
дубликаты, пока признак ещё доступен внутри нормализации. Наружу возвращает
прежнюю пару: tuple обычных HistoryPoint и tuple причин неполноты.
Не менять сигнатуры project_history/merge_history_points, их входные
и выходные форматы, вызовы из Controller и публичные DTO.

### Выбор значения

Условие выбора находится внутри project_history:
descriptor.key.kind == 'circuit' и descriptor.key.field == 'worktime'.
Собрать записи одного исходного ответа по точному datetime, выбрать группу
максимального приоритета, затем разрешать совпадения внутри этой группы:

| Записи на одном времени | Результат |
| --- | --- |
| Абсолютная и дельта с разными значениями | Абсолютная |
| Абсолютная null и дельта с числом | null, без подстановки дельты |
| Несколько абсолютных с одинаковым значением/качеством | Одна точка |
| Несколько абсолютных с разными значениями | null, Quality.UNKNOWN, conflicting_timestamps |
| Только дельты, значения совпадают | Одна точка |
| Только дельты, значения расходятся | null, Quality.UNKNOWN, conflicting_timestamps |

Порядок поступления не меняет выбор. Более поздняя дельта не затирает
абсолютную и не снимает конфликт двух абсолютных. Точки с разными datetime
не конкурируют по виду метки: сохраняются и сортируются по времени.

Граница применения — один исходный ответ ZONT. Для противоречий между
уже нормализованными частями запроса остаётся существующий unknown:
межслойный контракт не содержит вида исходной метки, добавлять или скрыто
кодировать его в DTO/quality/причинах неполноты запрещено. В целевом once
оба запроса (46 и 120 минут) меньше суточной части Controller и не требуют
межчастного выбора. Это ограничение явно указать в документации и тестах.

Приоритет не применяется к температуре, целям, reset, mode_id и другим
полям. Для них остаётся прежнее консервативное разрешение противоречий.
Признак conflicting_timestamps добавлять для оставшегося противоречия;
побеждённая дельта сама по себе больше не создаёт его для worktime.
Причины null_values для worktime выводить из выбранных точек, чтобы
отброшенная null-дельта не делала пригодную абсолютную точку неполной.

В исследовательских архивах, уже утративших вид исходной метки, приоритет
не восстанавливать догадкой. Их loader и старые golden-результаты
не переписывать. Новые чтения через Controller получают новое правило.

## Критерии приёмки

1. При пустом reset внутри 46 минут, но пригодном последнем OFF внутри
   двух часов, неизвестность не возникает только из-за длины старого окна.
2. Полностью неизвестный reset, недавний реальный сброс, неполная история
   и неизвестные телеметрические значения сохраняют прежние ограничения.
3. Пара дельта=60/абсолютная=0 на одном времени даёт worktime=0 и
   не очищает буфер как conflicting_timestamps.
4. Два равноприоритетных противоречивых значения по-прежнему дают unknown;
   правило не влияет на другие поля и на порядок точек разных секунд.
5. Все офлайн-проверки проходят без ZONT-токена, доступа к облаку и сети.
   Алгоритм, конфиги и физические команды не меняются за пределами двух правок.
6. Изменения runtime-логики ограничены boiler_reset.py для reset и history.py
   для worktime; клиент, транспорт, загрузчик, предметный адаптер и межслойные
   интерфейсы не изменены. Отдельно допускаются перечисленные тесты,
   офлайн-smoke, документация и обязательные метаданные выпуска __version__.

## После реализации

При наличии локальных снимков дополнительно повторить 16:30 с двухчасовой
reset-серией и 16:46 с новым правилом исходного worktime, с последней
температурной минутой и без неё. Эта проверка необязательна; поздний повтор
не восстанавливает исходный облачный ответ и не доказывает его причину.

Реальный запуск для проверки не нужен до отдельного согласования: изменение
пригодности данных может разрешить настоящий сброс при confirmed_pattern.
При согласованном деплое проверить GitHub Actions и logs/notes обычных
плановых вызовов, не создавать искусственный отказ и не запускать импульс
для диагностики. Каждый ручной запрос yc требует отдельного подтверждения.

Перед переносом плана и постановки в completed проверить обязательные
результаты, зафиксировать границы выполненной проверки и исправить ссылки.
План, зелёный CI и версия исходников сами по себе не означают деплой.
