# Бюджет аренды исполнителя

15.10.2026. Решение владельца по первому замечанию
[холодного ревью плана](../reviews/2026-10-15-architecture-alignment-plan.md).

## Первоначальное решение

Запас уточнён последующей поправкой ниже; остальные пункты сохраняются.

1. Принят большой запас на расхождение скоростей часов: rho=0.10 вместо
   прежнего 0.01. Сохраняется консервативная модель [1-rho, 1+rho],
   K=(1+rho)/(1-rho)=11/9. Исполнитель использует L/K, наблюдающий координатор
   ждёт полный L по своим часам. Абсолютная синхронизация не требуется.
2. Запрашивающий алгоритм сам выбирает срок на получение grant и всю
   критическую секцию, включая finally и запас на задержки. Управляющий
   модуль не оценивает длительность критической секции за алгоритм.
3. Каждая команда допустима до локального истечения аренды, без отдельного
   резерва на время команды: принято допущение о достаточно быстром и
   атомарном исполнении. В точке приёма проверяется now < deadline.
4. При now >= deadline новая команда отклоняется до отправки, включая
   команду из finally. Принятая до deadline команда завершается; последующее
   истечение срока, timeout/stop алгоритма её не отменяют.
5. Новый лидер учитывает выданную аренду с тем же запасом; отсутствие
   heartbeat не отзывает её немедленно. Сохраняются nonce-подтверждения,
   неизменность deadline при повторном чтении и отдельный полный бюджет
   служебных операций координатора.

Формулы и переходы закреплены в
[контракте](../reference/leader-election.md#срок-исполнителя-и-допуск-команд)
и этапе 7 [плана](../plans/20261015005915-architecture-alignment-implementation-plan.md).
Для API lease_seconds означает локальный бюджет от отправки подтверждаемого
nonce; R2.lease_s=K*lease_seconds, deadline=nonce_send+R2.lease_s/K.

Замечание №1 закрыто этим решением. Остальные замечания ревью не закрываются.
Существующие риски R1/R2 и сбор статистики сохраняются. Быстрота и атомарность
команды — принятое допущение, а не доказанное свойство ZONT. Результат API
по-прежнему может быть неизвестным. Код не изменялся, команды не отправлялись.

## Поправка: запас по длительности периода

Позднейшая поправка владельца от 15.10.2026 заменяет постоянный rho=0.10:

| Исходный период | Запас rho |
| --- | --- |
| До 60 с включительно | 10% |
| Свыше 60 с, до 300 с включительно | 5% |
| Свыше 300 с, до 600 с включительно | 1% |
| Свыше 600 с | 0.5% |

Коэффициент K=(1+rho)/(1-rho) сохраняется. Ступень выбирается по исходному
периоду до масштабирования и фиксируется на интервал; в R1/R2 хранится
clock_rho. По увеличенному lease_s ступень заново не выбирается. Для коротких
служебных окон запас вычисляется отдельно от длительной аренды.
Обновлены действующий контракт и TDD-план; замечание №1 остаётся закрытым.
