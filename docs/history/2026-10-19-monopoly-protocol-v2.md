# Монополия управления: реализация протокола v2

19.10.2026. Подготовлен выпуск 0.3.0, один PR — один выпуск.
[Выполненный план](../plans/completed/20261019002421-monopoly-protocol-v2-implementation-plan.md),
[постановка и уточнения владельца](../plans/20261019002421-monopoly-protocol-v2-task.md).
Этот результат не означает слияния, публикации тега или деплоя.

## Принятые решения и результат

Wire v1 заменён без legacy-адаптеров. R1=name с точным исходным префиксом
содержит лидера, текущий+один будущий grant, последний отказ и handled_request;
пишут только кандидаты/лидер. R2=notes содержит один запрос исполнителя;
лидер только читает. Даже роли одного процесса обмениваются только R1/R2.
Потеря R2 возможна, FIFO/справедливости нет; без лидера grant не выдаётся.

Controller API v1, request handles/terminal results, фиксированные timeout/lease,
локальная монополия и shutdown drain сохранены. Future grant не раскрывает
session до usable_from. Полученный grant хранит исходную причинную проекцию
и переживает смену лидера до expiry. Новые команды на expiry, включая finally,
отклоняются; принятые раньше завершаются. Lease на весь цикл/finally выбирает
алгоритм, не executor. Cancel/finish не отзывают опубликованный резерв.

Все ID — UUID; revision остаётся счётчиком. UNIX-метки относятся к фиксированной
epoch/BOOTTIME шкале лидера. Системные часы после snapshot не участвуют,
исполнитель проецирует свой nonce/sample на BOOTTIME со ступенями rho.
Fischer W=2Delta, исходное полное окно с per-call HTTP cap, freeze guard,
stop-margin Delta, карантин K(Delta_cmd)*Delta_cmd и отдельное подтверждённое
renewal перед каждым grant соблюдают горизонт leader_until>=grant_until+Delta.
Непрерывный срок ограничен 20 минутами от первого захвата, renewal его не сбрасывает.

Слоты сохраняются до valid_until+command_guard и продвигаются только после
окончания резерва. Память обработанных ключей живёт весь срок, один маркер
handled_request переживает cleanup/takeover. Старый term не обслуживается;
pending создаёт новый nonce с прежним request_id и бюджетами. Restart не
восстанавливает сессию из одной строки. Shutdown оставляет естественное
истечение R1, без раннего FREE.

Пакет coordination зависит только от stdlib, своих модулей и control_types.
Production использует статические экспорты/порты; application собирает DI
с поздней фабрикой worker и закрывает ресурсы после drain. Новых зависимостей,
IPC, процессов алгоритмов, watchdog, recovery-журналов и сервиса операций нет.

## Запуск и конфигурация

По решению владельца старых протокольных значений на приборах нет. Первый
запуск — обычный протокол на исходном name/пустых notes, без миграции/очистки.
Неизвестный/v1 формат или профиль не FREE и не стирается. Все клиенты обновляются
совместно; controller.json нужно привести к [v2 примеру](../../config/controller.example.json).
Переход последующих профилей A→B требует остановки A, полного previous_profile
и нового UUID B: дождаться аренды/хвоста A, R1 B, затем запрос исполнителя R2 B.
R1 B/R2 A после остановки между строками продолжает обычный протокол.

При старом горизонте 300 с наблюдение ≈331.58 с от первого своего чтения плюс
poll/HTTP/W/карантин; один request с timeout 90 с недостаточен. Запущенный
координатор переживает terminal bootstrap-запрос; после выбора роли новый
запрос получает свои фиксированные сроки. Старый запрос не продлевается.

## Проверка и калибровка

После задач 1–6: make check PYTHON=python3 — 646 unittest, четыре прежних
installed-only skip; PIP_NO_INDEX=1 make package-check PYTHON=python3 —
шесть тестов без skip. Проверены часы/границы/freeze, конкуренция кандидатов
и динамических исполнителей, future grants, хвост, takeover, unknown, профили,
первый запуск и одинаковый API исходников/wheel. Тесты без реальных команд.
Документация и версия отдельно проверяются перед фиксацией задачи 7.

[Калибровка](../reports/2026-10-19-coordination-v2-calibration.md):
3 888 000 нормальных запросов, отдельно 7776 fault cases. Симуляционный
победитель poll 1/retry 5/jitter 0.25/renewal 0.25 имеет 2825/9000 GRANTED,
18 DECLINED, 6157 timeout; цензурированные timeout и все начатые запросы сохранены.
Это результат модели нагрузки, не надёжность настоящего API.

После наблюдавшихся HTTP 429 пример вручную использует provisional
poll 20/retry 60/jitter 0.25/renewal 0.25. Натурный aggregate: четыре запроса,
один GRANTED и три timeout, одна команда «Расписание»/readback mode 20503.
Actual step=1.0 не соответствует разрешённым ±0.1, поэтому по явному решению
владельца температурная серия пропущена. Температурных/reset команд,
запусков автономных алгоритмов и деплоя не было.

Delta=5 с, Delta_cmd=5 с, период 300 с остаются unmeasured допущениями.
API RTT/readback и 40-секундный цикл reset не измеряют физический хвост:
physical_tail=unknown. Полные окна, команда, секция и residual effect учитываются
раздельно, рекомендации не применяются автоматически.

Атомарность/линеаризуемость строк и применение до timeout либо никогда —
предпосылки модели, не доказанные гарантии ZONT. Freeze после guard,
превышение Delta/rho/Delta_cmd, внешнее вмешательство остаются границами.
Старые R/L/A сопоставлены с конкретными защитами или остаточным риском в
[реестре](../reference/coordination-failure-scenarios.md). Принятый риск не
разрешает новых причин нарушения или ослабления проверок. Строгая безопасность
и достигнутые 99.9% не заявляются. Прямой ЛК остаётся под ответственностью
человека; индикация в name/R1 не блокировка и не доказательство автора команды.

Полный текущий контракт — [лидерство](../reference/leader-election.md),
[API](../agents/contracts.md), [архитектура](../agents/architecture.md),
[статистика](../reference/orchestration-risk.md). Облачные workflow/идентификаторы
не менялись. Версия выше локальной базы 0.2.1 и локальных тегов до v0.2.0;
актуальные base/tags повторно проверяет CI. Аннотированный v0.3.0 после merge
создаёт Release tag workflow; вручную теги не создаются и не переносятся.
