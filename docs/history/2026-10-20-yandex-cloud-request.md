## Запрос владельца

1. Посмотреть в репозитории gorpsys/autorepeater, как реализован деплой в
   облако и как формируется архив для облачного деплоя.
2. Добавить в Makefile таргет формирования аналогичного архива. В облачном
   архиве — только разовый запуск определения аномалий и сброса котла.
3. Секрета и функции пока нет. Создать функцию в том же каталоге, что
   функция образца. Создать отдельный сервисный аккаунт деплоя для нашего
   репозитория, по аналогии и с теми же правами. Создать отдельный секрет:
   в образце t_token, для ZONT — z_token. Значение владелец положит позже.
   Создать и настроить триггер раз в 15 минут, использовать существующий
   аккаунт invoker. Остальные ресурсы использовать те же, что у образца.
4. Логгер привести в соответствие с образцом. Облачный запуск использует
   подходящий для облака логгер.
5. Для манипуляций с облаком использовать yc. Каждый запрос предварительно
   подтверждать у владельца с объяснением действия и цели.
6. Если что-либо непонятно — уточнять у владельца.
7. Цель — автоматический деплой в Yandex Cloud и работа функции по таймеру.
8. Все необходимые команды yc уточнить по документации на этапе плана.
   Читать облако можно; реальные изменения — строго при реализации.

## Последующие подтверждения

- Во время реализации владелец переименовал функцию образца в t-invest.
  Её ID d4e6d0l53hkivgrmfano остаётся привязкой; python-function — имя,
  наблюдавшееся до переименования. Архитектура и общие ресурсы не меняются;
  дополнительных запросов yc для перепроверки переименования не выполняли.
- Подтверждение каждого запроса yc относится к ручным действиям агента.
  Согласованный автоматический workflow выполняет деплой без отдельного
  подтверждения каждой своей команды.
- По первоначальному уточнению таймер предполагалось создать заранее и
  держать на паузе. После холодного ревью владелец заменил этот порядок:
  **создавать таймер после первого успешного деплоя**. До заполнения секрета
  и успешного деплоя таймера нет. Отдельное подтверждение его создания
  охватывает включение плановых реальных сбросов.
- Замечание P2 принято: локальный logger настраивается в application.main,
  общем для console script и python -m zontcontrol, без настройки при импорте
  библиотеки или вызове create_application.
- После повторного ревью владелец выбрал повторы как у autorepeater:
  retry_attempts=1 и interval=10s у таймера, без явного --async-max-retries
  при публикации версии функции. Повтор таймера выполняет весь once и может
  снова инициировать сброс; это не автоматический повтор отдельной команды.
- Все выполненные при планировании запросы yc были отдельно согласованы.
  Читались метаданные функции/версии/таймера, имена аккаунтов, IAM и OIDC,
  метаданные секрета. Payload Lockbox и значения env не читались.

## Применимые прежние договорённости

Runtime — stdlib; TDD и офлайн-проверки. Авторизация и особенности ZONT
остаются за Controller API v2. Используется существующий boiler_reset и
его калибровка; новый детектор не создаётся. Синхронизация управления
удалена, локальные или распределённые блокировки не возвращаются.
Импульс — on, 40 секунд, off в finally; смерть процесса и жёсткое
завершение хоста остаются вне гарантии. Работа с секретом не означает
разрешения читать или публиковать его значение.
