# История версий

> Исторические состояния выпусков с датами приведены ниже. Текущая
> [процедура выпуска](../../scripts/README.md#версии-и-выпуск) хранится отдельно;
> старые статусы подготовки и деплоя не являются состоянием проекта сейчас.

## Выпущен 0.7.0, 21.10.2026

MINOR добавил публичное чтение/замену notes выбранного устройства и сохранение
трёх последних cloud-логов. [PR #15](https://github.com/gorpsys/zontcontrol/pull/15)
слит в SHA 6dc71121cbc2feb290dbc5403bb1ef450bf379ea; аннотированный тег v0.7.0
указывает на этот коммит. Controller API дополнен совместимыми операциями;
координация управления не возвращалась.

[Отчёт приёмки](../reports/2026-10-21-yandex-cloud-acceptance.md#публикация-и-источники-проверки)
фиксирует успешный автоматический deploy этого SHA и отдельно — включение
таймера владельцем. Наблюдаемые ручной и последующие вызовы, сохранение notes,
normal/unknown и границы проверки описаны в том же отчёте. Ни тег, ни ACTIVE
сами по себе не доказывают вызов или физическое восстановление котла.

## Выпущен 0.6.0, 21.10.2026

MINOR добавил UTC-отметку первого подключения клиента в name и подробную
безопасную диагностику облачного вызова. [PR #14](https://github.com/gorpsys/zontcontrol/pull/14)
слит в SHA 3a17ff774704d186e2e55d7a5599b725caa72dca; аннотированный тег v0.6.0
указывает на этот коммит. Возможности добавлены без смены контракта детектора
или возврата монополии управления.

Публикация наблюдаемости и ручной вызов с результатом normal без сброса
подтверждены в [хронологии приёмки](../reports/2026-10-21-yandex-cloud-acceptance.md#промежуточные-этапы-публикации).
Это свидетельство прежнего выпуска, отдельное от последующей приёмки 0.7.0.

## Выпущен 0.5.2, 21.10.2026

PATCH восстановил рабочий способ загрузки ZIP через yc с обычным путём --body,
YC_IAM_TOKEN и временным профилем. [PR #13](https://github.com/gorpsys/zontcontrol/pull/13)
слит в SHA 73ff90b1d804caa8c5ad3f07037e1d473da8ce98; аннотированный тег v0.5.2
указывает на этот коммит. Исправление деплоя сохранило runtime и алгоритмы.

[Первый успешный автоматический deploy](https://github.com/gorpsys/zontcontrol/actions/runs/39575985386)
опубликовал версию функции из этого SHA и подтвердил ACTIVE. Создание таймера
после deploy было отдельно разрешено владельцем; само по себе оно ещё не
подтверждало плановые вызовы. Источник и дальнейшие этапы —
[хронология приёмки](../reports/2026-10-21-yandex-cloud-acceptance.md#промежуточные-этапы-публикации).

## Подготовка 0.5.1: состояние до публикации 21.10.2026

PATCH улучшает безопасную диагностику границ HTTP/yc и неизвестного исхода
upload; протокол публикации, runtime и алгоритмы сохранены. На момент этой
записи облачная приёмка ещё не была завершена. Позднее в тот же день
[PR #12](https://github.com/gorpsys/zontcontrol/pull/12) слит в SHA
9641bdf8f23137087740730562efa0d354862946, на который указывает аннотированный
тег v0.5.1. Deploy этого выпуска остановился на upload без создания версии
функции — [хронология](../reports/2026-10-21-yandex-cloud-acceptance.md#промежуточные-этапы-публикации).
Номер и тег исходников не подтверждали успешный deploy.

## Выпущен 0.5.0, 21.10.2026

Один MINOR относительно master 0.4.0 добавляет облачный once-вход, минимальный
ZIP и автоматический workflow OIDC/Lockbox. Controller API v2 и контракт
детектора сохранены. [PR 11](https://github.com/gorpsys/zontcontrol/pull/11)
слит в SHA 5003b9cf33d774c267f4c4ecb69757c7eab47f04; Release tag опубликовал
v0.5.0. [Project checks](https://github.com/gorpsys/zontcontrol/actions/runs/39517478702)
успешны, автоматический deploy пока неуспешен:
[диагностика](../reports/2026-10-20-yandex-cloud-provisioning.md#попытки-деплоя-и-исправление-oidc-21102026).
Таймера и облачной приёмки ещё нет. Номер не подтверждает активацию.

В 0.5.0 внутренний каталог BUILTIN_SPECS из zontcontrol.autonomy.catalog
заменён ленивой фабрикой builtin_specs(). Для прежнего явного импорта переход
состоял в вызове create_application(catalog=builtin_specs()); стандартное
локальное приложение использует create_application(), once без CLI —
create_application(catalog=(BOILER_RESET_SPEC,)). Eager-алиас не сохранялся:
он снова импортировал бы отсутствующий в минимальном облачном ZIP BoilerCLI.
BUILTIN_SPECS не входил в потребительский Controller API; сам перенос
внутреннего импорта не требовал MAJOR по
[правилам версий](../../scripts/README.md#версии-и-выпуск).
Текущие фабрики и границы — [архитектура](../agents/architecture.md#3-регистратор-и-запуск).

## Первоначальный порядок выпуска: решение 16.10.2026

Раздел описывает состояние на 16.10.2026, до первого продуктового выпуска.
Действующая процедура — [scripts/README](../../scripts/README.md#версии-и-выпуск).

После сверки с autorepeater/master на SHA 49cb338daae8d808706ec9d2480ca3f21ea4dcfd
принят явный номер __version__ в zontcontrol/__init__.py, совпадающий с первым
выпуском CHANGELOG. Первый подготовленный номер был 0.1.0; на тот момент
тега и опубликованного выпуска не было. Вычисление версии из git describe
с суффиксами .dev/dirty было отменено.

В принятой тогда схеме Offline checks проверял увеличение номера относительно
тегов и базы PR, а Release tag должен был создавать аннотированный тег на SHA
мержа отдельной очередью. Скрипт был проверен на временных Git-репозиториях
и локальных bare remotes. Git checkout и origin gorpsys/zontcontrol были
настроены; Actions фактически прошёл
для SHA этапа 16 — [итог](2026-10-16-architecture-implementation.md).
Источники/адаптация — [история технического обновления](2026-10-15-autorepeater-technical-refresh.md).

Весь первоначальный PR составлял **первый продуктовый выпуск 0.1.0**. Базой master был
пустой подписанный корень 618729441d34cd3c8c5ade78d316144307fa1fa1, без
версии приложения. Прежняя ошибочная публикация прототипа и его тега отменена
по решению владельца; на origin на тот момент тегов не было. Локальная резервная ссылка
не являлась выпуском и не предназначалась для публикации. Это исправление первого
продуктового выпуска, а не основание переносить уже выпущенные теги позднее.
Версия оставалась 0.1.0 для всех этапов первоначального PR. Завершение локального
плана не выполняло merge/release/tag/deploy; создание тега было поручено
workflow на будущем SHA мержа.

## Начальное состояние

В проекте первоначально был статический номер 0.1.0 в pyproject.toml,
но подтверждённого релиза, аннотированного тега и привязки к release SHA нет.
Первоначально была принята вычисляемая из тегов версия checkout без тегов
0.0.0.dev0; эта схема заменена явной версией описанным выше решением.

На этом этапе первый номер 0.1.0 был подготовлен локально; подтверждение
его выпуска ожидалось от workflow.
Номер исходников не подтверждает успешный production-деплой.
