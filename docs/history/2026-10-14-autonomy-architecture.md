# Архитектура автономных модулей, 14.10.2026

По требованиям владельца записана [целевая архитектура](../agents/architecture.md):
управляющий модуль одного ЛК с несколькими приборами, собственными DTO и
фиксированным API чтения/истории/команд; каталог, DI и регистратор независимых
потребителей; контролируемый once и continuous с автозапуском/stop/start.

boiler_reset поддерживает оба режима и при текущем confirmed_pattern
запрашивает импульс сброса 40 секунд. boiler_cli — continuous-only,
обновление раз в минуту, графики/устройства/команды из собственного конфига.
Запрещённые модули и minimum/recommended timeouts задаются конфигурацией
регистратора. Все доступные доверенные модули вне списка запрета регистрируются.

В первом проекте выделены управление deadline вне алгоритма, конфликты
физических команд и завершение off независимо от жизни worker. Последнее
позднее заменено решением владельца №4 на finally с ограниченной гарантией.
Процессная изоляция —
проектируемый вариант для некоперативного кода, не sandbox для вредоносных
модулей. В первой версии не нужны DI-фреймворк, event bus, microservices
или динамическое сканирование сторонних plugins.

Функция Яндекса подходит для once, а не бесконечного CLI. Импульс требует
расчёта бюджета поверх 40 секунд, включая off из finally до жёсткого timeout.
Независимый механизм восстановления не нужен по решению №4. Координация
прямого ЛК остаётся вопросом №7.

Код и параметры действующего детектора не менялись. Владелец запросил
отдельное ревью холодным читателем: оно выполняется независимым субагентом
по первому проекту документов. [Ревью](../reviews/2026-10-14-autonomy-architecture.md)
содержит десять замечаний и сравнение альтернатив; архитектура уточнена.
[Реакция автора](../reviews/2026-10-14-autonomy-architecture-resolution.md)
различает решения владельца и предложения по остальным замечаниям.

## Решение владельца по замечанию №1

При работающем continuous разовый запуск того же алгоритма завершается
понятной ошибкой, без скрытой остановки/перезапуска. Dual-mode по умолчанию
после регистрации ждёт команды: continuous начинается по явному start либо
при autostart_dual_mode=true в конфиге регистратора (умолчание false).
Continuous-only сохраняет немедленный запуск после регистрации.
Этим заменена предложенная автором схема выбора host-профилей; платформа
Cloud Functions всё равно не поддерживает постоянную работу.

## Решение владельца по замечанию №2

Реальное управление — часть назначения автономного алгоритма. Boiler_reset
при подтверждённой аномалии должен сбросить котёл; обязательный глобальный
режим preview/execute у регистратора или управляющего API не нужен.
Предпросмотр, если требуется, реализуется конкретным потребителем.
Этим снято прежнее предложение автора об общем режиме выполнения.
Поведение текущего ручного CLI не менялось; код алгоритмов не писался.

## Решение владельца по замечанию №3

Повторы — ответственность алгоритма. Для continuous после выключения сброса
и включения котла установлена пауза 5 минут до повторной проверки.
Для once специальный учёт повторов не вводится; рекомендуемый интервал
запусков примерно 15 минут по оценке владельца. Отдельная пятиминутная
пауза внутри once после импульса не нужна. Прежние предложения об общем
guard, хранилище попыток и ручном повторном разрешении сняты.
Согласованное поведение хранится в [описании модуля](../reference/boiler-reset.md).

## Решение владельца по замечанию №4

При штатной остановке и исключениях finally немедленно выключает сброс,
включая котёл; оставшиеся 40 секунд не ожидаются. Эта граница гарантии
достаточна. Журналы, watchdog, независимый исполнитель и восстановление
после принудительного kill/смерти host не вводятся. Общий pulse/ticket API
снят: составное действие выполняет сам алгоритм обычными командами.
Код не менялся, документировано ожидаемое поведение.

## Решение владельца по замечанию №5

Команда, отправленная алгоритмом управляющему модулю, исполняется всегда:
она не отзывается по таймауту или остановке алгоритма, в том числе если
ожидала во внутренней очереди. Предложение проверки активности запуска
при допуске/перед отправкой снято. Обычные команды и finally используют
один API без отдельного разрешения на завершение. Таймаут самого алгоритма
остаётся под контролем регистратора; технические ошибки команд сохраняются.
Код не менялся.

## Решение владельца по замечанию №6

В исполнитель добавлено требование монополии на целое устройство по принципу
мьютекса. Один алгоритм управляет одним прибором в данный момент; разные
приборы доступны разным алгоритмам одновременно. Вне своей монополии все
управляющие воздействия возвращают ошибку без сетевой команды; чтения,
история и предпросмотр её не требуют. Это уточняет допуск по решению №5:
принятая от владельца команда не отменяется по timeout/stop.

Boiler_reset удерживает монополию до off из finally, освобождает после него,
на пятиминутную паузу не удерживает. CLI захватывает её для отправки команды,
а не на всю жизнь интерфейса. Журналы и независимый исполнитель не добавлены.

[Исследование API](../reports/2026-10-14-zont-control-lock-api.md) не выявило
документированного mutex/lease/CAS или произвольного флага аккаунта. Возможный
общий флаг-переключатель не обеспечивает атомарный захват, его безвредная
настройка на SMART 2.0 не проверена. Гарантия относится к общему исполнителю;
между отдельными исполнителями/host нужна общая синхронизация, backend ещё
не выбран. Прямой ЛК остаётся замечанием №7. Изучались только публичные
документы; код, флаги и настройки реального устройства не менялись.

### Последующее решение: условный выбор лидера

После натурных проверок name и notes владелец предложил Fischer + lease.
Приняты поправки о запасе ожидания при rho, измерении полных окон операций
и наблюдении неизменной записи перед перехватом. Алгоритм применяется только
к роли лидера устройства; через вторую строку лидер координирует исполнителей.
Монополия на управляющие воздействия и finally алгоритма отделены от lease
координатора.

L выбирается кандидатом по ожидаемой работе; технический минимум сохраняет
V>=8*Delta. Весь непрерывный срок лидерства ограничен 20 минутами от захвата,
продления не начинают новый срок. Для переменного L в записи обязательно
lease_s. [Контракт](leader-election.md) содержит формулы, бюджет
запуска/освобождения и примеры 1, 2, 5 и 20 минут при rho=0.01.

Условная безопасность опирается на заявленные временные границы и
линеаризуемость, которая для ZONT пока не доказана. Протокол передачи активного
доступа между лидерами и конкурентные изменения второй строки ещё предстоит
закрепить; один выбор лидера не объявлен полной гарантией монополии.
Рабочий код и настройки котла этим решением не менялись.

### Принятие схемы R1/R2 с риском

Владелец принимает текущую схему с оговоркой: собирать статистику и
дорабатывать её по результатам. Это заменяет предыдущее условие сначала
обосновать успешность 99.9%. Целевой уровень не объявляется достигнутым.

R1 (notes) совмещает лидерство и запросы/heartbeat исполнителей. R2 (суффикс
name с сохранением исходного названия) — источник разрешения; исполнители
только читают R2. Перед его записью лидер подтверждает роль через R1,
исполнитель сверяет grant с текущим сроком лидера. Новый лидер учитывает
существующую аренду; отсутствие heartbeat не отзывает её немедленно.

Найденные гонки и неопределённости сохраняются как основания последующих
доработок; для оценки собираются эпизоды, задержки, конфликты и неизвестные
исходы. Это не возврат отклонённых журналов восстановления/watchdog.
Замечание №6 закрыто принятием риска. [Учёт](orchestration-risk.md),
[схема](leader-election.md). Изменена документация, код не правился.
