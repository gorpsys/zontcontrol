# Правила ведения документации

## 1. Выбор места

Перед созданием текста определите его назначение: действующий контракт,
процедура, обоснование, свидетельство проверки или будущая работа.
Общий вход — [карта документации](../README.md), выбор правил для правки —
[индекс инструкций](README.md). Новые README в каждом каталоге не нужны.

| Документ или каталог | Что хранится | Что сюда не добавлять |
| --- | --- | --- |
| [README](../../README.md) | Установка, запуск и использование текущего приложения | Хроника PR, промежуточные SHA, история настройки облака |
| [scripts/README](../../scripts/README.md) | Команды разработки, упаковки, CI и выпуска | Полная копия облачного how-to, журнал старых ошибок |
| [config/README](../../config/README.md) | Схема конфигов, defaults и ошибки валидации | Обязательная миграция уже удалённого прототипа |
| [AGENTS](../../AGENTS.md) | Короткие обязательные ограничения и маршрутизация | Хроника сессий, таблицы API и IAM |
| [docs/README](../README.md) | Маршруты пользователя, разработчика и оператора, история и планы | Второе описание runtime |
| [Индекс инструкций](README.md) | Область изменения → текущие правила → обоснование | Требование читать все архивы перед каждой правкой |
| Этот документ | Размещение, изменение, проверка и архивирование документации | Копия бизнесовых правил алгоритма |

| [Контракты](contracts.md) | Python/DTO/CLI-обязательства, ошибки и наблюдаемые эффекты | Облачные ID и журналы приёмки |

| `docs/reference/yandex-cloud-resources.md` | Реестр ресурсов проекта с датой и источниками | Secret payload, значения env, догадки о внешнем состоянии |

Реестр ресурсов и H-индекс — назначенные места для следующих шагов
упорядочения. Пока они не созданы, ссылки ведут на существующие отчёты
и [исторический индекс](../history/README.md). Названия имеющихся тематических
справочников сохраняются; симметрия каталогов не является причиной переноса.

## 2. Один источник

API и поведение описываются в соответствующем контракте или справочнике;
порядок выпуска — только в [scripts/README](../../scripts/README.md#версии-и-выпуск);
текущие ресурсы — в их реестре после его создания. В остальных местах давайте
краткое описание и ссылку вместо копии изменяемого списка. Повторяемая таблица
допустима как явно обозначенный пример, не как второй действующий реестр.

## 3. Основания утверждений

Действующий контракт сверяйте с кодом и существующими тестами. Несовпадение
документа и реализации само по себе не разрешает менять код под текст.
Для внешнего факта укажите дату проверки, конкретный источник или отчёт,
SHA/ID при наличии и предел вывода. Отсутствие свидетельства оставляйте
неопределённостью, не заполняйте догадкой.

## 4. Статусы

Текущий документ описывает действующее поведение без «этот PR» и статуса
сессии. У плана явно указан статус: draft, принят, в работе или выполнен.
Исторический документ содержит дату; для отменённого решения — заметную
пометку и ссылку на заменившее решение. Старое ревью не является списком
нынешних открытых проблем без проверки применимости.

## 5. Изменение контракта

Обновите один канонический раздел и затронутые ссылки и примеры. Причину
существенного решения запишите в `docs/history/`, результат выпуска —
в [CHANGELOG](../../CHANGELOG.md). Реорганизация документации не разрешает
менять бизнесовые правила, калибровку или runtime. Из autorepeater можно
заимствовать устройство документации; его бизнесовые решения здесь не действуют.

## 6. Версия и деплой

Различайте подготовленную версию исходников, тег выпуска, опубликованную
версию функции и наблюдённый вызов. CI, сборка и план не доказывают активацию.
Датированный отчёт не подтверждает нынешний ACTIVE или новую физическую
проверку. Успех API не доказывает физическое восстановление; unknown
сохраняется как unknown. Порядок выпуска задаёт
[единственная процедура](../../scripts/README.md#версии-и-выпуск).

## 7. Находки

Для новой находки используйте следующий свободный H-ID: дата, один контрпример,
причина, ссылка на проверенный источник и действующий канонический раздел.
ID не переиспользуются. Отменённая находка остаётся с пометкой и ссылкой
на заменившее решение. Короткой находке не нужен отдельный файл; большие
свидетельства храните в `docs/reports/` или `docs/reviews/`. До создания
H-индекса обоснования доступны через [историю](../history/README.md).

## 8. Жизненный цикл плана

В `docs/plans/` храните только невыполненную работу. Перед переносом
в `completed/` проверьте обязательные результаты и внешние действия,
если они нужны цели. Отсутствие разрешения не означает выполнение.
Не закрывайте невыполненный пункт как пропущенный. При переносе исправьте
входящие и исходящие относительные ссылки и якоря; compatibility-файл
на прежнем пути не создавайте. Локальные `progress-*.txt` не публикуются.

## 9. Архивирование

Сохраняйте свидетельства отменённой координации и первоначальные вердикты.
Не переписывайте старые измерения под новую архитектуру: добавьте исторический
статус и ссылку на [решение об удалении синхронизации](../history/2026-10-20-remove-synchronization.md).
Архив не переопределяет контракт и не становится обязательным чтением для
обычного запуска или любой правки. Карту архивов поддерживайте
в [историческом индексе](../history/README.md).

## 10. Примеры и секреты

Не публикуйте рабочие токены, пароли, сертификаты, secret payload, сырые ответы
с credentials и рабочие JSON-конфиги. Не переносите их в логи или аргументы.
В how-to явно обозначайте placeholders, адресата и эффект команды, ожидаемый
результат и способ проверки. Чтение инструкции не разрешает выполнять команды.
Каждый ручной запрос `yc` требует отдельного подтверждения владельца;
согласованный автоматический workflow не требует разрешения на каждую команду.
Офлайн-проверки не вызывают ZONT или облако. Merge требует отдельного запроса
владельца; подготовка документа или PR его не разрешает.

## 11. Проверка

Используйте локальные относительные ссылки с действительными якорями;
свидетельства в GitHub привязывайте к конкретному SHA. После правок выполните
`make lint` и `git diff --check`, при завершении — `make check` по
[правилам разработки](development.md#проверки). Для shell-примеров применяйте
`bash -n`, для Python — compile без исполнения команд и внешних эффектов.
Если меняется состав пакета, требуется `make package-check`. Новые инструменты
проверки и зависимости ради Markdown не добавляйте.

## 12. Завершение изменения

Проверьте карту документации, канонический раздел, обоснование при необходимости,
статус плана, release metadata и отсутствие секретов в полном staged diff.
Версия в `zontcontrol/__init__.py` совпадает с первым выпуском CHANGELOG;
один PR — один выпуск по [процедуре](../../scripts/README.md#версии-и-выпуск).
Timestamp и фраза «проверено» не заменяют результат проверки. При неизвестном
внешнем состоянии укажите границу знания и источник, не объявляйте будущий
деплой или публикацию состоявшимися.
