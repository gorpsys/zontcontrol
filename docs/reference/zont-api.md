# Данные и команды ZONT

Подробности нормализации ответов и ограничений API. Начало работы —
[README](../../README.md); технические инструменты — [scripts/README](../../scripts/README.md).

## Снимок датчиков и контуров

Команда печатает JSON: `fetched_at` (UTC, RFC 3339), список приборов
(`id`, `name`, `model`, `online`) и их датчики
(`id`, `name`, `type`, `status`, `value`, `unit`, `triggered`).
Дополнительно у каждого прибора возвращаются `circuits` (отопительные контуры)
и `modes` (названия режимов). У контура:

- `actual_temp` — фактическая температура, `target_temp` — текущая целевая,
  `unit` — °C;
- `setpoint_temp` — расчётная уставка теплоносителя из полного API:
  `io["z3k-state"]["ID контура"].setpoint_temp`;
- `type` — `boiler`, `consumer`, `dhw` или `cooling`;
- `current_mode` — ID режима, `current_mode_name` — его название;
- `active` — идёт нагрев, `is_off` — контур выключен,
  `in_summer_mode` — включён летний режим, `work_mode` — способ работы из API;
- `min`, `max`, `step` — допустимые пределы и шаг задания температуры.

Для вашей конфигурации SMART 2.0 у используемого контура «Отопление»
(ID `20496`) `target_temp` — целевая температура воздуха, `setpoint_temp` —
расчётная температура теплоносителя. Оба значения берутся из ZONT
и могут меняться при работе его алгоритма. Контур «Котел» возвращается API,
хотя скрыт в вашем интерфейсе; клиент пока выводит все контуры.
Для других конфигураций назначение температуры определяется настройками
контура: тип `consumer` сам по себе не гарантирует регулирование по воздуху.
Значение `current_mode: null` означает ручной режим по документации API.
Если ID режима есть, но его название отсутствует в ответе, возвращается
`current_mode_name: null`. Недоступные температуры и пределы тоже равны `null`.
Если для контура нет `setpoint_temp` в полном API, выводится `null`.
Значения связываются по ID прибора и контура, без подстановки уставки из другого
контура. Два запроса читают данные последовательно: снимок не атомарный.

Серийные номера, SIM, геопозиция и остальные поля полного ответа не выводятся.

`value: null` означает отсутствие числового показания, а не ноль.
`triggered` нужен для дискретных датчиков. Статусы могут быть `ok`, `failure`,
`unknown`, `alarm`, `silent_alarm`; отдельно учитывается `online` прибора.

**`fetched_at` — время получения ответа, а не измерения датчика.**
Схема Sensor в API v3 не предоставляет время измерения. Даже `online: true`
и `status: ok` не гарантируют свежесть числового значения.
Перед реализацией управляющей логики потребуется проверка давности показаний
через доступные данные истории/полного API, а также безопасное поведение
при потере связи и ошибках датчиков.

## История

Последние сутки для вашего контура «Отопление»:

```sh
python3 -m zontcontrol --history --hours 24 --device-id 700877 --circuit-id 20496
```

Используются `ZONT_TOKEN` и `ZONT_CONTACT` либо `--contact`.
Без `--hours` и `--from` берутся последние 24 часа. Фиксированный период:

```sh
python3 -m zontcontrol --history --device-id 700877 --circuit-id 20496 --from '2026-10-12T10:00:00+03:00' --to '2026-10-13T10:00:00+03:00'
```

Даты должны содержать часовой пояс (`Z` или `+03:00`). `--from` и `--hours`
вместе не используются; `--to` без `--from` задаёт конец относительного периода.
Если не указать `--device-id`, запрашиваются все приборы. `--circuit-id`
фильтрует историю контуров и требует однозначного выбора одного прибора;
история температурных датчиков прибора остаётся целиком.

Клиент читает текущие имена датчиков и контуров, затем историю методом
`POST /api/load_data` с типами `z3k_temperature` и `z3k_heating_circuit`.
Это проверено для вашего SMART 2.0; другие типы архивов пока не поддерживаются.
Результат содержит `requested_period`, `fetched_at` и у каждого прибора:

- `temperature_sensors`: ID, текущее имя датчика, °C, `points`;
- `circuits`: ID, текущее имя контура и `series` с рядами `target_temp`,
  `setpoint_temp`, `mode_id`, `status`, `worktime`, `target_sensor_id`;
- `modes`: текущие названия режимов и их ID;
- `time_truncated`: признак сокращения диапазона сервером.

Каждая точка имеет `time` (RFC 3339, UTC) и `value`.
Delta-time Array декодируется по правилу ZONT: отрицательное значение времени
означает прибавление его абсолютного значения к предыдущей метке.
Точки сортируются по времени и ограничиваются запрошенным диапазоном.
Промежуточные значения не достраиваются, `null` не заменяется нулём.
Частота записи отличается у разных рядов: показания обычно поминутные,
изменения уставок и режимов могут записываться реже.
Если датчик или контур больше не присутствует в текущей конфигурации,
сохраняется его архивный ID, а имя равно `null`.

## Элементы управления

```sh
python3 -m zontcontrol --list-controls --contact YOUR_EMAIL
```

Используются те же `ZONT_TOKEN`, `ZONT_CONTACT`, `--device-id`, `--timeout`.
Команда делает один GET-запрос к API v3 и возвращает у каждого прибора
`elements`: контуры, режимы, кнопки, переключатели, регуляторы, сценарии,
охранные зоны и исполнительные устройства, которые присутствуют в ответе.

У элемента есть `id`, `name`, `kind`, `source`, `state`, `actions`.
Список `actions` описывает документированные команды: метод, URL и параметры
JSON-тела. Получение списка не выполняет команды и само по себе не проверяет
их успешность на приборе. Если `actions` пуст, поле `reason`
объясняет отсутствие команды. Неизвестные категории тоже показываются
без предположений о способе управления ими.

Реле, насосы, смесители и адаптеры отображаются в списке, но в документации
API v3 нет отдельных методов их прямого управления. Статусы отображаются
без команд. Зависимые контуры не получают команду изменения уставки.
Скрытые в интерфейсе элементы могут присутствовать в ответе API.

У переключателей сохраняются `active_label` и `inactive_label`: они описывают
смысл состояний `true` и `false`. Изменение `target_temp` переводит контур
в ручной режим. Активация режима без `circuit_id` применяется к устройству;
локальная активация с `circuit_id` документирована только для линеек + и PRO.

Проверенный список на вашем SMART 2.0 (прибор `700877`):

| ID | Элемент | Документированная команда v3 |
| --- | --- | --- |
| 20496 | Отопление | Задать целевую температуру, перевод в ручной режим |
| 20494 | Котел (скрыт в интерфейсе) | Задать целевую температуру |
| 20503 | Расписание | Активировать режим |
| 20501 | Комфорт | Активировать режим |
| 20502 | Эконом | Активировать режим |
| 8654 | Горячие батареи | Активировать режим |
| 8349 | Поддержание температуры | Активировать режим |
| 20504 | Выключен | Активировать режим |
| 8832 | Сброс котла | Установить состояние переключателя |
| 20488 | Реле | Отдельной прямой команды нет |
| 8818 | Реле сброса | Отдельной прямой команды нет |

У «Сброс котла» API возвращает подписи `true` → «отключен котёл»,
`false` → «включен котёл». Список зависит от конфигурации прибора; актуальную версию
получайте командой `--list-controls`.

## Подготовка и отправка

Отдельная утилита `python3 -m zontcontrol.control` по умолчанию только показывает
JSON будущего запроса (`dry_run: true`). Сетевых обращений нет, токен не нужен.
Предпросмотр проверяет ID и типы параметров, но не проверяет актуальные
возможности прибора и его пределы.

Примеры для вашего прибора — все команды ниже только готовят запрос:

```sh
# Целевая температура воздуха контура «Отопление».
python3 -m zontcontrol.control set-temp --device-id 700877 --element-id 20496 --temperature 22

# Режим «Расписание»; эта команда пригодится для возврата из ручного режима.
python3 -m zontcontrol.control activate-mode --device-id 700877 --element-id 20503

# Режим «Комфорт» на 30 минут.
python3 -m zontcontrol.control activate-mode --device-id 700877 --element-id 20501 --duration 30

# Сброс котла: false, подпись API «включен котёл».
python3 -m zontcontrol.control set-switch --device-id 700877 --element-id 8832 --state off
```

У «Сброс котла» `--state on` отправляет `target_state: true` (подпись API
«отключен котёл»), `--state off` — `false` («включен котёл»).
Эти подписи описывают состояния переключателя; физическое поведение
зависит от настройки автоматики и проверяется непосредственно у котла.

Поддерживаемые команды:

| Команда | Обязательный параметр |
| --- | --- |
| `set-temp` | `--temperature` |
| `activate-mode` | Нет; `--duration` опционально, минуты |
| `set-switch` | `--state on/off` |
| `press-button` | Нет |
| `set-regulator` | `--value` в единицах регулятора |
| `run-scenario` | Нет |
| `set-guard` | `--state on/off` |

Каждая команда требует `--device-id` и `--element-id`. Утилита предназначена
для элементов с соответствующей командой из `--list-controls`:
простых кнопок, регуляторов, сценариев и охранных зон у вашего прибора
при последней проверке не было. Прямое управление реле не реализовано,
поскольку соответствующей документированной команды v3 нет.
`setpoint_temp` читается как расчётная уставка теплоносителя; отдельной команды
её изменения в контуре «Отопление» мы не нашли. `set-temp` меняет `target_temp`.

**Отправка выполняется только при добавлении `--execute`.** Она требует
`ZONT_TOKEN` и `ZONT_CONTACT` либо `--contact`. Перед отправкой клиент читает
актуальный список элементов, проверяет связь с прибором, наличие элемента,
его тип, поддерживаемую команду и диапазон `min`/`max` для числового значения.
Точный шаг числового значения сервер проверяет сам; `step` из UI не округляет
передаваемое значение. Зависимый контур не допускает задания температуры.
Активация режима выполняется для устройства целиком, без `circuit_id`;
таймер `schedule` и локальная активация режима пока не реализованы.

При отправке устанавливается таймаут. Автоматических повторов нет.
Ошибка или таймаут после отправки не доказывает, что команда не выполнилась:
перед повтором прочитайте состояние и проверьте прибор.
Изменение температуры переводит контур в ручной режим и сбрасывает текущий
режим; для возврата в расписание активируйте режим `20503`.

В Python доступны `prepare_command(...)` из `zontcontrol.commands` и
`client.apply_command(command)` — по умолчанию предпросмотр без сети.
`client.apply_command(command, execute=True)` читает список элементов
и отправляет команду. В результат не включаются заголовки авторизации.

## Монополия и общие флаги

В целевой архитектуре управляющие воздействия требуют монополии на прибор
у общего исполнителя; текущий standalone CLI ещё не реализует этот контракт.
В опубликованных спецификациях ZONT не найден штатный mutex/lease или
атомарная условная запись. Читаемое состояние переключателя может быть
согласительным флагом, но не доказывает монополию между клиентами.
Доступность отдельного безвредного флага на SMART 2.0 не проверена.
Название name читается методом devices и изменяется update_device полного
API. [Реальные тесты строки](../reports/2026-10-14-zont-name-live-probe.md)
на SMART 2.0 подтвердили JSON/Unicode и длины до 65536 ASCII-символов без
обрезания; это не атомарный замок и не установленный верхний предел.
Второе поле notes также [проверено реальными запросами](../reports/2026-10-14-zont-notes-live-probe.md):
читается через devices и меняется отдельным полем update_device, сохраняя name.
Очистка — пустая строка; null получил HTTP 400. individual_device_note
присутствует в ответе, но проверенная запись не изменила его несмотря на ok=true.
Источники, кандидаты и границы —
[исследование от 14.10.2026](../reports/2026-10-14-zont-control-lock-api.md).

## Авторизация

Утилита создаёт токен методом POST /api/widget/v3/authtokens с Basic Auth
и client_name. Ответ содержит token и token_id; пароль вводится скрыто.
Каждый запуск создаёт новый токен. Основной клиент использует X-ZONT-Token,
X-ZONT-Client (контакт, не обязательно логин), HTTPS и явный таймаут.
401/403 — отказ в доступе, 429 — ограничение частоты. Основной клиент не
повторяет запросы автоматически; сборщик архива отдельно повторяет чтение
при 429 с ограниченной задержкой. Управляющие запросы не повторяются.

Официальные источники:

- [Widget API v3](https://my.zont.online/api/widget/v3/)
- [Спецификация OpenAPI v3](https://my.zont.online/api/widget/v3/docs)
- [Полный API](https://lk.zont-online.ru/api/docs/)
