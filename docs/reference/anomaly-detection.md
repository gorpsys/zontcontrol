# Алгоритм разового обнаружения

Текущий профиль: SMART_2_HEATING_CONFIG, калибровка 22.07—13.10.2026.
BoilerReset получает T один раз и отдельно читает телеметрию за [T−46 минут,T]
для 45 минутных отсчётов и reset за [T−120 минут,T]. Два ответа преобразуются
прежним адаптером; внутри алгоритма reset-серия целиком добавляется к основному
предметному входу. Начало/конец и телеметрия остаются от первого ответа,
received_at — максимум двух ответов, time_truncated — OR, общие причины
неполноты объединяются. Каждый запуск принимает решение на T новым экземпляром
детектора. Состояние между запусками не требуется. Только измерения с временем
не позже момента решения.

## 1. Что читать

Фактическая температура воздуха: z3k_temperature[8207].
Фактическая температура воды: z3k_temperature[8429].
Цель воздуха: z3k_heating_circuit[20496].target_temp.
Цель воды: тот же контур «Отопление», setpoint_temp.
Запрос нагрева: worktime того же контура, секунды за минуту.
Выбор датчика воздуха: target_sensor_id должен быть 8207.
Намеренное отключение: z3k_web_element[8832].state, «Сброс котла».
Скрытый контур «Котел» 20494 не используется для целей температур.
worktime — запрос автоматики, не измерение пламени. Цифрового адаптера
котла нет; аппаратного кода ошибки и прямого признака пламени нет.
Режимы и неизвестные биты status не считаются признаками неисправности.

## 2. Пригодность данных

Вход monitor — HeatingHistory после явного адаптера Controller или архива.
Исходные измерения сортируются по точному datetime без округления секунд.
При дублях выбирается последняя исходная точка; плохое качество/null в ней
не заменяется предыдущим хорошим дублем. Controller quality кроме good
даёт вычислительное None при сохранении исходного value.

Внутри одного assess_history приватный RowCache ёмкостью 7 переиспользует
подготовленные ряды и индексы исходных timestamps. Ключ включает идентичность
frozen HeatingSeries и точный cutoff=min(history.end, received_at); запись
удерживает исходный объект. Промах выполняет полный фильтр времени, LRU
вытесняет только подготовленный результат. Самостоятельный history_samples
создаёт отдельный кэш при начале итерации. Между вызовами кэш не сохраняется;
правила пригодности и результаты не зависят от попадания в него.
Обоснование ёмкости и проверка эквивалентности —
[приёмка RowCache](../reports/2026-10-26-rowcache-acceptance.md).

До предметного входа Controller разрешает дубли circuit/worktime и
circuit/setpoint_temp одного исходного ответа: абсолютная метка имеет
приоритет над дельтой независимо
от порядка. Абсолютная null также побеждает число из дельты и остаётся
неизвестной. Приоритет — правило клиента, а не гарантия ZONT или подтверждение
физической правильности значения. Равные значения выбранного приоритета дают одну точку;
противоречивые — null/unknown и conflicting_timestamps. Отброшенная null-дельта
не добавляет null_values. Для других полей и конфликтов между нормализованными
частями запроса сохраняется unknown. Разные точные datetime не конкурируют.
Вид метки не передаётся в предметный вход; его нельзя восстановить догадкой
в старых архивах. Формат меток — [справочник ZONT](zont-api.md#история).

Фактические температуры воздуха и воды нормализуются независимо. Точное пригодное
измерение на расчётной минуте используется прямо; иначе между двумя
непосредственными соседями t0 < t < t1 с интервалом <=120 с вычисляется
T(t)=T0+(T1-T0)*(t-t0)/(t1-t0). Обе опоры должны быть конечными числами
пригодного качества. Null/плохая точка не обходится поиском дальней опоры;
при отсутствии пары температура неизвестна. Переноса последней температуры
и экстраполяции нет. Цели, worktime, выбор датчика и reset остаются ступенчатыми:
последнее значение с точным временем <= t. Null не заменяется нулём.

T — точный конец исходного окна, G — начало его минуты. Все точки заранее
ограничены временем <= T и <= received_at. Конец сетки E=G; если у воздуха
или воды нет точки с временем >=G, E=G-60 с. Наличие null/плохой опоры
не разрешает скрыть её сдвигом. Дальнейшего сдвига нет; пропуски внутри
сетки сохраняются. Минуты берутся строго после max(history.start,E-45 минут)
до E включительно: при полном окне 45 отсчётов. Отставание E от T может
достигать почти 120 с. Свежесть исходных измерений и состояние reset
проверяются относительно T, включая события после E. Правая опора позже
внутренней минуты допустима только если уже доступна к T/received_at.

Нечисловые значения, worktime вне 0—60, другой выбранный датчик воздуха
или разрыв больше 120 секунд очищают наблюдение. Для решения нужны
не менее пяти пригодных минутных точек после последнего пропуска/сброса.
Настоящие временные метки датчиков проверяются отдельно от fetched_at
и минутной сетки. Последние измерения старше 120 секунд или сокращённый
сервером диапазон дают unknown (anomaly=null), а не отказ или норму.

## 3. Намеренное отключение

state=1: suppressed, anomaly=false, intentional_shutdown.
После последнего реального переключения дать 5 минут на запуск:
suppressed, anomaly=false, restart_grace. Учитывать короткие события
между минутными измерениями. Повторная запись того же состояния не
продлевает паузу. Проверять переключатель на точное время конца периода,
включая события после последней точки сетки. Если состояние неизвестно,
unknown, anomaly=null. При сокращённом архиве результат остаётся unknown.
В BoilerReset последнее доступное состояние ищется во всей двухчасовой серии,
включая точку до начала температурного окна и на границе T−120 минут.
Отсутствующая/пустая серия, последняя null или плохое качество дают unknown;
текущее состояние и более старые отметки вместо истории не подставляются.
Будущая точка не определяет состояние в T. Повторный OFF старше 46 минут
сам по себе не делает reset неизвестным и не продлевает restart_grace.
В исторических проверках до 27.09.2026 23:36 Москва сброс считается OFF
по указанию владельца: переключателя тогда не существовало.

## 4. Неисполненный запрос нагрева

После пяти пригодных точек одновременно проверить:
а) среднее worktime последних пяти минутных точек >=40 с/мин;
б) эффективная цель воды = min(setpoint_temp,85 °C);
в) эффективная цель воды минус фактическая вода >=4 °C.
85 °C — физический предел котла. Историческая уставка ZONT 90 °C
нормальна; нынешняя 82 °C также подставляется в ту же формулу.
Если условия перестали выполняться, очистить текущий сегмент наблюдения.
Это само по себе не доказывает восстановления аппаратуры.

## 5. Проверка отклика

Взять предыдущие пять минут включая текущую точку (до шести точек).
Температура воды должна быть не ниже, чем в предыдущей точке, и выполняется
хотя бы одно: рост от минимума окна >=3 °C; рост относительно самой
ранней точки окна >=1 °C. Такой отклик очищает текущий сегмент.
Если отклика нет, запомнить начало непрерывных пригодных условий и
температуру воды в начале. В новом разовом запуске начало восстанавливается
из предыдущих 45 минут; оно может оказаться позже физической остановки.

## 6. Исключение стабильной горячей воды

Если вода теплее воздуха больше чем на 10 °C и остыла от начала сегмента
менее чем на 0,5 °C, новый сигнал не выдавать: постоянный нагрев может
работать без заметного роста температуры. Проверка действует до
предупреждения и подтверждения.

## 7. Предупреждение и подтверждение

Отсутствие отклика >=13 минут даёт WARNING, если пройдены предыдущие
условия. Для CONFIRMED_PATTERN дополнительно:
а) выдержка >=13 минут при текущей воде <=60 °C;
   выдержка >=14 минут при текущей воде >60 °C;
б) воздух не выше цели (target_air - actual_air >=0 °C)
   ИЛИ вода остыла >=3 °C относительно начала текущего сегмента.
Температурная граница 60 °C проверяется в каждой точке. При остывании
ниже неё выдержка становится 13 минут; накопление не начинается заново.
Подтверждение может сразу появиться без промежуточного WARNING.
Внутри непрерывного сегмента подтверждение не понижается из-за колебания
одного порога. Сброс, отсутствие запроса, достижение цели или отклик
прекращают текущий сегмент. В новом запросе весь расчёт независим.

## 8. Итог разового запроса

state_at_period_end: normal, warning, confirmed_pattern, suppressed, unknown.
anomaly=true для warning/confirmed_pattern, false для normal/suppressed,
null для unknown. decision_reason объясняет решение. false — отсутствие
текущих признаков по порогам; это не гарантия исправности котла.
Предыдущие события в прочитанном окне сами по себе не означают аномалию
сейчас. incident_pending — диагностика внутри окна, не отдельный критерий
решения; очищается при росте воды >=5 °C за <=5 минут на восходящей фазе.
Результат подтверждает температурный паттерн, не аппаратный диагноз.
automatic_control=false; автоматических команд и фонового процесса нет.
requested_period — исходный запрос истории, а latest_valid_sample — реальная
метка измерения. Синтетическая минута не становится measured_at. Ключи
sample_period/sample_lag_seconds в ответ не добавлены; границы сетки приводятся
только в [отчёте нормализации](../reports/2026-10-20-typed-heating-regressions.md).

Диагностика assessment и основного события once_finished:

- valid_temperature_samples — минуты с обеими ненулевыми температурами;
  прежнее поле не проверяет пригодность остальных каналов.
- usable_samples — число точек, принятых в буфер детектора за весь проход;
  detector_buffer_size — размер буфера в конце, после очисток, максимум 40.
- latest_valid_sample_age_seconds — возраст latest_valid_sample на конец
  requested_period, null при отсутствии точки. Метка сохраняет прежний смысл:
  минимум последних good ненулевых измерений воздуха и воды.
- reset_active_at_period_end — историческое состояние reset на T;
  reset_latest_measured_at/reset_latest_quality — метка и качество последней
  причинно доступной точки reset, null при её отсутствии. Плохая последняя
  точка не заменяется предыдущей good.
- time_truncated — объединённый флаг; BoilerReset дополнительно сохраняет
  telemetry_time_truncated и reset_time_truncated отдельно для каждого ответа.
- decision_reason — причина monitor; reason рядом с assessment — причина
  алгоритма. При current_reset_unknown сохраняются также current_reset_active
  и current_reset_quality из отдельной проверки перед командой. Они не заменяют
  исторический reset на T; отсутствие проверки в логе обозначается null.

once_finished содержит эти поля и requested_period без events, исходных рядов,
конфигов и заголовков. Это ограниченная структурная диагностика, а не снимок
входа для строгого повтора; правила решения и пороги не меняются.

## 10. Запуск

Для решения без управляющих воздействий используйте read-only фасад и
проверяемую проекцию истории из модуля. Пример запускается из корня проекта
с настроенными config/controller.json, config/boiler_reset.json и ZONT_TOKEN
в окружении; он читает последние 46 минут, включая историю сброса:

```python
from datetime import datetime, timedelta, timezone
from zontcontrol.application import create_read_controller
from zontcontrol.algorithms.boiler_reset import load_config
from zontcontrol.heating_adapter import from_controller_history
from zontcontrol.monitor import assess_history

config = load_config()
controller = create_read_controller()
end = datetime.now(timezone.utc)
history = controller.read_history(config.device_id, config.history_keys,
                                  end - timedelta(minutes=46), end)
typed = from_controller_history(history, device_id=config.device_id,
    circuit_id=config.circuit_id, air_id=config.air_sensor_id,
    coolant_id=config.coolant_sensor_id, reset_id=config.reset_control_id)
print(assess_history(typed, config=config.detector_config))
```

Повторное чтение даёт следующее разовое решение. Модуль boiler_reset уже
реализован: `python3 -m zontcontrol once boiler_reset` при подтверждённой
аномалии выполняет настоящий импульс сброса с off в
finally. Это управляющий запуск; успешный ответ API не доказывает восстановление
нагрева. Режим continuous также управляет котлом; политика, сроки и ошибки
описаны в [контракте сброса](boiler-reset.md).
