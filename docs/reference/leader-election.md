# Выбор лидера устройства: условный Fischer + lease

Статус: договорённости по решению владельца от 14.10.2026, после
[разбора формул](../reports/2026-10-14-fischer-lease-review.md).
Реализовано локально 16.10.2026 и проверено на виртуальном ресурсе офлайн.
Механизм выбирает лидера-координатора одного устройства;
монополия алгоритма на управляющие воздействия — отдельное понятие.
Текущая схема R1/R2 принята владельцем с известным риском и требованием
[собирать статистику и дорабатывать по ней](orchestration-risk.md).
Подтверждение 99.9% не является предварительным условием этого решения.

## Назначение и два поля

### Реализованный wire-формат v1

Кодек — zontcontrol/coordination/models.py. notes содержит JSON-объект
с точными ключами v=1, leader, request; leader/request могут быть null.
Пустая строка или null при чтении notes означает пустой R1; пустой R1
записывается пустой строкой. Неизвестные/повторные поля, другая версия,
повреждённые значения и несовместимые типы отклоняются, не превращаются в FREE.

| Запись | Поля |
| --- | --- |
| R1.leader | owner, token, seq, lease_s, clock_rho |
| R1.request | owner, request_id, nonce, lease_seconds, state, grant_id, grant_revision |
| R2 grant | v=1, owner, request_id, grant_id, leader_token, revision, lease_s, clock_rho, nonce |

owner/request_id/grant_id/nonce — канонические UUID; token/leader_token —
32 шестнадцатеричных символа (128 бит). seq/revision/grant_revision —
неотрицательные целые. state запроса: request, heartbeat, finished.
Для request grant_id/grant_revision равны null; heartbeat/finished обязаны
ссылаться на конкретные grant и revision. nonce связывает подтверждение
с локальной отправкой; исполнитель проверяет совпадение grant и текущего
срока leader_token. Один токен лидера не является grant алгоритму.

name без grant точно равен исходному имени. При grant форма строки:
`<исходное имя> [zc:v1 управление занято <JSON grant>]`.
Исходный префикс сохраняется; служебный суффикс снимается только после
полной проверки формата. Исполнители R2 не записывают. Перед записью R2
лидер подтверждает R1, при смене лидера учитывает активный grant.

Все сроки на wire относительные: lease_seconds — запрошенный исходный
период, lease_s — период с поправкой K; clock_rho фиксирует выбранную ступень.
Локальные expires_at/deadline/CLOCK_BOOTTIME значения и wall-clock timestamps
между процессами не передаются. Удержание mutex не продлевает R2.
Наблюдения записываются в JSONL, [схема и границы](orchestration-risk.md#реализованные-наблюдения).

Лидер через вторую строку может согласовывать доступ исполнителей.
Лидерство само по себе не является разрешением переключать котёл.
Лидер запрашивает доступ для собственного алгоритма так же, как остальные.

- notes (R1): лидерство, аренда лидера, запрос и heartbeat исполнителя.
  Пустое состояние лидерства — FREE; заявки не дают права на команды.
- name (R2): исходное название без изменения как префикс; служебный суффикс —
  единственный источник разрешения исполнения. Исполнители его только читают;
  действующий лидер выдаёт и продлевает аренду исполнителя.

Служебные записи полей — внутренние действия механизма координации, не
пользовательские команды отоплению. Они не требуют уже выданной ControlSession,
иначе выбор лидера был бы невозможен. Алгоритмы-потребители не получают
произвольную запись метаданных в обход управляющего модуля.

Разделение полей не означает доказанную безопасность очереди: независимость
записи name от notes в обратном направлении требует проверки реализации.
Подтверждена реальная запись notes без изменения name. Совместная запись R1
исполнителями и лидерскими переходами имеет известные гонки, принятые как риск.
Выдачу сериализует корректно действующий лидер; до совпавшего grant исполнитель
не управляет устройством. Новому лидеру нельзя заменять действующую аренду
исполнителя до её безопасного окончания. Потерянные запросы повторяются;
отсутствие heartbeat не означает немедленного отзыва уже выданной аренды.

## Временная модель

Используются только локальные монотонные часы CLOCK_BOOTTIME на Linux.
Wall-clock, NTP и обмен абсолютными метками часов процессов не используются.
Линеаризуемость get/set, предел относительных скоростей часов rho и жёсткая
граница Delta — условия безопасности, а не доказанные свойства ZONT.
Клиенты доверенные, заранее неизвестные; CAS и fencing устройства отсутствуют.

Поправкой владельца от 15.10.2026 запас rho выбирается по исходному периоду P
до применения поправки к длительности:

| Период P | rho |
| --- | --- |
| 0 < P <= 60 с | 0.10 (10%) |
| 60 < P <= 300 с | 0.05 (5%) |
| 300 < P <= 600 с | 0.01 (1%) |
| P > 600 с | 0.005 (0.5%) |

Сохраняется консервативный коэффициент K(P)=(1+rho(P))/(1-rho(P)). Для каждого
интервала коэффициент выбирается отдельно и фиксируется на этот интервал.
Масштабирование периода и пересечение порога не меняют уже выбранный rho.
Для короткого служебного окна нельзя брать меньший запас длительной аренды.
Это принятое допущение о погрешности на данном периоде, а не результат замера.
Все участники используют одну таблицу. Delta общий для участников/профиля
прибора, задаётся конфигом, не меньше 10*p99.9 RTT. Измеренная квантиль сама не доказывает верхнюю
границу. Окна включают паузы процесса и применение отправленных запросов.

## Длительность аренды и общий предел лидерства

L выбирает кандидат исходя из ожидаемого времени полезной работы, а не
автоматически выдаёт каждому запуску 20 минут. Для once при штатном завершении
лидер освобождает регистр; после crash другие ожидают выбранное L.

Сохраняется продление выбранной аренды с периодом T_r, но общий срок одного
лидерства ограничен 1200 секундами от первой отправки записи захвата.
Продления не начинают новый двадцатиминутный срок. Это два ограничения:
короткий интервал аренды L для восстановления после отказа и предел всей
непрерывной роли лидера. L фиксируется на время данного token, 0<L<=1200;
новый интервал/срок требует нового выбора лидера и нового token.

Запись R1.leader, пример формы полей без фактического изменения прибора
(на wire вложена в R1; owner/token здесь условные, не валидный payload):

```json
{"v": 1, "owner": "uuid-запуска", "token": "128-битный-случайный-token", "seq": 0, "lease_s": 120, "clock_rho": 0.05}
```

lease_s и clock_rho обязательны: наблюдатель не угадывает L и выбранную ступень
из собственной конфигурации. Для L=lease_s проверяется, что P=L/K соответствует
ступени clock_rho; по масштабированному L ступень заново не выбирается.
Значения валидируются по общей политике. Непонятную/некорректную запись нельзя
считать FREE или произвольно короткой арендой. Для каждого захвата новый token;
seq растёт при каждой записи подтверждённого лидера. Не-FREE записи не должны
повторяться; отсутствие случайных коллизий является условием гарантии.
Проверяется вместимость и точное чтение всего сериализованного record,
включая рост seq. Поддержка 16 байт сама по себе недостаточна.

## Формулы и проверка конфигурации

```text
rho = rho(P)                    # полезный период до поправки
K   = (1+rho)/(1-rho)
L   = K*P
V   = L/K
T_r = V/3
poll = L/10 + неотрицательный jitter
K_delta = (1+rho(Delta))/(1-rho(Delta))
W   = 2*Delta
```

W — барьер после ack захвата; обязательно W>K_delta*Delta.
Jitter барьера может только
увеличивать W. Сам deadline аренды начинается с отправки, не с ack.

Если t0 — отправка первого захвата, а s — отправка текущей записи:

```text
term_deadline  = t0 + 1200/K_term  # rho=0.005, период предела > 10 минут
lease_deadline = min(s + V, term_deadline)
```

Все эти моменты принадлежат локальным часам лидера, в строку не передаются.
Предел консервативный: при rho=0.005, K_term=1.005/0.995 полезный временной
бюджет максимального лидерства не больше 1188.060 секунд (19 минут 48.060 секунд) от t0.
Позднее продление не увеличивает term_deadline.

При старте обязательно V>=8*Delta, иначе отказ. Лидер также выбирает нижнюю
границу по ожидаемой работе. Для планирования можно использовать:

```text
A = 2*Delta + W                # консервативный бюджет захвата и подтверждения
C = Delta                      # бюджет штатного освобождения
H = ожидаемое время полезной работы координатора
P_min = max(8*Delta, A + H + C)
L_min = K(P_min) * P_min
L_min <= L <= 1200
```

Если L_min>1200, роль не запускается с такой конфигурацией. H — оценка для
выбора срока, не доказательство фактической длительности работы. Новые действия
координатора допускаются только по оставшемуся фактическому бюджету.
При Delta=5, H=60, W=10 период P_min=85 с, rho=0.05, L_min примерно 93.947 с;
выбор P=90 с, L примерно 99.474 с
покрывает эти оценки без двадцатиминутной аренды.

| L, с | clock_rho | V, с | T_r, с | poll без jitter, с | Максимальное Delta из V>=8*Delta, с |
| --- | --- | --- | --- | --- | --- |
| 60 | 0.10 | 49.091 | 16.364 | 6 | 6.136 |
| 120 | 0.05 | 108.571 | 36.190 | 12 | 13.571 |
| 300 | 0.05 | 271.429 | 90.476 | 30 | 33.929 |
| 600 | 0.01 | 588.119 | 196.040 | 60 | 73.515 |
| 1200 | 0.005 | 1188.060 | 396.020 | 120 | 148.507 |

Это допустимые числа по одному условию V>=8*Delta, не эксплуатационные
рекомендации для измеренного API. Опрос раз в 120 с даёт заметную задержку
наблюдения; фактическое ожидание после отказа включает опросы и HTTP.

## Захват, наблюдение и продление

1. Прочитать FREE либо наблюдать одну неизменную полную запись. После любого
   изменения owner/token/seq/lease_s отсчёт наблюдения начинается заново.
2. Для занятой записи от получения первого ответа до отправки последнего
   чтения должно пройти не меньше L из этой записи. Только точное совпадение
   последнего ответа разрешает попытку захвата.
3. От отправки разрешающего чтения до ack записи собственного record должно
   пройти не больше Delta. Превышение или неопределённость запрещают вход.
4. После ack ждать W, затем ограниченным чтением подтвердить собственную
   полную запись. До подтверждения действий координатора нет.
5. Каждая запись подтверждённого лидера и каждый переход второй строки,
   выдающий доступ, требуют can_coordinate(d_op). Бюджет d_op включает весь
   участок от проверки до завершения, в том числе до отправки HTTP.
6. Продление допустимо только при достаточном старом бюджете. Новый seq;
   deadline от отправки и с прежним term_deadline. Неизвестный результат —
   LeaseLost, cancel-событие для роли координатора; слепых повторов нет.
7. Штатное освобождение не выдаёт новых разрешений. Перед FREE завершены
   служебные in-flight запросы и согласована судьба активного доступа.
   Отправив FREE, прежний лидер больше не координирует, даже при потере ack.
8. Достижение term_deadline требует завершить роль. Дальнейшее участие
   начинается только через новый захват с новым token; автоматического
   продления старого token за предел 20 минут нет.

Локальные heartbeat/release/выдача разрешений согласуются одним механизмом
состояния. Все проверки времени принудительно принадлежат управляющей
координации, алгоритмы не могут продлевать их произвольно.

## Отдельная монополия исполнителя

Принятая схема R1/R2 требует, чтобы лидер перед каждой записью
разрешения R2 подтвердил свою роль чтением R1. Исполнитель сверяет owner,
request_id, grant_id и token текущего срока лидера R1 перед действием.
UUID процесса без token недостаточен при переизбрании. Обе проверки входят
в ограниченные окна; они сами по себе не являются атомарной парой операций.
Heartbeat не даёт права немедленно отзывать уже выданный grant.

### Срок исполнителя и допуск команд

Алгоритм запрашивает lease_seconds через try_acquire_control. Это локальный
бюджет от отправки подтверждаемого nonce, включающий получение grant и всю
критическую секцию с finally и запасом. Оценить его должен алгоритм;
исполнитель не оценивает длительность алгоритма и не требует запаса на
отдельную команду. ControlSession сообщает локальный expires_at.

```text
rho = rho(lease_seconds)
K = (1+rho)/(1-rho)
R2.lease_s = K * lease_seconds
R2.clock_rho = rho
executor_deadline = nonce_send + R2.lease_s/K
accept_command = valid_ownership_and_grant and now < executor_deadline
```

clock_rho сохраняет выбранную ступень: при чтении R2 её нельзя пересчитать
по увеличенному lease_s. Например, запрос ровно на 60 с использует 10%,
хотя R2.lease_s примерно 73.333 с. Запрос ровно на 300 с использует 5%,
хотя R2.lease_s примерно 331.579 с. Несовместимая запись права не даёт.

Локальный nonce_send запоминается до отправки уникального request/heartbeat.
Право появляется только после подтверждения именно этого nonce в R2;
повторное чтение не начинает срок заново, неизвестный nonce права не даёт.
Поздний ответ с уже истёкшим deadline не даёт даже краткого права управления.
Продление требует нового nonce и подтверждения; слепых повторов при неизвестном
исходе нет. Повторный try-acquire той же сессии сам по себе срок не продлевает.

При выдаче следующей аренды и смене лидера координатор наблюдает неизменный
полный grant R2 не меньше R2.lease_s по собственным часам: от получения первого
ответа до отправки последнего чтения. Изменение grant/revision сбрасывает
наблюдение; последнее чтение должно подтвердить то же значение. Пока нет
завершения владельцем или такого наблюдения истечения, конфликтующий grant
не выдаётся. Абсолютные часы клиентов не сравниваются.

Если истёкший grant относится к всё ещё записанной заявке R1, координатор
сначала потребляет эту заявку, сохраняя подтверждённый header лидера, затем
очищает R2. Следующий poll не выдаёт новую аренду тому же старому request.
Неизвестный исход записи прекращает роль без слепого повтора; принятый риск
гонок read/modify/write R1 сохраняется. Записи ушедших локальных владельцев
очищаются при следующих захватах: pending после срока запроса, finished
после срока сессии. Действующие сессии и незавершённый release до истечения
срока сохраняются для явного подтверждения.

После обязательных проверок owner/request/grant/leader_token исполнитель
проверяет now < executor_deadline в точке приёма команды под локальной
синхронизацией. При равенстве или превышении — ControlOwnershipRequired
до отправки команды. Дополнительный d_op/Delta из остатка не вычитается:
по принятому допущению команда достаточно быстрая и атомарная. Принятая до
deadline команда выполняется, даже если ответ придёт после него; in-flight
учитывается до завершения. Последующие команды, включая off из finally,
без действующей аренды отклоняются обычным API. Недостаточно длинная аренда —
ошибка расчёта запрашивающего алгоритма, она не даёт обхода проверки.

Это условное допущение, а не измеренная гарантия времени команды ZONT.
Отдельный бюджет полного окна сохраняется для can_coordinate и служебных
записей лидера; отказ от него относится только к управляющим командам.
Решение закрывает [первое замечание плана](../reviews/2026-10-15-architecture-alignment-plan.md)
и записано в [истории](../history/2026-10-15-executor-lease-budget.md).

При добавлении executor_request в тот же R1 его обычная перезапись может
восстановить старый header лидерства. Первоначальная модель лидерского
регистра не покрывает такие записи сторонних исполнителей. Даже ограниченные
по Delta копии могут переносить старый header цепочкой между клиентами.
[Проверка предложения R1/R2](../reports/2026-10-14-two-register-coordination-review.md)
содержит контрпример с обеими дополнительными проверками и условия для
относительных сроков grant. Эти риски не снимают последнее решение владельца:
схема принята со сбором статистики и последующими доработками. 99.9% и строгая
безопасность не объявляются доказанными.

Fischer выбирает координатора, а не отзывает команду котла по его lease.
Локальная монополия сохраняется на составное действие и finally; право новых
команд дополнительно ограничено собственным сроком R2, как описано выше.
LeaseLost прекращает новые действия координатора;
само по себе это не команда отменить уже принятые управляющие воздействия.
Сброс 40 секунд не требует can_coordinate(40) у выполняющего его алгоритма.

При смене лидера нельзя выдавать новый конфликтующий доступ, пока прежний
исполнитель имеет действующую аренду R2. Новый лидер учитывает её завершение
либо консервативное истечение по правилам выше. Сохранённый локальный мьютекс
прежнего процесса сам по себе не продлевает межклиентскую аренду.
Поведение при потерях/гонках R1 и отказах учитывается в статистике и
дорабатывается. Детали сериализации и переходов проверяются при реализации;
результат выбора лидера не объявляется доказательством всей монополии.

Паузы/задержки больше Delta, выход за rho и нарушенная линеаризуемость могут
привести к двум лидерам. CLOCK_BOOTTIME обнаруживает прошедшее время suspend,
но не даёт fencing. Прямой ЛК не соблюдает данный протокол; справедливости нет.

По решению владельца от 15.10.2026 в ЛК предусматривается видимая индикация
активного доступа через суффикс name/R2 при сохранённом исходном префиксе.
Состояние «управление занято» относится к grant исполнителя, а не наличию
лидера без исполняемой работы. Человек контролирует редкие ручные вмешательства
и принимает риск конфликта, включая завершение сброса из finally. Индикация
не является технической блокировкой прямого ЛК; замечание №7 закрыто этим
решением. Правила импульса — [boiler_reset](boiler-reset.md).
