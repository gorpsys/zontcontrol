# Сценарии отказа координации и границы монополии

Решение владельца от 16.10.2026. База: `master`
`6b9174571f2f266b761cdcb1b95cad742fd41027`, выпуск `0.1.2`.
Протокол — [лидерство/R1/R2](leader-election.md), измерения —
[риск и статистика](orchestration-risk.md).

Уточнение 17.10.2026 для API запроса монополии 0.2.0: принятый A04
сохраняется — потерянная idle-session до возврата handle может ожидать expiry.
Новый запрос не наследует отказанную session/ack и не выходит за собственный
created_at+lease_seconds (C03). Скрытая unclaimed-session защищена до атомарного
решения manager и первой попытки cleanup (C02); reuse проверяет действительность
reservation при выдаче GRANTED. Timeout между стадиями ленивой инициализации
обеспечивает срок API и сам по себе не доказывает строгую монополию; ранее
работающий coordinator независим от заявки. Начатые стадии могут закончиться
позднее (R04). Эти уточнения не переоткрывают R/L/A и не разрешают новые причины
нарушения. [Точный договор](../agents/contracts.md#запрос-монополии-api-v1).

## Как пользоваться реестром

Известные риски ниже приняты. Их наличие больше не является поводом заново
обсуждать выбранную архитектуру или блокировать разработку. Исправлять их
следует только если эксплуатационная статистика показывает слишком частое проявление.
Численный порог владелец пока не задавал; единичный эпизод или синтетический
контрпример сами по себе не объявляются превышением порога.

Новые изменения не должны добавлять пути нарушения или ослаблять имеющиеся
проверки. Сценарии сопоставляются по причине, участникам и порядку операций,
а не только по результату «два владельца». Отсутствие fencing уже принято;
раскрытие сессии отклонённого запроса через новый Python-метод — новая ошибка,
которую нужно устранить при разработке, не дожидаясь статистики.

Реестр объединяет известные классы перестановок операций и отказов в принятой
модели. Доказательства полноты для произвольного поведения ZONT, оборудования
и стороннего кода нет. Новая причина не считается принятой только из-за
сходства результата с одной из строк.

Статусы:

- **Риск** — известный путь конфликта, принятый с наблюдением частоты.
- **Граница** — условие гарантии; при выходе за него монополия не обещается.
- **Доступность** — ожидание/отказ, сами по себе не конфликт монополии.
- **Защищено** — предотвращение обязательно; появление пути является регрессией.

Два кандидата, две pending-заявки или несколько Busy ещё не означают два
права управления. Split-brain лидерства учитывать отдельно: пока не было
конфликтующих назначений, это не наблюдённый конфликт команд. Нарушение
исключительности права — два одновременно допустимых владельца **одного**
прибора; наблюдённый конфликт команд — их пересекающиеся несовместимые
воздействия. Два разрешения могут существовать без отправленных команд;
отсутствие команд не делает такую выдачу корректной.
Разные приборы допускают параллельное управление. Unknown/ошибка отопления
не превращаются автоматически ни в конфликт, ни в безопасный эпизод.

## Известные пути конфликта

| ID | Статус | Условия и порядок событий | Результат и принятая реакция |
| --- | --- | --- | --- |
| R01 | Риск | Исполнитель читает R1; лидер продлевает seq; исполнитель публикует request со старым header. Несколько исполнителей переносят старое значение цепочкой. | Откат seq, восстановление token/FREE и ABA при наблюдении. Кандидат может ошибочно считать аренду завершённой. Точное сравнение record сохраняется, но этот класс не устраняет. |
| R02 | Риск | На фоне R01 разные лидеры в разные моменты подтверждают себя через R1, читают свободный R2 и записывают разные grants. Исполнители проверяют свой R2 и подходящий R1 в разные моменты. | Два исполнителя могут пройти проверки и начать пересекающиеся действия. Чтения/записи двух строк не составляют CAS или транзакцию; дополнительное чтение само по себе не доказывает устранения гонки. |
| R03 | Риск | После успешной проверки права grant/лидер меняется, а принятая команда ещё доставляется или исполняется. Устройство не проверяет fencing token. | Старое действие может примениться после нового назначения. Принятую команду не отменяем; локальная проверка токена не заменяет fencing ресурса. |
| R04 | Граница | GC, планировщик, сеть, серверная очередь, suspend или миграция VM увеличивают полное окно больше Delta; отправленная операция исполняется позднее. | Локальная потеря роли может случиться после изменения регистра; возможны два лидера и позднее воздействие. Роль останавливается при обнаруженной неопределённости, отправленный HTTP не отзывается. |
| R05 | Граница | Скорости часов выходят за rho, BOOTTIME после восстановления VM/снимка вне модели либо состояние процесса клонировано. | Владелец и наблюдатель расходятся в оценке срока, новый доступ может быть выдан раньше безопасного момента. Wall-clock/NTP не используются; неподдерживаемые часы не заменяются скрытым fallback. |
| R06 | Граница | Операции сервиса не линеаризуемы, чтения устарели или подтверждение/применение записи не соответствует модели регистра. | Readback может не отражать актуальное общее состояние. Линеаризуемость ZONT не доказана; успешное чтение и валидный JSON не являются её доказательством. |
| R07 | Риск | Прямой ЛК, клиент без протокола или код вне управляющего API меняет устройство/метаданные при активном grant. | Человек и алгоритм могут конфликтовать. Прямой ЛК сохранён сознательно; name-индикация не блокировка. Это не разрешение новым штатным алгоритмам обходить executor. |
| R08 | Граница | Повторно использованы owner/token/request/nonce/revision, произошла случайная коллизия или восстановлена старая идентичность процесса. | Старое подтверждение может стать неотличимым от нового. Штатный код создаёт уникальные ID/token и возрастающий seq; намеренное повторение значений новым кодом запрещено. |
| R09 | Риск | Команда принята перед expiry, но реальное воздействие длится дольше допущенного быстрого атомарного действия; другой процесс после своего безопасного ожидания начинает работу. | Внешние действия могут пересечься при корректном локальном admission. Резерв на каждую команду отвергнут владельцем. In-flight защищает локальный процесс, но не продлевает удалённый grant. |

### Воспроизводимый порядок R01/R02

1. A имеет token A, seq=2; B начал наблюдение этого header.
2. A продлевает seq=3; чужие R1 read/modify/write возвращают seq=2 и seq=3,
   каждый раз из недавнего чтения.
3. B в конце интервала опять видит seq=2, хотя продление уже было, и после
   своего барьера подтверждает захват.
4. Чужие записи чередуют A/B. B видит R1=B и FREE в R2; A позднее видит
   R1=A и ещё FREE в R2.
5. B пишет Y, исполнитель Y проверяет grant и R1=B. Затем A пишет X,
   исполнитель X проверяет grant и R1=A. Их действия пересекаются.

Каждая операция может уложиться в Delta даже при одинаковой скорости часов.
Полная шкала — [модель R1/R2](../reports/2026-10-14-two-register-coordination-review.md).
Повторное описание этого порядка не является новым замечанием к архитектуре.

Timeout после отправки не доказывает отсутствия эффекта. Неизвестный исход
записи лидера прекращает роль, но запись может примениться позже и восстановить
header/grant: это R01–R04/R06. Он не разрешает продолжать роль или повторить
запись вслепую. Для физической команды unknown также сохраняется без повтора;
следующий успешный off не доказывает автора и время прежней команды.

## Выбор, продление и передача лидерства

| ID | Статус | Сценарий | Поведение и граница |
| --- | --- | --- | --- |
| L01 | Доступность | Кандидаты читают FREE и перезаписывают token друг друга. | Нет гарантии справедливости/времени победы. До барьера и точного подтверждения роли нет. Возможные два прошедших лидера относятся к R01/R04–R08; R01 не требует выхода за Delta. |
| L02 | Доступность | Продление seq или повторные изменения header сбрасывают наблюдение. | Наблюдение начинается заново; takeover может задерживаться. Живой лидер удерживает роль только в пределах своего term. |
| L03 | Доступность | Лидер упал, замолчал, убит или остановлен. | Кандидат ждёт неизменную запись не меньше её L плюс poll/HTTP/барьер. При активном R2 дополнительно учитывает его завершение/истечение. Восстановление ровно через L не обещано. |
| L04 | Доступность | Token потерян, lease истёк либо запись/продление не подтверждены. | LeaseLost прекращает координацию и новые локальные выдачи. Сессия исполнителя не отменяется только из-за потери роли. Поздние общие записи остаются R01–R04. |
| L05 | Доступность | Достигнут предел непрерывного лидерства 20 минут с поправкой часов. | Старый token не продлевается за term_deadline. Дальше только новые выборы/token; прежний процесс может снова выиграть, справедливости нет. |
| L06 | Доступность | Новый лидер избран при действующем grant старого исполнителя. | Выборы не означают FREE в R2. Новый лидер ждёт finished либо неизменный полный grant в течение его L. Игнорирование ожидания новым кодом — регрессия. |
| L07 | Доступность | При штатном FREE потерян ack или пришла чужая R1-запись. | После отправки FREE старый лидер не координирует и не повторяет FREE вслепую. Восстановленный header — R01, поздняя запись — R04/R06. |
| L08 | Доступность | Не хватает аренды для V>=8*Delta, барьера/работы либо неверна rho. | Роль не запускается/прекращается. Ошибочный конфиг не даёт права сократить барьер или перезапустить общий 20-минутный предел продлением. |
| L09 | Доступность | R1/R2 неизвестны, повреждены/усечены, строка не вмещается, имя нормализовано/переименовано. | Отказ/unknown/readback mismatch. Неизвестное не считается FREE и не затирается. Восстановление старой валидной записи — R01/R06/R08. |
| L10 | Доступность | 429, HTTP error, большой RTT, сеть или кабинет недоступны. | Проверки права не обходятся, роль может остановиться. Unknown/потеря покрытия учитываются отдельно от конфликтов монополии. |

Fischer требует ограниченного read→write, W>K_delta*Delta и точного
подтверждения. Ожидание ровно Delta без поправки имеет контрпример, но
**не разрешено текущим контрактом**: W=2*Delta и проверки времени сохраняются.
Основание — [проверка формул](../reports/2026-10-14-fischer-lease-review.md).

## Заявки исполнителей и последствия для отопления

| ID | Статус | Сценарий | Результат и политика |
| --- | --- | --- | --- |
| A01 | Доступность | Request/heartbeat/finished потеряны при записи целой R1, несколько клиентов борются за request-строку. | Ожидание/голодание/зависшая индикация. Известную потерянную заявку повторяют по протоколу; неизвестную запись не повторяют вслепую. Нет heartbeat — не повод отозвать grant немедленно. Header replay — R01. |
| A02 | Доступность | Клиент упал после request, до получения/использования grant. | Неиспользуемый grant ждёт консервативного истечения. Старый nonce не даёт право при позднем ack; просроченная заявка не должна выдаваться заново. |
| A03 | Доступность | Ack/release потерян, наблюдается другой token/revision. | Неподходящий/неизвестный ответ права не даёт. Неподтверждённый release держит локальную reservation до expiry и конца работы без автоматического повтора. |
| A04 | Доступность | Потеряна локальная idle-сессия, в том числе из-за прерывания до возврата handle. | По заказанному lease она истекает при следующем acquire/drain. Acquisition, принятые команды и pending/running release ждём до конца; очистка не стирает чужой R2. |
| A05 | Доступность | Алгоритм запросил слишком короткую аренду; перед off/finally срок истёк. | Новый off отклонён; достаточный lease с запасом — обязанность алгоритма. Сброс может остаться включённым, но это само по себе не выдача двух монополий. |
| A06 | Граница | Kill/смерть host/потеря питания во время импульса. | Finally не гарантирован. Истечение grant восстанавливает возможность управления, а не физическое включение котла. Watchdog/журнал восстановления отвергнуты; риск принят. |
| A07 | Риск | Человек во время импульса отправляет on, затем finally алгоритма отправляет off. | Ручное вмешательство не отменяет off; редкие вмешательства контролируются человеком. Уже включённый до импульса сброс не трогается. Внешний обход — R07. |
| A08 | Доступность | API принял команду, но нагрев не восстановился/датчики ещё не отражают эффект. | API-успех не подтверждает физическое восстановление. Без признаков пересечения воздействий это не конфликт монополии. |
| A09 | Доступность | Статистика отсутствует/частична, sink неисправен. | Команды/cleanup не повторяют ради наблюдений. Partial не доказывает отсутствия конфликтов и не даёт полной эксплуатационной частоты. |

«Управление занято» может остаться после crash/потери finished или исчезнуть
при ручном переименовании. Индикация помогает человеку, но не доказывает автора
команды, исключительность доступа и блокировку других клиентов.

## Новые нарушения, которые запрещено добавлять

Это обязательные защиты, а не разрешённые исключения при низкой частоте.

| ID | Статус | Запрещённый путь | Проверка |
| --- | --- | --- | --- |
| C01 | Защищено | Команда без своей действующей session, чужая/скопированная session, другой прибор, обход gate/mutex или исключение для finally. | Нет сетевой команды; identity и expiry в точке admission, общий executor. |
| C02 | Защищено | Async request уже DENIED/отменён/истёк, а его unclaimed-session раскрывается через immediate/reuse до решения manager. | Unclaimed не раскрывается и не считается idle; issued и GRANTED атомарны; guard действует до конца in-flight/cleanup. Это новый путь плана issue #4, не принятый R01–R09. |
| C03 | Защищено | Старый ack/request/nonce/token/revision даёт новое право, GET/retry перезапускает lease, неизвестный heartbeat продлевает session. | Точные ID и исходный deadline; новый request не наследует старый ack; наблюдение не равно renew. |
| C04 | Защищено | Reservation удаляется до конца acquisition, принятой команды, первой попытки release или выполняющегося release. | Счётчики/переходы под общим lock, барьерные тесты direct/deferred release; expiry не убивает принятую работу. |
| C05 | Защищено | Shutdown закрывает транспорт до cleanup, потеря роли лидера автоматически отзывает finally исполнителя. | Ресурсы до drain; независимость роли/session; bounded close возвращает False вместо ложного успеха. |
| C06 | Защищено | Новый лидер игнорирует R2/освобождает чужой grant, исполнитель пишет R2, сокращены барьер/наблюдение. | Роли писателей, владение, полный период, K/rho и term_deadline сохраняются. |
| C07 | Защищено | Слепой повтор неизвестной записи/команды, ошибка/повреждение считаются FREE, token/seq намеренно повторены. | Безопасные ошибки, уникальность, отсутствие автоматического повтора эффекта. |
| C08 | Защищено | Новый поток/метод выдаёт право мимо единой локальной синхронизации либо перезапускает закрывающегося владельца. | Одно место выдачи, отказ новых захватов при закрытии, без обходных facade/adapters. |

Каждый новый план/PR сверяется с этими ID. Принятый класс подтверждается теми
же предпосылками и причинной цепочкой; его не переоткрывают. Новую операцию
проверяют на её новые окна гонок. Исправления сохраняют тест порядка событий.

## Частота и основания для доработки

Использовать существующую [статистику](orchestration-risk.md), не вводить ради
этого журнал восстановления/watchdog или автоматические команды:

- разделять protocol_version/profile, runtime и специально заданные контрпримеры;
- сохранять device/run/request/grant/leader term, порядок, ожидание/RTT,
  Delta breach, unknown/error и покрытие; credentials и тела API не писать;
- при разборе указывать R/L/A-ID; Busy, конфликт и неизвестность считать отдельно;
- считать эпизоды конкуренции, а не разбавлять выборку read-only poll;
- при partial/none описывать наблюдаемую часть, не объявлять 99.9% достигнутыми.

Редкий эпизод принятого класса: сохранить факты, продолжить наблюдение.
Слишком частые проявления: выбрать доработку по данным вместе с владельцем,
с воспроизводимым сценарием и раздельной статистикой до/после изменения.
Новая причина или нарушение C01–C08: исправить как регрессию, не ждать частоты
и не расширять принятую базу молчаливым добавлением строки «риск».

Редактирование реестра не запускает ZONT, выборы, алгоритмы или команды.
