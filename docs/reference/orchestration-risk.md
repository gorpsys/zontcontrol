# Допустимый риск оркестрации

19.10.2026. Реализован wire v2 в подготовленном выпуске 0.3.0:
R1=name — лидер/ответы/grants, R2=notes — запросы исполнителей.
[Точный протокол](leader-election.md),
[решения и проверка](../history/2026-10-19-monopoly-protocol-v2.md).
Решение владельца от 14.10.2026 сохраняется: собирать статистику и дорабатывать
протокол по её результатам. Условие предварительно подтвердить 99.9% заменено этим решением.
99.9% остаётся целевым ориентиром, а не достигнутой или доказанной надёжностью.
Офлайн-проверки не выполняют команд устройству. Ограниченная натурная проба
описана ниже; эксплуатационная частота нарушений по ней не установлена.

Уточнение владельца от 16.10.2026: известные сценарии зафиксированы в
[реестре отказов координации](coordination-failure-scenarios.md). Они приняты
и не переоткрывают обсуждение архитектуры. Исправлять их следует только при
слишком частом проявлении по эксплуатационной статистике. Численный порог
пока не задан. Новые пути нарушения монополии и ослабление существующих
защит запрещены; их исправляют при разработке, не ожидая накопления случаев.

Controller API v1 не меняет эту оценку: timeout/cancel/lease ограничивают
локальную выдачу и новые стадии попытки, но не отзывают уже отправленный HTTP
и не доказывают линеаризуемость ZONT. A04 остаётся принятым; C02/C03 защищают
невыданные session и исходные ID/сроки. Ранее запущенный coordinator независим
от timeout заявки. [Контракт](../agents/contracts.md#запрос-монополии-api-v1)
и уточнение реестра от 17.10.2026 описывают проверенные границы.

## Смысл критерия

В текущем обсуждении оценивается монополия управления: полный эпизод
конкуренции за разрешение, защищённые действия, cleanup и освобождение.
Нарушение — одновременно действующие конфликтующие исполнители. Чтения
датчиков и опросы без команд не увеличивают выборку безопасных эпизодов.
Правила учёта эпизодов фиксируются до теста.

Доступность учитывается отдельно: завершение запроса, потеря/зависание заявки,
ожидание и штатный отказ. Нормальный Busy сам по себе не нарушает монополию.

## Что известно

[Модель v1](../reports/2026-10-14-two-register-coordination-review.md)
показала структурный replay лидерства внутри Delta, но не его частоту в ZONT.
В v2 этот путь закрыт раздельными capabilities писателей; исторический
контрпример не является допустимой трассой v2. Сопоставление R/L/A с защитами
и остаточным риском — [реестр](coordination-failure-scenarios.md).
Атомарность/линеаризуемость строк, отсутствие первого применения записи
после timeout и пределы Delta/rho/Delta_cmd остаются допущениями. HTTP/readback
и отсутствие превышений в малой выборке их не доказывают. Freeze после guard,
нарушение модели регистра, хвост сверх Delta_cmd и прямой ЛК сохраняют риск.

Для произвольного числа клиентов и произвольного расписания численная
гарантия 99.9% не следует из протокола. Оценка требует ограниченного профиля
нагрузки и данных о задержках/отказах. Сам контрпример не определяет вероятность.

## Статистическое обоснование

Если эпизоды независимы, репрезентативны и имеют постоянную вероятность
нарушения p, при нуле наблюдаемых нарушений односторонняя верхняя граница:

```text
p_upper = 1 - alpha**(1/N)
```

| Доверие | Эпизодов без нарушений для p_upper<=0.001 |
| --- | --- |
| 95% | 2995 |
| 99% | 4603 |

Это статистическая граница при перечисленных предположениях, не абсолютная
гарантия. Зависимые опросы, повторы одного расписания и синтетические задержки
с произвольным распределением не доказывают надёжность реальной эксплуатации.

99.9% отдельного запроса не означает 99.9% эпизода. По union bound вероятность
нарушения эпизода не выше суммы вероятностей опасных событий: десять событий
с вероятностью ошибки <=0.001 дают лишь границу <=0.01. Учитываются гонки
лидерства и заявок, а не только HTTP timeout.

## Проверка и сбор статистики принятой схемы

- Задать профиль: число активных клиентов, частоту записи, сроки обеих аренд,
  Delta/rho и точный порядок проверок.
- Проверять целые окна запросов, паузы, позднее применение после timeout,
  сетевые ошибки и 429.
- Включить смену лидера при кешированном grant, future grants, конкурентные
  heartbeat/заявки, reserve после expiry/finish/cancel, память nonce и cleanup.
  Replay header v1 сохранять как исторический контрпример, late apply —
  как out_of_model fault, а не допустимое расписание модели v2.
- Разделить специально подобранные контрпримеры и статистическую выборку.
  Первая проверяет безопасность расписаний, вторая оценивает выбранную модель.
- Сначала использовать виртуальный ресурс и тестовые регистры, без команд
  котлу. Синтетическую оценку не переносить на ZONT без измерений и проверки
  временных/семантических предположений.

Данные для наблюдений: число эпизодов/попыток/выдач доступа,
время ожидания, смены лидера при активном grant, повторные и потерянные заявки,
превышения Delta, RTT, 429/timeout, результаты завершения и cleanup,
обнаруженные конфликты управления. Для сопоставления — device_id, run_id,
request_id, grant_id и идентификатор срока лидерства. Credentials не сохраняются.

Неизвестный исход и недостаток наблюдений отмечаются отдельно: отсутствие
обнаруженного нарушения не равно доказанной монополии каждого эпизода.
Нужны показатели покрытия наблюдения и условий нагрузки. По найденным
конфликтам сохраняется воспроизводимый сценарий с ID из реестра. Известный
принятый сценарий требует доработки при слишком частом проявлении, а не
автоматического пересмотра протокола после каждого случая. Новый путь ошибки
исправляется без ожидания частоты. Выборка после изменения версии
анализируется отдельно.

Наблюдения реализованы в JSONL, формат описан ниже. Это измерение,
а не возврат ранее отклонённых журналов восстановления, watchdog
или отдельного исполнителя импульсов. Набор из 2995/4603 эпизодов служит
для возможного статистического вывода, а не предварительным запретом внедрения.

## Реализованные наблюдения

application создаёт JsonlSink по statistics.path из config/controller.json;
statistics.profile маркирует профиль. Для независимых процессов задавайте
разные файлы: блокировка sink локальна процессу. JSONL — выход наблюдений,
не журнал восстановления, разрешений или состояния котла.

Обязательные поля каждой строки: schema=1, event, protocol_version, profile,
source (runtime, simulation или counterexample). Допустимые дополнительные
поля: device_id, episode_id, run_id, request_id, grant_id, leader_term,
revision; wait_s, rtt_s, delta_s, elapsed_s; outcome, coverage и phase
(command, session или metadata).
Wire v2 маркируется protocol_version; schema JSONL остаётся 1.
Добавлены role/stage/window_id, read_write_s, sync_window_s, freeze_gap_s,
exceeded и BOOTTIME границы started_at/finished_at/expected_resume_at.
Для команды — command_observation_id (UUID), clock_id, admitted_at,
api_response_at; допускаются sample_kind и completion_basis для офлайн-образцов.
outcome: success, unknown, conflict, failure, busy;
coverage: complete, partial, none. Строка ограничена 4096 символами, текстовые
метки и поля проходят allowlist; credentials и произвольные тела API не пишутся.

События включают episode_started/episode_finished, attempt/poll, request,
request_repeated/request_lost, grant/grant_ack, heartbeat/finished,
leader_attempt, leader_acquired, leader_renewed, leader_lost, leader_released,
leader_changed_active_grant,
delta_breach, rtt, rate_limited, timeout, error, cleanup, conflict, command.
CommandExecutor записывает исход каждой команды собственной сессии,
включая отказ допуска, явную ошибку API и неизвестный исход без повтора.
Для выключения toggle_buttons дополнительно пишет cleanup с phase=command:
это включает off из finally, но само по себе не определяет назначение
переключателя. При release после всех in-flight пишет cleanup с phase=session
и итогом команд сессии (unknown сохраняется даже после успешного off).
GrantCoordinator пишет cleanup с phase=metadata при удалении завершённого
резерва из R1 и продвижении слотов; notes/R2 он не пишет.
Эти события содержат идентификаторы исходных request/grant и срока лидера;
их coverage остаётся partial, физическое восстановление не подтверждается.
Отдельное событие или poll не объявляется успешно защищённым эпизодом.
Ошибки sink изолируются от исполнения команд и finally; они означают
потерянное покрытие наблюдений, а не повод повторить управление.

Офлайн-анализ через zontcontrol.coordination.statistics:

```python
from zontcontrol.coordination.statistics import analyze, read_jsonl

with open("reports/orchestration.jsonl", encoding="utf-8") as stream:
    report = analyze(read_jsonl(stream))
print(report)
```

read_jsonl отклоняет повреждённые/обрезанные/длинные строки безопасной ошибкой
с номером строки. analyze группирует по protocol_version/profile/source,
считает события, полные/частичные эпизоды, исходы и count/total/max wait_s/rtt_s.
Полный эпизод требует ровно одной начальной и конечной границы и явного
coverage=complete; неполное покрытие, timeout/unknown остаются unknown.
Наблюдаемый conflict сохраняется даже при частичном покрытии.

Runtime-записи выдачи/освобождения grant сами не наблюдают исключительность
всех физических команд. Текущий runtime помечает такое покрытие partial;
полнота требует независимого наблюдателя ресурса (в тестах — oracle).
Симуляции и специально подобранные контрпримеры анализируются отдельно;
анализатор не вычисляет процент надёжности, p_upper или доказанность 99.9%.
Оценки по независимой репрезентативной выборке остаются дальнейшей работой.

## Измерения времени и физического воздействия

sync_started/sync_read/sync_write_started/sync_write/sync_confirmation/sync_window и freeze
измеряют исходное полное окно, а не только один RTT. read_write_s отделено
от sync_window_s с подтверждающим READ; намеренный W не является freeze.
sync_write_started отмечает отправку, read_write_s заканчивается ответом WRITE.
При unknown сохраняется нижняя граница, без completion percentile. Старые
sync_write без outcome измеряли только начало отправки: ответ WRITE по ним
недоступен, анализатор сохраняет исходные значения как цензурированные.
Анализ по версии/профилю/источнику/прибору/стадии сохраняет count, max,
nearest-rank p99/p99.9, превышения и незавершённые окна. Цензурированные
elapsed не становятся completion percentile, потерянный образец — unknown.
Границы окна охватывают первый READ, bootstrap и отдельные чтения; вложенный
store не завершает измерение раньше владельца полного окна. Ошибка первого
READ сохраняет elapsed как цензурированную нижнюю границу. В старых данных
окно, имеющее только freeze/read без границ, остаётся incomplete/unknown;
его отсутствующую длительность восстановить нельзя.

command_started/command_finished фиксируют последний admission и API-ответ;
admitted_at взят тем же чтением BOOTTIME, что допуск. Это не physical_completion.
Офлайн scripts/analyze_command_effects.py различает critical_section, command,
residual_effect. Цикл CLI — одна команда, reset — весь on→ожидание→finally off;
границы задаёт алгоритм. У хвоста проверяются UUID команды, BOOTTIME-домен и
исходный admission. API RTT, readback уставки и длительность reset ≈40 с не
заменяют независимое наблюдение остаточного воздействия. Без него хвост unknown;
обязательного датчика/callback или сервиса операций не требуется.

Рекомендация Delta — max(5,10*p99.9,1.2*max_observed). Для Delta_cmd формула
применяется только к достоверным верхним оценкам хвоста от admission, включая
паузу до send. Рядом указываются sample count, timeout/unknown/превышения;
при неполных данных рекомендация incomplete. Это запас, не доказанный максимум.
Изменение безопасности — вручную общим новым профилем и согласованным A→B
с полным previous_profile; независимой автоподстройки клиентов нет.

Ранжирование: success_rate, successful_wait_p99, HTTP count, числовой кортеж.
