# Реакция на независимое ревью архитектуры

14.10.2026. [Ревью](2026-10-14-autonomy-architecture.md) выполнено отдельным
субагентом как холодным читателем первого проекта, без истории обсуждения.
Исходный отчёт сохранён; его номера строк относятся к первому проекту.
[Архитектура](../agents/architecture.md) уточнена автором после получения
находок. Это изменения договорённостей; код и реальные устройства не менялись.

## Замечания и решения

| № | Реакция | Статус |
| --- | --- | --- |
| 1. continuous против once | По решению владельца dual-mode по умолчанию не стартует постоянно; start запускает его явно, autostart_dual_mode=true меняет умолчание. При работающем continuous разовый вызов даёт Busy/already_running_continuous. Continuous-only по-прежнему стартует сразу | Закрыто решением владельца, §3/§4/§6 |
| 2. Полномочия эффектов | По решению владельца общий preview/execute не вводится. Предпросмотр — возможность конкретного потребителя; boiler_reset при подтверждении аномалии исполняет настоящий сброс как своё назначение | Закрыто решением владельца, предложение общего режима отклонено, §3 |
| 3. Повторные сбросы | Ответственность алгоритма: continuous ждёт 5 минут после включения котла; once отдельно повторы не учитывает, рекомендуемый интервал вызовов около 15 минут. Общий guard/счётчик/обязательное хранилище не вводятся | Закрыто решением владельца; [правила модуля](../reference/boiler-reset.md) |
| 4. Живучесть off | Сам boiler_reset в finally немедленно выключает сброс при штатной остановке/исключениях. Журналы, watchdog и независимый исполнитель не нужны; kill/смерть host вне гарантии | Закрыто решением владельца, §5/§8 и правила модуля |
| 5. Deadline/очередь | Принятая от владельца монополии команда исполняется независимо от последующего timeout/stop алгоритма. Проверки активности запуска и особое разрешение для finally не вводятся | Закрыто решением владельца, §3/§5; допуск уточнён решением №6 |
| 6. Несколько host | Для нескольких host принята схема R1/R2: Fischer + lease для лидера, запросы/heartbeat в R1, разрешения только лидером в R2 и проверки роли/grant. L по ожидаемой работе, общий срок максимум 20 минут. Известные риски приняты со сбором статистики и доработками | Закрыто решением владельца с принятием риска; 99.9% пока не подтверждено, §3 и [учёт](../reference/orchestration-risk.md) |
| 7. Прямой ЛК | Прямое управление сохраняется. По решению владельца от 15.10.2026 редкие вмешательства контролируются человеком, риск принят; активный grant индицируется в ЛК. Ручные команды не отменяют off из finally; уже включённый до импульса сброс не трогается | Закрыто решением владельца с принятием риска, §8 |
| 8. DI через IPC | По решению владельца от 15.10.2026 один процесс с потоками и обычным DI. Регистратор обеспечивает таймаут результата и сигнал отмены; завершение кооперативное. stopping/монополия сохраняются до finally; зависший поток принудительно не убивается | Закрыто решением владельца, §4/§5; IPC и процессы алгоритмов сняты |
| 9. accepted/completed | Сервис pulse/ticket/get_operation снят. По решению владельца от 15.10.2026 обычные команды синхронные: успех API, явная ошибка, неизвестный результат после отправки. Нет автоматических повторов и обязательного мониторинга; успех сброса не доказывает нагрев | Закрыто решением владельца, §2 |
| 10. Пригодность и смена параметров | По решению владельца история позволяет принять решение существующим детектором. Его правила сохраняются; дополнительный архитектурный допуск и отзыв/пересчёт из-за ручных изменений не вводятся. Человек контролирует вмешательство и принимает риск | Закрыто решением владельца, §7; предложение инвалидизации снято |

Эти статусы означают исправление текста или явную границу будущего решения,
не доказательство корректности ещё отсутствующей реализации.
Решения владельца приняты по всем №1–10. Последовательный разбор завершён;
прежние предложения и контрпримеры сохранены как основания решений,
не как открытые требования вопреки принятым договорённостям.

### Уточнение владельца по замечанию №1

В последовательном разборе замечаний владелец выбрал понятную ошибку
разового запуска при уже работающем постоянном и отсутствие автозапуска
continuous по умолчанию у dual-mode. Явный start либо настройка регистратора
включают постоянный запуск. Первоначальная рекомендация автора с отдельными
host-профилями для этого поведения заменена этим правилом; исходное
независимое ревью сохранено как историческая оценка первого проекта.

### Уточнение владельца по замечанию №2

Сброс котла — ожидаемое назначение разрабатываемого алгоритма. Запуск
boiler_reset предполагает его реальное исполнение при подтверждённой
аномалии, без обязательного общего переключателя preview/execute.
Предпросмотр и тестовые режимы относятся к внутренней реализации
конкретного потребителя. Регистратор управляет его жизненным циклом,
а управляющий API предоставляет чтение и исполнение команд. Технические
проверки команды и таймауты сохраняются; дополнительный диалог или флаг
разрешения штатного сброса не вводятся. Прежнее предложение автора о
глобальном режиме снято. Текущий ручной CLI с --execute не меняется.

### Уточнение владельца по замечанию №3

Политика повторных проверок — зона ответственности boiler_reset, не общей
архитектуры. В continuous после включения котла (выключения сброса) действует
пауза 5 минут. В once специальный учёт повторных попыток не нужен: по расчёту
владельца такие вызовы целесообразны примерно раз в 15 минут.
Модуль once не ждёт ещё 5 минут после импульса; расписание задаётся снаружи.
Прежние предложения о guard, ручном перевооружении и обязательном хранилище
сняты. [Правила модуля](../reference/boiler-reset.md) записаны отдельно.

### Уточнение владельца по замечанию №4

finally подходит для требуемой границы: штатной остановки и исключений.
Он немедленно выключает сброс и включает котёл, без ожидания остатка
40 секунд. Журналы, независимые исполнители, watchdog и восстановление
после kill/смерти host не нужны. Вызовы API для finally остаются доступны
при корректном завершении. Сам регистратор по-прежнему обеспечивает таймаут;
время завершения worker не превращается в произвольное продление результата.

Из архитектуры сняты API составного фонового pulse, tickets и восстановление
операций после crash: алгоритм сам вызывает обычные команды в try/finally.
Исходное ревью сохранено как оценка более сильной гарантии первого проекта.

### Уточнение владельца по замечанию №5

Команда, отправленная алгоритмом управляющему модулю, всегда исполняется.
Последующим решением №6 уточнён допуск: без своей монополии на прибор
команда отклоняется, правило исполнения относится к принятым командам владельца.
Последующий таймаут/остановка не аннулируют её в очереди и не требуют повторной
проверки активности запуска перед отправкой. Проверка/отзыв контекста как
механизм допуска команд снимаются. Для finally используется обычный API,
отдельное разрешение не нужно. Регистратор по-прежнему ограничивает время
самого алгоритма и возвращает ошибку по таймауту; API-ошибки и технические
проверки команды сохраняются. Это решение о судьбе отправленной команды,
а не обещание физического успеха при недоступности ZONT.

### Уточнение владельца по замечанию №6

Исполнитель требует явного получения монополии на управляющие воздействия
в конкретное устройство по принципу мьютекса. Только один алгоритм может
управлять одним устройством в данный момент; разные алгоритмы могут управлять
разными устройствами одновременно. Вне собственной монополии все управляющие
воздействия завершаются ошибкой до обращения к ZONT. Чтения не блокируются.
Импульс сброса удерживает монополию до off из finally; пауза 5 минут её не держит.

Проведено [исследование опубликованного API](../reports/2026-10-14-zont-control-lock-api.md).
Штатный mutex/lease/CAS и произвольный флаг аккаунта не найдены. Состояние
переключателя потенциально читается другими клиентами, но не даёт атомарного
захвата; безвредный отдельный переключатель на SMART 2.0 не проверен.
Возможность notes у существующего прибора также не установлена.

Позднее отдельные [натурные тесты notes](../reports/2026-10-14-zont-notes-live-probe.md)
подтвердили второе читаемое/изменяемое поле. Это расширяет возможности
согласительных маркеров, но само по себе не даёт атомарной блокировки.

Общий исполнитель обеспечивает монополию своим потребителям. Несколько
независимых исполнителей и прямой ЛК локальный мьютекс не охватывает.
Для первых нужен общий исполнитель либо подтверждённая общая синхронизация;
backend пока не выбран. Поэтому исходный риск нескольких writers явно
ограничен областью гарантии, а не объявлен решённым флагом ZONT.
Журналы/watchdog, снятые по №4, не возвращаются. Код и устройства не менялись.

Последующее решение владельца выбирает [условный Fischer + lease](../reference/leader-election.md)
для роли лидера, с переменной арендой и общим пределом 20 минут. Приняты
поправки временного барьера, окон can_coordinate и наблюдения неизменного
record. Выбор лидера отделён от монополии алгоритма, поэтому не отменяет
его finally. Механизм выдачи и передачи активного доступа через вторую
строку ещё требует отдельного контракта и проверки.

Окончательное решение владельца по текущему замечанию: принимается текущая
схема R1/R2 с оговоркой о сборе статистики и доработках на её основе.
Требование сначала обосновать 99.9% больше не блокирует принятие. Порог
остаётся ориентиром; неизвестная вероятность и контрпримеры не объявлены
устранёнными. Замечание №6 закрыто этим решением. Контракты лидерства и
учёта обновлены; код и котёл при записи решения не менялись.

### Уточнение владельца по замечанию №7, 15.10.2026

Ручные вмешательства через ЛК редки, контролируются человеком, который может
исправить результат и принимает риск. По №6 в ЛК предусматривается индикация
занятого управления; она помогает принять решение о вмешательстве, но не
блокирует команды ЛК.

Согласованное завершение автоматического импульса сохраняется: после попытки
on finally пытается отправить off, включая неизвестный исход on; ручная команда
во время импульса его не отменяет. Уже включённый перед импульсом сброс
остаётся намеренным отключением и не трогается. Не вводятся определение
автора по повторному чтению, запрет ЛК или дополнительное разрешение cleanup.
Замечание №7 закрыто принятием риска. Изменена документация, код не менялся.

### Уточнение владельца по замечанию №8, 15.10.2026

Владелец принимает один процесс с потоками алгоритмов. Исходное требование
к таймауту — регистратор возвращает ошибку по собственному таймеру; более
сильное требование принудительно остановить произвольный код снимается.
Фабрика получает обычные Python-зависимости через DI, управляющий фасад
обеспечивает потокобезопасность и монополию. Отдельные процессы, IPC и
межпроцессный прокси не нужны.

Отмена кооперативная, ожидания прерываются сигналом, HTTP имеет таймауты.
После TimeoutError поток может ещё выполнять finally; состояние stopping
и монополия сохраняются, повторный запуск запрещён до завершения. Зависший
поток нельзя безопасно убить отдельно от приложения, он может удерживать
доступ и мешать завершению; эта граница принята. Уже принятые команды не
отзываются. Замечание №8 закрыто; код и устройство не менялись.

### Уточнение владельца по замечанию №9, 15.10.2026

Владелец принимает обычные синхронные команды с тремя различимыми исходами:
успешный ответ API, явная ошибка/отклонение и неизвестный результат после
отправки при timeout/обрыве. Ошибки до отправки не подменяются неизвестным
исполнением. Управляющие команды автоматически не повторяются.

Успех API не доказывает физического результата. В частности, восстановление
нагрева после сброса оценивается по дальнейшим показаниям. Дополнительное
чтение возможно, обязательный мониторинг каждой команды не требуется.
Сервисы фоновых операций, tickets и operation_id не возвращаются.
Timeout самого алгоритма остаётся отдельным исходом регистратора и не
отменяет уже принятые команды. Замечание №9 закрыто; код не менялся.

### Уточнение владельца по замечанию №10, 15.10.2026

Наличие истории означает возможность принятия решения действующим
детектором. Новые ограничения истории, отдельная проверка актуальности
подготовленного решения и обязательный пересчёт из-за ручной смены условий
не требуются. Пользователь, вмешиваясь, знает, что и как делать, и принимает
риск. Предложение автора об автоматической инвалидизации снято.

Правила ранее откалиброванного детектора и его unknown не меняются;
регистратор/управляющий фасад не анализируют температуры. Проверки монополии,
online, возможностей команды и уже включённого сброса до импульса сохраняются.
Замечание №10 закрыто, все десять пунктов разобраны. Код и пороги не менялись.

## Оправданность конструкции

Управляющий фасад нужен для одного API нескольким независимым потребителям.
Каталог и прямой DI дают одну точку подключения без service locator.
Один процесс с потоками выбран владельцем по №8: внешнего таймера результата
и кооперативной отмены достаточно для согласованного контракта. Потоковый
timeout не объявляется принудительной остановкой кода или изоляцией процесса.
Для согласованного импульса достаточно обычных команд и finally самого
алгоритма. Отдельный исполнитель/журнал после выбора границы гарантии №4
не вводятся. Решение №5 отделяет таймаут алгоритма от исполнения команды;
DI остаётся обычной передачей интерфейса в том же процессе, IPC не вводится.

Следует начать с небольшого числа модулей внутри одного проекта, простого
локального взаимодействия. Не требуются event bus,
DI-фреймворк, произвольные plugins, десять пустых пакетов или распределённые
writers. CLI остаётся continuous-потребителем согласно требованию владельца,
но его UI/рендерер отделены от бизнес-детекторов.

## Альтернативы и границы

1. Один процесс с потоками выбран владельцем по №8. Он подходит для
   доверенных кооперативных алгоритмов и таймаута результата; принудительное
   завершение произвольного зависшего потока не входит в гарантии.
2. Один host с процессами и локальным executor дешевле эксплуатации;
   подходит для локальных проверок. Он не гарантирует выключение при смерти
   самого host, даже если файл журнала сохранён.
3. Процессы потребителей и независимый executor с durable журналом рассмотрены
   ревью, но отклонены владельцем по №4 как ненужные для выбранной гарантии.
4. Несколько writers функций с общей базой/CAS масштабируют выполнение,
   но добавляют распределённое владение и неопределённые исходы без fencing
   ZONT. Для одного котла сложность не оправдана.
5. Аппаратный импульс с проверенным автовозвратом может существенно упростить
   пункт 3 и пережить потерю связи. Поддержка текущим устройством не доказана,
   поэтому этот вариант не объявлен доступным API.

## Итог последовательного разбора

Все замечания №1–10 закрыты решениями владельца. Часть первоначальных
предложений отклонена, границы гарантий и известные риски приняты явно.
Закрытие ревью не означает написанного кода или доказанной надёжности R1/R2.

При этом формирование управляющего API, регистратора, тестов с подставным API
и UI следует согласованным решениям и может
реализовываться отдельным этапом после запроса на код.
