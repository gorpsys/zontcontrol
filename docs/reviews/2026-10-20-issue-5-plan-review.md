# Холодное ревью плана issue #5

Проверен [план предметного входа](../plans/completed/20261020120717-typed-heating-input-implementation-plan.md)
на коде master 9f157f8. Отдельный субагент получил только код, план и
документацию, без контекста переписки и GitHub. Исходные ignored reports
не читал, API/управление и WunderReview не запускал.

Результат: три P2, P1 нет. Замечания применимы к текущему тексту плана;
перед реализацией нужны уточнения. Сам план этим ревью не изменён.

После обсуждения с владельцем план уточнён: старые потери качества и точности
исследовательского loader не исправляются; меняется только нужный формат.
Различие отсутствующего и существующего пустого reset сохраняется явно.
Сортировка и выбор субсекундных измерений остаются предметом обсуждения;
первоначальное замечание о порядке не следует считать закрытым.

Последующее решение владельца: точная сортировка, минутная сетка и линейная
интерполяция фактических температур. Порядок больше не требует сохранения
ошибочного целосекундного поведения; план обновлён. Затем согласованы предел
пары 120 секунд и дополнительная минута исходной истории без переноса старой
температуры: запрос 46 минут для прежнего прогона 45 минут, конец сетки может
отставать на одну минуту от текущей расчётной минуты. Пропуски не удаляются
ради числа точек. Старый baseline служит
сравнением политик, полное совпадение решений при нормализации не обещается.

## 1. Исследовательский путь теряет данные до предметного адаптера

План, строки 28, 69 и 290: сохранить исходные времена, quality и метаданные,
при этом строить HeatingHistory непосредственно из объединённого series.

В [scripts/analyze_3weeks.py](../../scripts/analyze_3weeks.py), load_series
(строки 32/38/41), остаются только пары (epoch(time), value). Функция epoch
(строки 18–19) уже отбрасывает дробную часть секунды. Quality/source/unit/kind
также не попадают в series. Новый from_archive_packet этот путь не обслуживает.
Из такого series невозможно восстановить утраченное; архив с явным плохим
quality даст разные вычислительные данные через два входных пути.

Нужно явно определить получение семи предметных рядов до этой потери и
перечислить изменения загрузки. Отделить новый путь от сохранённого frames,
который используется существующим ускоренным replay. Альтернатива — явно
ограничить гарантии исследовательского пути и согласовать исключение.

## 2. Сортировка точных дат меняет прежний секундный lookup

План, строки 80 и 132–133: сортировать архивные точки по точному measured_at.
Строки 144–146 одновременно требуют сохранить прежнюю секундную проекцию.

В [monitor.py](../../zontcontrol/monitor.py), строка 42, сортировка стабильная
по int(timestamp). Различающиеся дробные даты внутри одной секунды сохраняют
исходный порядок. Предварительная сортировка по точному datetime меняет его.

Читатель подтвердил на синтетических данных: исходные точки
00:00:00.9 → 21, затем 00:00:00.1 → 22 дают прежнее минутное значение 22,
после точной сортировки — 21. HTTP и управление не используются.

Нужно выбрать правило для этой ситуации, согласованное с порядком points
в HeatingSeries. Либо воспроизвести старое поведение, либо явно согласовать
изменение. До перехода добавить именно такой characterization case;
тест одинаковых timestamps не покрывает разные даты в одной секунде.

## 3. Пустой reset в heating_window не имеет однозначного отображения

План, строка 86: None означает отсутствующий ряд, пустой HeatingSeries —
существующий пустой. Строка 290 требует брать семь рядов напрямую из series,
но не определяет результат пустого среза reset.

В [validate_one_shot.py](../../scripts/validate_one_shot.py), history_window,
строка 94, web_element не создаётся, если срез reset пуст. Поэтому прежний
monitor возвращает reset_history_available=False (строка 123). Читатель
подтвердил этот результат синтетически. Новый HeatingSeries(points=())
изменит полный результат даже при сохранении state=unknown.

Нужно явно задать: пустой выбранный срез reset в heating_window → None.
При этом явно существующий пустой reset из archive packet или Controller DTO
остаётся пустым HeatingSeries. Проверить оба случая полными результатами.

## Необязательная рекомендация

Уточнить manifest baseline (план, строка 198). При использовании load_dataset
входами являются также reports/profile-prior-2months.json и
reports/anomalies-3w.json: они определяют период и разметку в
[recalibrate_archive.py](../../scripts/recalibrate_archive.py), строки 49 и 67.
Их и оба manifest следует явно включить в список хешей либо однозначно
указать замороженный validation report как источник периода/разметки.

## Что проверено без замечаний

Полные expected снимаются существующим monitor до перехода, а не новым
кодом. Отбор 704 времён соответствует validate_recalibration; прежняя
проверка сравнивала только state, план усиливает её до полного результата.
Переход четырёх исследовательских потребителей предусмотрен атомарно;
обязательных причин красных тестов между этапами не найдено. Лишних
Protocol/factory/registry план не вводит.
