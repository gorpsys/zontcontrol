## Подтверждённое замечание

### P2. Установленный CLI обойдёт настройку локального логгера

В плане, Task 1, Files (строка 292 на момент ревью), настройка local logger
помещена в zontcontrol/__main__.py. Но установленная команда zontcontrol
направлена непосредственно в zontcontrol.application:main —
[pyproject.toml](../../pyproject.toml), project.scripts. __main__.py выполняется
при python -m zontcontrol и только делегирует main.

При буквальной реализации плана установленная команда не настроит текстовый
logger и не обеспечит вывод новых INFO-событий BoilerReset.

Минимальное исправление плана: вызывать configure_local_logging() в
application.main, без настройки при импорте или create_application.
Предусмотреть проверку обоих входов: console script и python -m zontcontrol.

Проверка основным агентом: подтверждено по pyproject.toml:14,
zontcontrol/__main__.py:1–3 и плану:291–292. Применимо к этой задаче,
поскольку локальное и облачное логирование входят в её требования.

## Существенный открытый вопрос

### Создание таймера до первой версии функции

План (строки 256–259 на момент ревью) требует создать таймер с $latest на
функцию без единой версии и затем поставить его на паузу. Это исключает
обращения к ZONT между create и pause, но возможность такого создания
не подтверждена.

[Официальная инструкция timer-create](https://yandex.cloud/ru/docs/functions/operations/trigger/timer-create#before-you-begin)
перечисляет создание версии функции среди предварительных шагов.
Справка CLI доказывает синтаксис команды, но не допустимость цели без версии.
Это не доказательство того, что API обязательно откажет.

Рекомендация: явно обозначить эту предпосылку и запасной порядок действий
при отказе. Возможный вариант для согласования — no-op bootstrap-версия
без доступа к ZONT, затем timer → pause → полная версия. Этот вариант не
считается принятым решением по результатам ревью.

Проверка основным агентом: предварительное условие в официальной инструкции
подтверждено. Реальный create не выполнялся; вывод ограничен пробелом плана,
а не заявлением о наблюдаемом отказе сервиса.

## Область проверки и результат

Других подтверждённых P1/P2/P3 читатель не нашёл. Проверены:

- Минимальный ZIP и фактические импорты с учётом запланированного builtin_specs.
- Жизненный цикл once, результат, ошибки и ожидание finally перед закрытием.
- Локальный и облачный logger, безопасные сообщения и повторная настройка.
- Происхождение checks/SHA, gate перед OIDC, полномочия и параметры workflow.
- Первая публикация и сохранение настроек при последующих публикациях.
- IAM, Lockbox metadata, timer v2, отключение повторов и порядок активации.
- Тесты, документация и критерии облачной приёмки.

Реальных yc/ZONT-запросов, изменений ресурсов или запусков WunderReview
не было. Ограничения жёсткого завершения и одновременного управления,
явно принятые в постановке, не переоткрывались. План в рамках этого ревью
не исправлялся; отчёт фиксирует результат для следующего решения владельца.

## Решение владельца и правки плана

После ревью владелец принял P2 и поручил перенести создание таймера на момент
после первого успешного деплоя. План и справочник команд обновлены:

- Локальный logger настраивается в application.main; предусмотрены проверки
  обоих входов CLI и отсутствия настройки при библиотечном использовании.
- Таймер до успешного первого deploy отсутствует. Его создание после проверки
  версии отдельно подтверждается как включение плановых реальных сбросов.
  Предварительные pause/resume и no-op bootstrap не требуются.

Оба пункта этого ревью учтены в плане. Это не означает реализацию кода,
создание ресурсов или новую независимую итерацию ревью.
