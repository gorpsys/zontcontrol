# Независимое ревью архитектуры автономных модулей

> Историческое ревью: исходная запись 14.10.2026, последующие решения указаны ниже.
> Упомянутые требования координации отменены
> [решением от 20.10.2026](../history/2026-10-20-remove-synchronization.md);
> действующая [архитектура](../agents/architecture.md) хранится отдельно.
> Первоначальные вердикты и принятые риски сохранены; это не список нынешних нерешённых проблем.

Дата: 14.10.2026. Это независимое ревью первого проекта
[архитектурного текста](../agents/architecture.md), до исправлений автора по
результатам ревью. Проверены локальные инструкции, действующие
[контракты](../agents/contracts.md), [детектор](../reference/anomaly-detection.md)
и [контракт деплоя](../agents/deployment.md). Код и реальные устройства не
проверялись; архитектура ещё не реализована. Номера строк ниже относятся к
первому проекту, последующие правки могут их сдвинуть.

Требования владельца приняты как исходные: фиксированный управляющий API,
несколько приборов одного ЛК, независимые потребители, единый регистратор с
DI, принудительный timeout для once, автозапуск зарегистрированного
continuous, stop/start, отключаемые модули, оба режима сброса и постоянный
CLI. Запрос зафиксировать архитектуру не разрешает запуск управления сейчас.

## Находки по важности

### 1. Высокая: регистрация автоматически делает once недоступным

Источник: [§4](../agents/architecture.md), строки
152–153 и 170–172; [§10](../agents/architecture.md),
строки 397–400.

`register_all` запускает каждый валидный continuous сразу. `boiler_reset`
поддерживает оба режима, а его once при работающем continuous получает
`Busy`. Следовательно, обычная регистрация перед облачным once поднимает
бесконечный worker и блокирует нужный once. `disabled_modules` запрещает
модуль целиком и не решает выбор режима. Это противоречие именно в
публичном жизненном цикле, а не вопрос предпочтений реализации.

Исправление: явно выбрать профиль host при создании регистратора. В
`once-host` регистрируются once-возможности без запуска continuous; в
`continuous-host` регистрация continuous сохраняет обязательный автозапуск.
Запрет модуля остаётся независимым от выбора режима. Альтернатива —
`register_all(catalog, mode=...)`; проще интерфейс, но больше возможностей
случайно смешать режимы внутри одного host. Рекомендуется профиль host и
приёмка «регистрация once-host → run_once → никакого continuous worker».

### 2. Высокая: отсутствует явная граница разрешения эффектов

Источник: [§4](../agents/architecture.md), строки
149–153; [§6](../agents/architecture.md),
строки 222–247; [§7](../agents/architecture.md),
строки 275–283. Требование предпросмотра: AGENTS.md, пункт 2;
[контракты команд](../agents/contracts.md), строки 46–48.

Пустой `disabled_modules` и корректная конфигурация фактически включают
действующий сброс при регистрации. Текст упоминает полномочия, но не
фиксирует, кто и каким явным действием разрешил execute. Это создаёт
нежелательное управление после установки, добавления модуля в каталог
или запуска host ради просмотра данных.

Исправление: определить полномочия host/controller `preview` и `execute`,
по умолчанию `preview`. В execute автономный `boiler_reset` выполняет
разрешённый импульс после подтверждения детектора без диалога на каждом
сбросе: это соответствует заданной владельцем автономности. Регистрация,
наличие элемента и возможность действия не повышают полномочия. В preview
нужно определить результат проверки и предпросмотра импульса без
переключения. Раздельный флаг каждого модуля точнее, но сложнее и допускает
расхождение нескольких флагов; для первого этапа рекомендуется единая
граница host с ограниченным набором устройств и действий.

### 3. Высокая: лимит попыток не определён через действительный эпизод

Источник: [§7](../agents/architecture.md),
строки 291–299. Действующий детектор:
[§2](../reference/anomaly-detection.md#2-пригодность-данных), строки 27–32;
[§7](../reference/anomaly-detection.md#7-предупреждение-и-подтверждение),
строки 85–87; [§8](../reference/anomaly-detection.md#8-итог-разового-запроса),
строки 91–98.

«Один импульс на непрерывный подтверждённый эпизод» не является готовым
ограничителем. Собственный сброс прекращает сегмент детектора и даёт
`suppressed`; разрыв данных также очищает наблюдение. Затем прежний
неустранённый отказ может образовать новый confirmed-сегмент. Начало сегмента
восстанавливается из скользящих 45 минут и тоже не является стабильным ID.
`normal`, снижение worktime или отсутствие запроса не доказывают ремонта.
Наивное использование этих состояний повторно разрешит сброс.

Исправление: оставить детектор разовым и чистым, а исполнительную блокировку
попытки хранить отдельно. Зафиксировать ключ физического котла/сброса,
атомарное резервирование попытки до on, трактовку неизвестного исхода,
правило сохранения блокировки через `unknown`, `suppressed`, перезапуски и
скользящее окно. Реальное восстановление должно иметь самостоятельный
измеримый критерий; существующие диагностические поля нельзя объявить таким
критерием без проверки. Минимальный консервативный вариант — после одной
возможной отправки on разрешать повтор лишь явным решением владельца.
Автоматическое повторное разрешение по измеренному отклику удобнее, но
требует отдельной политики и проверки на историях; это блокер автоуправления,
а не повод менять калиброванные пороги детектора.

### 4. Высокая: durable cleanup описан как обязательство без выбранного исполнителя

Источник: [§5](../agents/architecture.md),
строки 203–209; [§8](../agents/architecture.md),
строки 308–337.

Проект признаёт незакрытый watchdog и не обещает гарантию при
недоступном оборудовании. Однако последовательность импульса уже требует
сохранить обязательство до on и выключить после смерти worker/host.
Отдельный worker того же host решает только смерть алгоритма. Запись на
диске сама по себе не выполняет off, а смерть host между принятием on и
записью подтверждения требует восстановления по заранее сохранённой записи.
«Небольшой служебный предел cleanup worker» также неоднозначен: если это
исполнитель off, его завершение может оборвать обязательство. Таймаут
остановки алгоритма и срок жизни обязательства off должны быть разными.

Исправление: до execute выбрать конкретный механизм, место durable записи,
кто восстанавливает её при старте, условие передачи обязательства при close
и поведение после ошибки off. Проекту нужны состояния принятия и исполнения
операции, а не только общий `uncertain`.

Аппаратный импульс/автовозврат, если действительно поддерживается, лучше
переживает потерю связи; его нельзя предполагать без документации устройства.
Независимый долгоживущий исполнитель с журналом работает с текущим API, но
добавляет эксплуатацию и всё равно не гарантирует off при недоступном ZONT.
Один host с локальным журналом дешевле, однако до его восстановления котёл
может остаться отключённым. Рекомендация: выбрать проверенную аппаратную
возможность либо независимого исполнителя; до выбора разрешать preview.

### 5. Высокая: запрет эффектов после deadline нуждается в точке принятия команды

Источник: [§3](../agents/architecture.md),
строки 110–119; [§5](../agents/architecture.md),
строки 195–209; [§11](../agents/architecture.md),
строки 414–415.

Отзываемый контекст и принудительное завершение процесса оправданы. Но
проверка контекста при входе в прокси недостаточна: запрос может провести
время в очереди, пережить отзыв и только затем начать HTTP. Параллельные
проверка deadline и отзыв также образуют гонку. Уже начатый до deadline
запрос может физически сработать позже; это сам текст правильно признаёт,
поэтому буквальное «нет новых эффектов после отзыва» слишком сильно.

Исправление: определить атомарную точку принятия внешней команды у
исполнителя, повторную проверку run context после очереди и непосредственно
до начала отправки. Обещать отсутствие новых принятых команд после отзыва,
а не отмену позднего физического эффекта начатого запроса. Cleanup уже
принятого импульса должен иметь отдельные полномочия, не отозванный контекст
алгоритма. Все ожидания очереди и IPC расходуют остаток бюджета. Проверка
в worker проще, но не защищает при зависании/смерти worker; рекомендуется
единый контролируемый шлюз эффектов у исполнителя.

### 6. Высокая: облачные once и несколько host обходят локальное владение

Источник: [§3](../agents/architecture.md),
строки 123–127; [§7](../agents/architecture.md),
строки 296–297; [§10](../agents/architecture.md),
строки 397–403.

Единственный исполнитель одного приложения может сериализовать своих
потребителей. Несколько вызовов функции, два локальных процесса и локальный
host одновременно с облаком уже имеют разные управляющие экземпляры.
Привязка «один ЛК на экземпляр» не создаёт общей блокировки. Сохранение состояния
после перезапуска worker ещё не означает, что оно сохранится при новом вызове функции.
Возможны два on и две независимые записи попытки.

Исправление: объявить одного авторитетного исполнителя на управляемую
физическую систему. Облачные once направляют команды туда, либо владеют
общей durable записью с атомарным захватом и восстановлением. Поскольку API
ZONT не заявлен как поддерживающий fencing, одно истечение lease не должно
автоматически разрешать нового отправителя, пока старый запрос мог остаться
в полёте. Первый вариант проще доказать, второй обеспечивает распределённое
размещение ценой значительной сложности. Для первого выпуска рекомендуется
один исполнитель, read-only облачный once до появления такой интеграции.

### 7. Высокая: прямой ЛК делает cleanup конфликтом намерений владельца

Источник: [§7](../agents/architecture.md),
строки 278–280; [§8](../agents/architecture.md),
строки 315–343.

Проверка «уже on → не трогать» защищает только перед импульсом. После on
автоматики человек может записать on через ЛК, намеренно отключая котёл.
Повтор той же записи может не породить видимого изменения, и автоматический
off отменит его намерение. После неизвестного исхода автоматического on
последующее чтение on также не доказывает владение этой записью. Текст верно
признаёт невозможность атомарности, но оставляет без решения, какой участник
имеет приоритет. Независимый watchdog этот конфликт не устраняет.

Исправление: выбрать и описать политику для активной операции, ручного off,
ручного on и неизвестного on; показать её владельцу при включении execute.
Единый маршрут команд через приложение сохраняет наблюдаемое владение,
но ограничивает использование ЛК. Сохранение прямого ЛК удобнее, но требует
явно принять, что off активной операции может отменить неразличимую ручную
запись. Аппаратная команда импульса с отдельным элементом может уменьшить
конфликт, если оборудование это поддерживает. Рекомендация: не представлять
повторное чтение состояния как подтверждение намерения и не включать
автоматический cleanup до принятия конкретной политики владельцем.

### 8. Средняя: процессы оправданы, но DI через IPC ещё не определён

Источник: [§1](../agents/architecture.md#1-состав-и-границы), строки 27–37;
[§4](../agents/architecture.md), строки 175–178;
[§5](../agents/architecture.md), строки 188–215.

Раздельные процессы соответствуют требованию ограничивать некооперативный
once и независимо останавливать continuous. Однако Python-фабрика с живым
API, часами, вводом и рендерером не является готовым межпроцессным DI:
объекты могут быть непереносимыми, содержать блокировки, TTY или транспорт.
Fork после создания транспорта также наследует его память, что расходится
с «секреты только у транспорта» в сильном прочтении. Процессный прокси означает
IPC, а значит новые точки зависания, очередь, корреляцию ответа и ошибки.

Исправление: определить запуск worker и минимальный локальный IPC-протокол:
запрос/ответ, request_id/run_id, сериализуемые DTO, пределы сообщения и
очереди, остаток deadline, разрыв канала и неизвестный исход команды.
Передавать worker прокси и безопасную конфигурацию, не controller/transport;
локальные UI/часы создавать в worker по описанию зависимости. Не превращать
IPC в отдельную сетевую платформу. Потоки/async дешевле и пригодны для
доверенного кооперативного кода, но не исполняют заданное требование
принудительного timeout; процесс здесь оправдан. Реальный антипаттерн —
замаскировать RPC под обычный DI и забыть его отказовые свойства.

### 9. Средняя: заявленный фиксированный API пока не фиксирует семантику операции

Источник: [§2](../agents/architecture.md), строки
57–65 и 91–100; [§7](../agents/architecture.md),
строки 281–283.

`pulse_switch` возвращает «результат и operation_id», но не определено,
блокируется ли он до проверенного off или возвращает принятие операции.
Если ID выдаётся только после результата, timeout может оставить caller без
ID уже исполняющегося импульса. `get_operation` ограничен «своей операцией»,
но новый worker после stop/start уже имеет другое instance_id/run_id.
Также `Busy` и `TimeoutError` используются вне списка публичных ошибок.

Исправление: зафиксировать до реализации границу accepted/completed,
стабильную корреляцию операции, доступ после перезапуска, повтор запроса
с тем же ключом без второго on и типизированные результаты/ошибки.
Синхронное ожидание проще для once, но всё равно требует ранней регистрации
ID и раздельного ожидания. `submit_pulse → operation_id`, затем
`get/wait_operation` лучше отражает независимый cleanup, ценой дополнительного
метода. Рекомендуется второй вариант или эквивалентная явно описанная
семантика существующего `pulse_switch`; имена методов сами по себе ещё
не делают API стабильным.

### 10. Средняя: наличие истории не определяет её пригодность, сериализация не определяет политику

Источник: [§2](../agents/architecture.md), строки
73–89; [§3](../agents/architecture.md),
строки 110–114; [§7](../agents/architecture.md),
строки 272–274. Реальные свойства данных:
[детектор, §2–3](../reference/anomaly-detection.md#2-пригодность-данных).

Положительно: сохранены measured_at, null, покрытие, неатомарный Snapshot и
ограниченная архивируемость вычисляемых значений. Но «при неполноте — unknown»
может отклонить историю с допустимым старым разрывом, после которого есть
достаточное пригодное наблюдение; либо, при трактовке полноты только как
покрытия, пропустить устаревшие измерения. Для сброса важны реальные события
переключателя между температурными точками, а не минутная выборка состояния.
Перед on проверяются online и reset, но свежесть решения и изменение
контура/датчика во время очереди не оговорены.

Сериализация переключателя также не решает, что делать, если CLI меняет
цель/режим контура между детекцией и on. Конфликт может иметь несколько
element_id одного физического котла. Простое выполнение команд по очереди
обеспечивает порядок отправки, но не делает старое решение актуальным.

Исправление: поручить детектору действующие правила пригодности, а DTO —
описание фактических полноты, давности и разрешения рядов. Не вводить новое условие
«все 45 минут без пропусков» без отдельного решения. Задать maximum age
решения и предкомандные предпосылки по привязанному контуру/датчику;
определить конфликтный ресурс и последствия ручной команды для ожидающего
импульса. Широкая блокировка прибора проще, но мешает независимым чтениям и
несвязанным управлениям. Перечень конфликтующих ресурсов точнее, но сложнее.
Рекомендуется узкая блокировка физического сброса с явной инвалидизацией
решения при изменении значимых параметров.

## Оценка сложности и альтернатив

Явный каталог, фиксированные DTO, прямой DI и composition root соответствуют
задаче. В проекте нет самого service locator: регистратор не передаётся
потребителю, потребитель не ищет зависимости в глобальном контейнере.
Прокси конкретного controller API тоже не становится service locator лишь
из-за IPC. Сканирование произвольных plugins, самостоятельные клиенты ZONT у
каждого алгоритма и DI-фреймворк добавили бы сложность без текущей пользы.

Принудительный процессный deadline оправдан заданным контрактом. Управляющий
фасад на все устройства и элементы оправдан необходимостью независимых
потребителей. Отдельный исполнитель off оправдан наличием внешнего действия,
которое должно пережить отмену алгоритма. Сразу десять пакетов, сеть между
локальными компонентами и распределённые lease без реального размещения
были бы преждевременными; текст уже разумно разрешает меньше модулей.

| Вариант | Плюсы | Минусы и граница применения |
| --- | --- | --- |
| Один host, controller и executor в host, отдельные workers | Минимальные затраты на эксплуатацию; общий лимит API, очередь и владение; принудительная остановка потребителя | Смерть host останавливает executor; локальный журнал требует восстановления; недостаточно для обещания off при crash host |
| Один авторитетный executor с durable журналом, workers локально/в функции | Одна точка принятия команд и попыток; cleanup живёт дольше once; проще исключить дубли | Нужны размещение, recovery и наблюдение executor; отказ оборудования остаётся; прямой ЛК требует политики |
| Самостоятельные controller/executor каждого cloud invocation с общей координацией | Эластичное размещение без единственного локального host | Durable CAS, неизвестные результаты, lease/fencing и recovery; высокая сложность при API без заявленной атомарности |
| Потоки или asyncio для всех потребителей | Меньше IPC и bootstrap; удобно для UI и кооперативных задач | Нельзя принудительно остановить произвольный блокирующий код и гарантировать заданный deadline; общий сбой процесса |

Рекомендуется начать с одного авторитетного исполнителя и процесса на
потребителя, фиксируя локальный IPC вместо полноценного сервиса. Сначала
read-only/preview host и неизменный детектор; auto execute — после выбора
cleanup и политики прямого ЛК. Если аппаратный безопасный импульс доказан,
он может существенно упростить executor. Облачный handler текущего этапа
остаётся read-only согласно контракту деплоя; Scheduler запускает once,
continuous размещается отдельно. Архитектурный выбор не является разрешением
деплоя или запуска автоматических команд.

## Итог

Первый проект пригоден как описание направления, но не как закрытый контракт
для реализации автоуправления. Главные требующие решения противоречия:
автозапуск continuous против once-host, отсутствие явного execute, нестабильный
эпизод ограничения попыток, невыбранный механизм cleanup, работающий после смерти host, и область
владения между несколькими host/прямым ЛК. Их нельзя устранить одним finally,
проверкой state или принудительным завершением worker.

До реализации следует закрыть эти решения в архитектуре и добавить сценарии
приёмки: once-host без continuous, preview без эффектов, неизвестный on с
сохранённой попыткой, повторное confirmed после собственного импульса,
одновременные invocation/host, отзыв в очереди, получение ID после timeout,
восстановление после crash host и ручная команда из ЛК во время импульса.
Это проверки будущего поведения; ревью не утверждает, что они уже выполнены.
