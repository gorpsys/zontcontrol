# Фиксированная конфигурация

Сейчас реализованы чтение и офлайн-валидация инфраструктурных конфигов и
контракты алгоритмов. Поточный runtime, регистратор, встроенные алгоритмы
и новая точка входа ещё не реализованы; эти примеры сами ничего не запускают.

Имена фиксированы относительно **рабочего каталога**:

| Файл | Владелец схемы и чтения |
| --- | --- |
| config/controller.json | Управляющий модуль через composition root |
| config/registry.json | Регистратор |
| config/boiler_reset.json | Сам алгоритм boiler_reset |
| config/boiler_cli.json | Сам алгоритм boiler_cli |
| config/\<algorithm_id\>.json | Соответствующий новый алгоритм |

Запуск из checkout и установленного wheel предусматривает переход в корень
проекта с каталогом config/. Поиска вверх по дереву и относительно
site-packages нет. При установке wheel этот каталог нужно подготовить отдельно;
примеры из репозитория не устанавливаются как конфигурация приложения.
Нет общих --config и ZONT_CONFIG, общей схемы настроек алгоритмов или
module_configs у регистратора. Подстановка root/reader в Python-загрузчики
предназначена для обычного DI и офлайн-тестов.

Из корня проекта подготовьте инфраструктурные файлы:

```sh
cp config/controller.example.json config/controller.json
cp config/registry.example.json config/registry.json
```

Для среды без интерактивного терминала вместо второго файла:

```sh
cp config/registry.headless.example.json config/registry.json
```

Затем измените контакт и инфраструктурный профиль под свою среду. Настройки
boiler_reset/boiler_cli и их схемы будут добавлены вместе с самими алгоритмами;
согласованный контракт описан в [архитектуре, §6](../docs/agents/architecture.md#6-конфигурация-регистратора-и-модулей).
Не используйте реальные привязки устройства из примера архитектуры без проверки.

В JSON не должно быть токенов, логинов или паролей. Токен будущий composition
root читает только из ZONT_TOKEN; загрузчики конфигурации окружение не читают.
Контакт API — непустое ASCII-значение без управляющих символов. Неизвестные
поля, включая token/password/module_configs, отвергаются. Ошибка показывает
путь и инструкцию, не содержимое JSON. Обязательный отсутствующий или
некорректный файл отклоняется до внешних действий соответствующего компонента.

## controller.json

Все поля обязательны:

- contact — контакт для X-ZONT-Client;
- http_timeout_seconds — конечное положительное число, не больше 120;
- coordination.delta_seconds и leader_period_seconds — конечные положительные
  периоды. Проверяется возможность аренды по действующим формулам LeaseTiming;
- statistics.path — путь выходного JSONL, statistics.profile — непустое имя
  профиля наблюдений. Загрузчик не создаёт файлов и не открывает статистику.

Delta=1, период=60 и HTTP timeout=15 в примере — **необмеренный профиль для
настройки**, не гарантии ZONT. Подберите и измерьте их перед эксплуатацией.
Таблица rho фиксирована контрактом: исходный период до 60 с включительно —
10%, до 300 с — 5%, до 600 с — 1%, далее — 0.5%. K=(1+rho)/(1-rho).
Она не переопределяется JSON и не выбирается заново по увеличенному lease_s.
Лидерский период не задаёт длительность критической секции алгоритма:
алгоритм сам запрашивает lease_seconds с grant, finally и запасом.
Статистика не служит журналом восстановления или доказательством 99.9%.

## registry.json

- disabled_modules — список уникальных известных algorithm_id, по умолчанию
  пустой. Модуль из списка не создаётся и не читает свой файл.
- autostart_dual_mode — boolean, по умолчанию false. Once-only ожидает запуска,
  continuous-only запускается после регистрации. Модуль обоих режимов ждёт
  start; true разрешает его автоматический continuous. Headless-пример
  запрещает boiler_cli и сохраняет false.
- once_timeouts — объект с парами minimum_seconds/recommended_seconds для
  once-модулей. Оба числа конечны, положительны; recommended не меньше minimum.
  Эффективный minimum — максимум из пары и технического minimum spec.
  Если recommended ниже него или пара отсутствует, регистрация этого once
  отмечается failed; остальные модули регистрируются независимо.

Неизвестные ID и дубликаты в каталоге дают явную ошибку, не пропускаются молча.
Проверки отдельных spec (возможности и timeout) выполняются отдельно, чтобы
регистратор мог отчитаться о каждом модуле. Фабрику вызывают только после них;
сам модуль проверяет свою схему и привязки до собственных внешних действий.

Числа 120/180 — **необмеренный пример формы**, не доказанный minimum сброса.
Техническую границу определяет модуль по обязательным чтениям, grant, импульсу
40 с и cleanup; конкуренция может дать Busy/Timeout при корректном minimum.
Явный once timeout должен быть не ниже эффективного minimum; без него
используется recommended. Continuous не получает deadline регистратора,
его интервалы, внутренние таймауты и повторы принадлежат алгоритму.

## Контракт нового алгоритма

AlgorithmSpec объявляет уникальный algorithm_id, описание, непустой набор
Mode.ONCE/Mode.CONTINUOUS, фабрику, требуемые возможности API и технический
minimum_seconds. ID имеет форму `[a-z][a-z0-9_]*`. Наборы modes и
required_capabilities неизменяемые. validate_catalog проверяет ID и возвращает
разрешённые spec без создания экземпляров. validate_requirements проверяет
возможности API перед фабрикой. Это чистые проверки, runtime они не запускают.

Фабрика получает привязанный к потребителю Controller; часы, безопасный вывод,
ввод/рендерер передаются обычным DI через конструктор или замыкание фабрики.
Регистратор, токен и HTTP-транспорт алгоритму не передаются. Фабрика модуля
читает его фиксированный config/\<algorithm_id\>.json через read_json и сама
проверяет схему, выдавая ConfigurationError с путём. Чужие схемы регистратор
не знает. Изменение конфига применяется после stop/start, без live reload.

run_once(cancelled) возвращает AlgorithmResult с ResultStatus и собственным
value модуля. SUCCESS означает успех операции алгоритма, UNKNOWN/SUPPRESSED
сохраняют самостоятельный смысл. API-успех команды не доказывает восстановление
нагрева. run_continuous(cancelled) выполняет собственный цикл; достаточно
реализовать методы заявленных режимов. Сигнал cancelled требует кооперативного
выхода через finally. Он не отменяет принятую команду и не отзывает монополию.
Состояния зарегистрированного экземпляра: registered, running_once,
running_continuous, stopping, stopped, failed. stopping сохраняется до выхода
потока; принудительной остановки отдельного потока этот контракт не обещает.
