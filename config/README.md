# Фиксированная конфигурация

Реализованы чтение инфраструктурных конфигов, поточный runtime, регистратор,
модули boiler_reset/boiler_cli и точка входа zontcontrol/application.
Эти примеры сами ничего не запускают; инструкция — [README](../README.md).

Имена фиксированы относительно **рабочего каталога**:

| Файл | Владелец схемы и чтения |
| --- | --- |
| config/controller.json | Управляющий модуль через composition root |
| config/registry.json | Регистратор |
| config/boiler_reset.json | Сам алгоритм boiler_reset |
| config/boiler_cli.json | Сам алгоритм boiler_cli |
| config/\<algorithm_id\>.json | Соответствующий новый алгоритм |

Запуск из checkout и установленного wheel предусматривает переход в корень
проекта с каталогом config/. Поиска вверх по дереву и относительно
site-packages нет. При установке wheel этот каталог нужно подготовить отдельно;
примеры из репозитория не устанавливаются как конфигурация приложения.
Нет общих --config и ZONT_CONFIG, общей схемы настроек алгоритмов или
module_configs у регистратора. Подстановка root/reader в Python-загрузчики
предназначена для обычного DI и офлайн-тестов.

Рабочие config/*.json игнорируются Git. Версионируются только примеры
config/*.example.json; личные привязки и настройки остаются локально.

У controller coordination обязательны delta_seconds, delta_cmd_seconds,
leader_period_seconds, profile_id (UUID), poll_seconds, retry_seconds,
jitter_fraction (0–1) и renewal_fraction (0–1, границы исключены).
Пример v2 использует Delta=5 с, Delta_cmd=5 с и период лидера 300 с;
это начальные допущения. Pacing подбирается отдельно воспроизводимой
[калибровкой](../scripts/README.md#калибровка-координации-v2);
simulation не превращает профиль в измеренную границу ZONT. Запрошенный lease должен
помещаться в этот период вместе с поправкой часов и запасом Delta;
приложение не увеличивает период по запросу. Старый controller config
нужно заменить схемой примера до запуска.

profile_id и параметры безопасности должны совпадать у всех клиентов
одного прибора. Для согласованного изменения A→B сначала остановите все
клиенты A. В B можно явно указать previous_profile — объект с точными
profile_id, delta_seconds, delta_cmd_seconds и rho_version=1 профиля A.
Обычные выборы ждут остаток лидерской аренды A и хвост команды, затем
кандидат публикует R1 B, а исполнитель — R2 B. После прерывания между
строками переход продолжается автоматически. Неизвестные данные/профили
не очищаются; миграция и ручная подготовка пустых строк не нужны.

Изменение poll/retry/jitter/renewal не меняет UUID профиля безопасности.
После натурных измерений Delta рекомендуется не меньше
max(5, 10×p99.9, 1.2×max); это запас, а не доказанный максимум. Delta_cmd
меняется по отдельным достоверным верхним оценкам остаточного воздействия.
API RTT, readback уставки и длительность цикла сброса такой оценкой не являются.
Без физического источника подтверждения Delta_cmd остаётся исходным
допущением со статусом unmeasured; simulation, unmeasured и calibrated
нельзя подменять друг другом. Профиль безопасности меняется только вручную,
одинаково у всех клиентов, с новым UUID и согласованным перезапуском A→B.

Из корня проекта подготовьте инфраструктурные файлы:

```sh
cp config/controller.example.json config/controller.json
cp config/registry.example.json config/registry.json
```

Для среды без интерактивного терминала вместо второго файла:

```sh
cp config/registry.headless.example.json config/registry.json
```

Затем измените контакт и инфраструктурный профиль под свою среду. Для
boiler_reset подготовьте config/boiler_reset.json из boiler_reset.example.json
и проверьте все привязки. Для интерактивного CLI подготовьте
config/boiler_cli.json из boiler_cli.example.json;
согласованный контракт описан в [архитектуре, §6](../docs/agents/architecture.md#6-конфигурация-регистратора-и-модулей).
Не используйте реальные привязки устройства из примера архитектуры без проверки.

В JSON не должно быть токенов, логинов или паролей. Токен composition
root читает только из ZONT_TOKEN; загрузчики конфигурации окружение не читают.
Контакт API — непустое ASCII-значение без управляющих символов. Неизвестные
поля, включая token/password/module_configs, отвергаются. Ошибка показывает
путь и инструкцию, не содержимое JSON. Обязательный отсутствующий или
некорректный файл отклоняется до внешних действий соответствующего компонента.

## controller.json

Все поля обязательны:

- contact — контакт для X-ZONT-Client;
- http_timeout_seconds — конечное положительное число, не больше 120;
- coordination.delta_seconds и leader_period_seconds — конечные положительные
  периоды. Проверяется возможность аренды по действующим формулам LeaseTiming;
- statistics.path — путь выходного JSONL, statistics.profile — непустое имя
  профиля наблюдений. Загрузчик не создаёт файлов и не открывает статистику.

Delta=1, период=60 и HTTP timeout=15 в примере — **необмеренный профиль для
настройки**, не гарантии ZONT. Подберите и измерьте их перед эксплуатацией.
Таблица rho фиксирована контрактом: исходный период до 60 с включительно —
10%, до 300 с — 5%, до 600 с — 1%, далее — 0.5%. K=(1+rho)/(1-rho).
Она не переопределяется JSON и не выбирается заново по увеличенному lease_s.
Лидерский период не задаёт длительность критической секции алгоритма:
алгоритм сам запрашивает lease_seconds с grant, finally и запасом.
Статистика не служит журналом восстановления или доказательством 99.9%.

## registry.json

- disabled_modules — список уникальных известных algorithm_id, по умолчанию
  пустой. Модуль из списка не создаётся и не читает свой файл.
- autostart_dual_mode — boolean, по умолчанию false. Once-only ожидает запуска,
  continuous-only запускается после регистрации. Модуль обоих режимов ждёт
  start; true разрешает его автоматический continuous. Headless-пример
  запрещает boiler_cli и сохраняет false.
- once_timeouts — объект с парами minimum_seconds/recommended_seconds для
  once-модулей. Оба числа конечны, положительны; recommended не меньше minimum.
  Эффективный minimum — максимум из пары и технического minimum spec.
  Если recommended ниже него или пара отсутствует, регистрация этого once
  отмечается failed; остальные модули регистрируются независимо.

Неизвестные ID и дубликаты в каталоге дают явную ошибку, не пропускаются молча.
Проверки отдельных spec (возможности и timeout) выполняются отдельно, чтобы
регистратор мог отчитаться о каждом модуле. Фабрику вызывают только после них;
сам модуль проверяет свою схему и привязки до собственных внешних действий.

Числа 120/180 — **необмеренный пример формы**, не доказанный minimum сброса.
Техническую границу определяет модуль по обязательным чтениям, grant, импульсу
40 с и cleanup; конкуренция может дать Busy/Timeout при корректном minimum.
Явный once timeout должен быть не ниже эффективного minimum; без него
используется recommended. Continuous не получает deadline регистратора,
его интервалы, внутренние таймауты и повторы принадлежат алгоритму.

## boiler_reset.json

Модуль читает свой файл при создании, до сетевых действий. Обязательны
device_id, circuit_id, air_sensor_id, coolant_sensor_id, reset_control_id
и check_interval_seconds. ID — положительные целые, датчики воздуха и
теплоносителя должны различаться; интервал — конечное положительное число.
Идентификаторы примера относятся к виртуальному прибору. При проверке модуль
проверяет наличие именно этих значений в каталоге управляющего API.

Необязательные поля принадлежат модулю:

- detection_profile — только smart_2_heating (по умолчанию), действующий
  калиброванный профиль без переопределения порогов;
- grant_wait_seconds — ожидание разрешения, по умолчанию 30 с, больше нуля
  и не больше 30 с;
- grant_poll_seconds — прерываемый интервал опроса разрешения, по умолчанию
  1 с, больше нуля и не больше grant_wait_seconds.

Прочие поля отвергаются. Длительность импульса фиксирована: 40 с. После
успешного off continuous освобождает прибор и ждёт 300 с; once завершается
без этой паузы. В once планировщик может вызывать модуль примерно раз в
15 минут, без дополнительного счётчика или ручного разрешения внутри модуля.
Обычные continuous-проверки используют monotonic-слоты с пропуском просроченных.

Технический minimum spec — 170 с: 30 с на чтение/оценку, 30 с на grant,
20 с на повторные проверки/подготовку, 15 с на on, 40 с на импульс, 15 с на
off/release и 20 с запаса. Запрошенная аренда — 140 с при grant_wait_seconds=30;
первые 30 с чтения в неё не входят. Это **необмеренные инженерные бюджеты**,
а не гарантия длительности HTTP или успешного завершения. Пример recommended
180 с допускает этот minimum; конкуренция/задержки всё ещё могут дать ошибку.
При истечении grant off использует обычный API и отклоняется с видимой ошибкой.
Успех API сброса не доказывает восстановление нагрева.

## boiler_cli.json

Модуль работает только в continuous и автоматически стартует после регистрации.
При создании сам читает config/boiler_cli.json, проверяет все поля и наличие
интерактивных stdin/stdout. Без TTY регистрация даёт failed; headless-пример
регистратора явно отключает модуль. Конфигурация не вызывает чтений или команд.

Обязательные поля:

- devices — непустой список уникальных положительных device_id;
- controls — список объектов device_id/kind/element_id/actions. Каждый прибор
  входит в devices, actions — непустой список уникальных действий фасада;
- graphs — список graph_id/title/series. Каждый series содержит key с явными
  device_id/kind/element_id/field и необязательный label. График относится
  к одному разрешённому прибору; graph_id уникален в пределах прибора.

controls и graphs могут быть пустыми. При запросе проверяется пересечение
привязок с текущими возможностями фасада. Недоступная команда не отправляется;
график требует числовые исторические ряды одной единицы измерения.
Неизвестные поля отвергаются. Необязательные параметры:

- lease_seconds — запрошенная аренда всей ручной команды с получением grant,
  освобождением и запасом, по умолчанию 60, больше нуля и не больше 1200.
  Это инженерная настройка, не гарантия длительности или получения grant;
- grant_wait_seconds — ограниченное ожидание grant через acquire_control,
  по умолчанию min(30, lease_seconds / 2). Конечное положительное число,
  не больше lease_seconds; boolean не допускается. Поле необязательно,
  прежние конфиги без него продолжают работать;
- output_directory — каталог SVG, по умолчанию charts относительно рабочего
  каталога; существующие файлы сохраняются, повторный график получает подкаталог;
- display_timezone — IANA timezone, по умолчанию UTC.

Текущие значения обновляются раз в 60 секунд отдельным потоком. Пропущенные
слоты не догоняются. Таблица показывает quality и возраст измерения, а ошибка
чтения помечает предыдущие данные stale. Ввод не держит монополию; остановка
прерывает ожидание ввода/обновления и дожидается текущего HTTP-чтения.
На конкретный терминал допускается один работающий экземпляр.

Внутри CLI help показывает команды. Например, для виртуальных привязок примера:

```text
command 42 circuit 20496 target-temp '{"target_temp":22}'
command 42 circuit 20496 target-temp '{"target_temp":22}' --execute
command 42 toggle_buttons 8832 trigger '{"target_state":false}' --execute
graph 42 air 2026-10-15T10:00:00+03:00 2026-10-15T12:00:00+03:00
```

Каждая ручная команда сначала показывает адресат и preview. Только --execute
ожидает монополию в пределах grant_wait_seconds и отправляет команду, затем
освобождает сессию, включая ошибку и неизвестный исход. Автоматических повторов
нет. API accepted сообщает
принятие API; физический результат не установлен. Ручной trigger не создаёт
автоматический импульс или off. Другими алгоритмами CLI не управляет.
Остановка отменяет ожидание grant; отказ не отправляет команду и не требует
освобождения сессии. Поток минутного чтения продолжает работу во время ожидания.

graph требует даты с явными UTC offset, возвращает путь SVG и не запускает
просмотрщик. Дополнительный --view явно открывает сохранённый график обычным
просмотрщиком браузера. quit завершает только UI; потеря TTY/EOF даёт failed,
stop/start регистратора создаёт новый экземпляр с перечитанным файлом.

## Контракт нового алгоритма

AlgorithmSpec объявляет уникальный algorithm_id, описание, непустой набор
Mode.ONCE/Mode.CONTINUOUS, фабрику, требуемые возможности API и технический
minimum_seconds. ID имеет форму `[a-z][a-z0-9_]*`. Наборы modes и
required_capabilities неизменяемые. validate_catalog проверяет ID и возвращает
разрешённые spec без создания экземпляров. validate_requirements проверяет
возможности API перед фабрикой. Это чистые проверки, runtime они не запускают.

Фабрика получает привязанный к потребителю Controller; часы, безопасный вывод,
ввод/рендерер передаются обычным DI через конструктор или замыкание фабрики.
Регистратор, токен и HTTP-транспорт алгоритму не передаются. Фабрика модуля
читает его фиксированный config/\<algorithm_id\>.json через read_json и сама
проверяет схему, выдавая ConfigurationError с путём. Чужие схемы регистратор
не знает. Изменение конфига применяется после stop/start, без live reload.

run_once(cancelled) возвращает AlgorithmResult с ResultStatus и собственным
value модуля. SUCCESS означает успех операции алгоритма, UNKNOWN/SUPPRESSED
сохраняют самостоятельный смысл. API-успех команды не доказывает восстановление
нагрева. run_continuous(cancelled) выполняет собственный цикл; достаточно
реализовать методы заявленных режимов. Сигнал cancelled требует кооперативного
выхода через finally. Он не отменяет принятую команду и не отзывает монополию.
Состояния зарегистрированного экземпляра: registered, running_once,
running_continuous, stopping, stopped, failed. stopping сохраняется до выхода
потока; принудительной остановки отдельного потока этот контракт не обещает.
