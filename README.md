# zontcontrol

Python-приложение для чтения данных ZONT, управления приборами и запуска
автономных алгоритмов. Один ЛК может содержать несколько устройств.
Python >=3.11, runtime использует только stdlib.

Управление прямое: контроллер проверяет команду и отправляет её в API.
Локальной и межклиентской монополии, аренды и фоновой синхронизации нет.
Алгоритмы и ручной ЛК могут управлять одним прибором одновременно.
Причина упрощения — [решение от 20.10.2026](docs/history/2026-10-20-remove-synchronization.md).

При первом обращении к выбранному прибору каждый наш клиент добавляет в его
название заменяемый суффикс ` [zontcontrol connected 2026-10-21T12:34:56+00:00]`.
Исходное имя сохраняется; время UTC означает первое успешное чтение прибора, а не
успешное завершение алгоритма. Последующие опросы его не обновляют. Ошибка
записи отметки не мешает работе и не повторяется. Это касается и клиента
чтения/preview; просмотр списка всех устройств ничего не переименовывает.

## Установка и конфиги

```sh
make setup
cp config/controller.example.json config/controller.json
cp config/registry.example.json config/registry.json
cp config/boiler_reset.example.json config/boiler_reset.json
cp config/boiler_cli.example.json config/boiler_cli.json
```

Заполните contact в controller.json, ID приборов/датчиков/управления и
allowlist/графики в файлах алгоритмов. Схемы приведены в [справочнике конфигурации](config/README.md).
Рабочие конфиги игнорируются Git; токены в них не хранятся.
Для запуска без терминала используйте registry.headless.example.json.

## Авторизация

Клиент читает ZONT_TOKEN из окружения. Без него завершает работу с инструкцией.
Отдельная утилита запрашивает логин и скрытый пароль, выводит токен:

```sh
python3 -m zontcontrol.get_token
```

Если токен сохранён в ~/.tokens/zont:

```sh
export ZONT_TOKEN="$(cat "$HOME/.tokens/zont")"
python3 -m zontcontrol list
```

Контакт для X-ZONT-Client задаётся в controller.json и может отличаться от логина.
Пароль не передаётся обычному клиенту; токен не указывается в аргументах.

## Запуск

Команды выполняются из корня проекта. list показывает модули и их состояния.
Continuous-only boiler_cli стартует при регистрации, dual-mode boiler_reset
по умолчанию ждёт явной команды.

```sh
# CLI и постоянно работающий перезапускатор в одном процессе:
python3 -m zontcontrol host --start boiler_reset
# Один цикл детектора и при необходимости настоящий сброс:
python3 -m zontcontrol once boiler_reset --timeout 180
```

boiler_cli требует интерактивный терминал. SIGINT/SIGTERM кооперативно
останавливают модули и ждут их finally. Принудительный kill этой гарантии не даёт.
Once-таймаут возвращает ошибку и сигнал отмены; поток заканчивает cleanup.
Пока прежний запуск не завершился, повторный старт того же алгоритма запрещён.
Один зарегистрированный алгоритм не блокирует команды другого.

## CLI

Текущие значения обновляются раз в минуту, с источником/качеством и известным
возрастом измерения. Сбой чтения помечает прежние данные как stale.
Примеры синтаксиса; ID и графики должны быть в конфиге CLI:

```text
command 42 mode 20 activate '{}'
command 42 mode 20 activate '{}' --execute
command 42 circuit 10 target-temp '{"target_temp":22}' --execute
graph 42 air 2026-10-19T00:00:00+03:00 2026-10-20T00:00:00+03:00
help
quit
```

Без --execute — только preview. С --execute — повторная проверка и одна команда.
Графики сохраняются в SVG; --view открывает файл отдельно. quit закрывает UI,
а не другие алгоритмы. Результат API не доказывает физическое исполнение.

## Автоматический сброс

boiler_reset запрашивает 46 минут истории и применяет
[калиброванный детектор](docs/reference/anomaly-detection.md) к сетке до
45 минутных отсчётов. Только текущая подтверждённая аномалия
запускает on переключателя сброса, 40 с ожидания и off в finally.
boiler_reset не трогает уже включённый переключатель. При stop/исключении, включая
неизвестный исход on, алгоритм немедленно пытается отправить off. Команды не повторяются
автоматически. Ошибка off видна как ошибка запуска.
В continuous после off — пауза 5 минут; once завершается без неё.
Внешний интервал once рекомендуется около 15 минут.
[Полное поведение и результаты подбора](docs/reference/boiler-reset.md).

В истории worktime и расчётной цели воды при дублях одного timestamp
в одном ответе API выбирается запись с абсолютной меткой перед дельтой.
Это правило клиента, а не гарантия ZONT. Например, выбор 57,7 °C вместо
конфликтующей дельта-записи 57,6 °C не доказывает физическую правильность
этой уставки. Остальные конфликты сохраняют unknown —
[правила нормализации](docs/reference/zont-api.md#история).

## Python API

```python
from zontcontrol.application import create_application
from zontcontrol.controller.contracts import ControlKey

with create_application(catalog=()) as app:
    controller = app.controller()
    devices = controller.list_devices()
    snapshot = controller.read_current(42)
    command = controller.prepare_command(42, ControlKey(42, "mode", 20), "activate", {})
    result = controller.execute_command(command)
```

Пример отправляет настоящую команду при выполнении. API v2 также предоставляет
describe_values/read_history/list_controls и read_notes/write_notes. Для работы
только с управляющим API, без запуска регистратора и алгоритмов:

```python
from zontcontrol.application import create_controller

with create_controller() as controller:
    notes = controller.read_notes(42)
    controller.write_notes(42, notes)
```

write_notes полностью заменяет текст, пустая строка очищает поле. Существующий
create_read_controller предоставляет read_notes без метода записи.
Данные нормализованы; неизвестные
метки/пропуски не подменяются текущим состоянием. Отдельный
create_read_controller предоставляет чтение и предпросмотр без метода отправки команд.
При timeout после отправки — CommandOutcomeUnknown без автоматического повтора.
Внешние потребители завершают свои вызовы до app.close().
[Контракты](docs/agents/contracts.md), [архитектура](docs/agents/architecture.md).

```sh

```

[Технические команды, исследования и выпуск](scripts/README.md),
[CHANGELOG](CHANGELOG.md), [история решений](docs/history/README.md).
Облачный запуск использует handler, минимальный ZIP и workflow
Yandex Cloud Functions с OIDC/Lockbox. Версии деплоя, наблюдённые вызовы
и границы внешней проверки — в датированном
[отчёте приёмки](docs/reports/2026-10-21-yandex-cloud-acceptance.md).

Облачный handler возвращает итог, подробный `assessment`
и `log` текущего вызова — строку с точной копией Python stdout/stderr.
Сохраняются записи любых модулей, включая чужие обработчики логов с собственным
форматом и отключённым propagate. Дополнительной фильтрации/переформатирования
для ответа нет: строка может содержать и JSONL, и обычный текст.
Платформенные START/END и прямой вывод через OS file descriptors не захватываются.
При сбое после cleanup он бросает RuntimeError с JSON-отчётом в сообщении:
`status=error`, фиксированная категория `error`, завершённый `result` либо null
и `log`. Вызов завершается исключением; настроенные повторы платформы сохраняются.
Код не пишет токены, конфиги, upstream payload и тексты внутренних исключений
в результат или лог. Сериализация передаёт данные AlgorithmResult целиком,
не разбирая события алгоритма.

Handler также сохраняет этот же `log` в notes устройства
из config/boiler_reset.json. Поле содержит JSON-массив строк: текущий запуск
первым, затем два предыдущих. Старые записи удаляются целиком; строки логов
не разбираются и не фильтруются. Некорректное или чужое содержимое notes
не затирается. Одновременные запуски могут перезаписать историю друг друга:
блокировок и CAS нет. Сохранение выполняется после завершения основного
приложения отдельным коротким контроллером без алгоритмов и собственных логов.
`notes_saved` сообщает принятие записи API, `notes_error` — безопасную причину
сбоя либо null. Ошибка сохранения не меняет исход алгоритма и не запускает
его повторно; исходные ошибки алгоритма сохраняют платформенные повторы.
