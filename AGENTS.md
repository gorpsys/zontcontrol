# zontcontrol

Приложение ZONT: управляющий API, разовые и постоянные алгоритмы, ручной CLI.
Использование — [README](README.md), инструменты — [scripts/README](scripts/README.md).
Перед изменениями выбрать раздел в [индексе](docs/agents/README.md).
Текущие границы — [архитектура](docs/agents/architecture.md), Python API —
[контракты](docs/agents/contracts.md).

## Порядок работы

1. Разделять транспорт/авторизацию, нормализацию, чистый детектор, подготовку
   команд и UI. Потребители используют Controller API v2; детали API ZONT
   остаются в управляющем модуле. Все операции явно адресуют device_id.
2. По решению владельца от 20.10.2026 синхронизация управления удалена полностью:
   нет распределённого или локального мьютекса прибора, лидера, аренды,
   очередей разрешений, sessions/grants и записи координации в name/notes.
   execute_command(command) проверяет актуальные возможности/online и отправляет
   одну команду. Разные алгоритмы, приложения и ЛК могут вмешиваться одновременно.
   Каждый клиент один раз при первом scoped чтении прибора пытается обновить
   заменяемый суффикс времени подключения UTC в name, сохраняя исходное имя;
   это диагностика, а не координация. Ошибка отметки не блокирует работу,
   неизвестная запись не повторяется; notes не используется.
   Не восстанавливать удалённую координацию под видом guard, executor или binding.
   Основание — [решение](docs/history/2026-10-20-remove-synchronization.md).
3. Ручной boiler_cli показывает preview и отправляет команду только с --execute.
   boiler_reset при текущем confirmed_pattern выполняет настоящий сброс:
   on, 40 с ожидания, off в finally. Уже включённый до импульса сброс не трогать.
   finally немедленно пытается отправить off при штатной остановке и исключении;
   неизвестный on тоже требует попытки off. Автоматических повторов команд нет.
   API-успех не доказывает физический результат или восстановление нагрева.
   Kill/смерть host вне гарантии; watchdog, журналы восстановления и отдельный
   исполнитель не требуются. После off в continuous — пауза 5 минут;
   once не ждёт её, рекомендуемый внешний интервал once — около 15 минут.
4. Регистратор использует обычный DI и потоки одного процесса. Once имеет
   таймаут результата и сигнал отмены от регистратора; continuous имеет только
   start/stop и состояние. Его внутренние интервалы принадлежат алгоритму.
   Пока прежний запуск stopping/finally не завершился, повторный старт запрещён.
   Это жизненный цикл одного алгоритма, а не монополия управления прибором.
   Служебные locks состояния регистратора и вывода терминала сохраняются.
   Shutdown ждёт finally зарегистрированных алгоритмов до закрытия транспорта;
   внешние потребители сами завершают свои вызовы до app.close().
5. Конфиг алгоритма — фиксированный config/<algorithm_id>.json, читается и
   проверяется самим модулем. У регистратора config/registry.json, у контроллера
   config/controller.json с contact/http_timeout_seconds. Общих --config/ZONT_CONFIG
   нет. Рабочие конфиги игнорируются Git; шаблоны не содержат credentials.
6. Токен локально — ZONT_TOKEN, в облаке — Lockbox. Пароли/токены не сохранять
   в коде, документации, логах и аргументах. Не выводить произвольные API-ошибки.
7. Не подставлять скрытый «Котел» вместо «Отопление». Сохранять реальные метки
   времени, null/пропуски и unknown. Детектор и его калибровка не меняются
   из-за удаления синхронизации. Порог менять только с обоснованием и проверкой.
8. Правки через apply_patch, сохраняя чужую работу. Runtime — stdlib;
   новые зависимости согласовывать. Проверять unittest, make check и при
   изменении состава пакета make package-check. Офлайн-проверки не вызывают ZONT.
9. README — текущее приложение; CHANGELOG — выпуски; docs/reference — текущие
   справочники; docs/history — решения; docs/plans — будущая работа.
   Прототип заменён полностью, старые Python/CLI/JSON контракты не сохранять.
   Удалённый API монополии не поддерживать через совместимые заглушки.
10. SemVer X.Y.Z: __version__ в zontcontrol/__init__.py совпадает с первым
    выпуском CHANGELOG. Один PR — один выпуск; CI требует номер выше тегов
    и базы PR. Аннотированный vX.Y.Z создаёт Release tag на SHA слияния;
    вручную теги не публиковать/не переносить. [Процедура](scripts/README.md#версии-и-выпуск).

## Облако

Цель — Yandex Cloud Functions, GitHub OIDC и boiler_reset once раз в 15 минут
с настоящим импульсом при confirmed_pattern. Отдельные функция, deploy SA и
секрет z_token; cloud/folder, bucket, federation, runtime SA/invoker и журнал
переиспользуются из autorepeater по решению владельца. Исходные ресурсы
не менять. Следовать [контракту деплоя](docs/agents/deployment.md) и
[согласованному плану](docs/plans/20261020165020-yandex-cloud-boiler-reset-implementation-plan.md).
Каждый ручной запрос yc отдельно подтверждается владельцем; согласованный
автоматический workflow не требует подтверждений каждой команды.
Таймер создаётся и включается только после первого успешного деплоя и
отдельного подтверждения владельца. Сборка/CI/план не означают активацию.
