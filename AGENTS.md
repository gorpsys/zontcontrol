# zontcontrol

Клиент ZONT: чтение, разовая оценка нагрева и явные команды управления.
Использование — [README](README.md), инструменты — [scripts/README](scripts/README.md).
Перед изменениями выбрать раздел в [индексе](docs/agents/README.md).
Целевая архитектура управляющего API и автономных модулей —
[architecture.md](docs/agents/architecture.md); реализация ещё не начата.
Переработка заменяет прототип: старый монолитный клиент должен исчезнуть,
его ответственность разделяется по архитектуре. Обратная совместимость
прежних Python/CLI/JSON-контрактов не требуется; legacy-адаптеры не вводить.

## Порядок работы

1. Сохранять разделение API-клиента, нормализации данных, чистой логики
   обнаружения, подготовки команд и CLI. Сначала проверка, затем эффект.
2. Существующий ручной CLI по умолчанию показывает предпросмотр и отправляет
   команду с --execute. У автономных алгоритмов поведение задаёт сам модуль:
   boiler_reset при подтверждённой аномалии выполняет настоящий сброс.
   Общего переключателя preview/execute у регистратора/управляющего модуля
   не требуется. Паузы и политика повторных попыток принадлежат конкретному
   алгоритму; общий лимит/guard или обязательное хранилище для них не вводить.
   В boiler_reset finally немедленно выключает сброс при штатной остановке
   и исключениях. Журналы, watchdog и независимый исполнитель не требуются;
   принудительный kill/смерть host вне этой гарантии.
   Все управляющие воздействия требуют монополии на целый прибор в общем
   исполнителе: один владелец на прибор, разные приборы допускают параллельное
   управление. Без своей монополии — ошибка без сетевой команды. Чтения и
   предпросмотр не блокируются. Принятая от владельца команда исполняется без
   проверки активности запуска и отмены по его таймауту; это одинаково для
   обычных команд и finally. Монополия сохраняется до завершения finally.
   Локальный мьютекс не охватывает отдельные исполнители и прямой ЛК;
   общий флаг ZONT не считать доказанным распределённым мьютексом.
   Условный Fischer + lease используется только для выбора лидера устройства:
   notes (R1) — лидерство и запросы/heartbeat, name с исходным префиксом (R2)
   — разрешение. Исполнители R2 только читают. Лидер перед записью R2 проверяет
   R1; исполнитель проверяет grant и token текущего срока лидера. L выбирает
   кандидат; один непрерывный срок ограничен 20 минутами от первого захвата.
   Продление не сбрасывает общий предел. LeaseLost останавливает роль
   координатора, не отзывает монополию алгоритма и не отменяет его finally.
   Для часов принят ступенчатый rho по исходному периоду до поправки:
   до 60 с включительно 10%, до 300 с 5%, до 600 с 1%, свыше 600 с 0.5%.
   K=(1+rho)/(1-rho); ступень фиксируется на интервал, в R1/R2 хранится
   clock_rho, по увеличенному lease_s её заново не выбирают.
   Алгоритм запрашивает lease_seconds на получение grant и всю критическую
   секцию с finally и запасом; исполнитель не оценивает её длительность.
   Новая команда допускается только до локального истечения аренды, без
   отдельного резерва времени на команду (считается быстрой и атомарной).
   При истечении новые команды, включая finally, отклоняются; принятые до
   истечения завершаются. Удержание локального мьютекса не продлевает R2.
   Текущая схема принята с риском, сбором статистики и доработками по ней;
   контракт — docs/reference/leader-election.md, учёт —
   docs/reference/orchestration-risk.md. Предварительно доказывать 99.9% для
   принятия схемы больше не требуется; достигнутые 99.9%, строгую безопасность
   и линеаризуемость ZONT не заявлять без оснований. Не возвращать ради
   статистики отклонённые журналы восстановления/watchdog.
   Прямой ЛК сохраняется по решению №7: редкие вмешательства контролируются
   человеком, риск принят. Предусмотреть видимую индикацию занятого управления
   по grant в name/R2 с сохранением исходного префикса. Ручная команда во время
   импульса не отменяет off из finally; включённый до импульса сброс не трогать.
   Индикацию не представлять технической блокировкой ЛК или доказательством
   автора команды; дополнительных диалогов на штатное завершение не вводить.
   По решению №8 приложение работает одним процессом с потоками алгоритмов
   и обычным DI. Только для once регистратор сам возвращает Timeout
   и выставляет сигнал отмены. Continuous не имеет deadline регистратора:
   внутренние циклы, проверки, интервалы и таймауты принадлежат алгоритму,
   регистратор не задаёт им бюджеты. Его роль — start/stop и состояние;
   управляющие воздействия требуют действующей монополии в обоих режимах.
   Конфиг каждого алгоритма — его внутреннее дело: фиксированный файл
   config/<algorithm_id>.json, который читает и проверяет сам модуль.
   У регистратора свой config/registry.json без module_configs, у управляющего
   модуля config/controller.json. Общие --config/ZONT_CONFIG не вводить;
   подробности запуска из корня проекта — в архитектуре, §6.
   Остановка кооперативная, ожидания прерываемые, HTTP имеет свои таймауты.
   Зависший поток не убивается: stopping и его монополия сохраняются до
   завершения finally/принятых команд; повторный запуск в это время запрещён.
   IPC и отдельные процессы алгоритмов не вводить. Полную изоляцию от зависания
   процесса или принудительную остановку отдельного потока не обещать.
   По решению №9 обычные команды синхронные: успех ответа API, явная ошибка
   либо неизвестный исход после отправки при timeout/обрыве. Автоматических
   повторов нет. Обязательный мониторинг каждой команды и сервис operations
   не вводить; API-успех сброса не доказывает восстановление нагрева.
   По решению №10 история служит входом действующего калиброванного детектора.
   Его проверки и unknown сохраняются; дополнительного архитектурного допуска
   истории/срока решения и автоматического пересчёта из-за ручных вмешательств
   не вводить. Вмешивающийся человек знает последствия и принимает риск.
   Офлайн-проверки не обращаются к ZONT; запись архитектуры
   не запускает алгоритмы и не отправляет команды.
3. Не подставлять скрытый контур «Котел» вместо «Отопление»; использовать
   настоящие метки времени. unknown не превращать в normal или отказ.
4. Токены и пароли не хранить в коде, документации, логах и аргументах.
   Локально токен передаётся через окружение, в облаке — из Lockbox.
5. Делать правки через apply_patch, сохраняя чужую работу. Новые зависимости
   согласовывать до добавления; текущий runtime использует только stdlib.
6. Проверять поведение подходящими unittest и make check. Пороги детектора
   менять вместе с обоснованием и результатами проверки.
7. README описывает текущее приложение; CHANGELOG — выпуски; справочники —
   контракты; docs/history — решения; docs/plans — будущую работу.
8. Версии — SemVer X.Y.Z: литерал __version__ в zontcontrol/__init__.py
   совпадает с первым разделом выпуска CHANGELOG. Один PR — один выпуск;
   CI требует номер выше тегов и версии базы PR. Аннотированный vX.Y.Z
   создаёт Release tag на SHA мержа, вручную теги не публиковать/не переносить.
   Процедура — [scripts/README](scripts/README.md#версии-и-выпуск).

## Облако

Планируется Yandex Cloud Functions и GitHub OIDC. Ресурсы autorepeater
не переносить: идентификаторы zontcontrol задаются отдельно.
Применять [контракт деплоя](docs/agents/deployment.md). Сборка, CI и план
не означают выполненного деплоя или разрешения автоматически сбрасывать котёл.
